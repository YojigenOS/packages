# host/provides.txt —— 构建环境基线
# ============================================================================
#
# 这份列表是「构建环境必须提供、不再由包依赖解析去解决」的包。
#
# 它衡量自举进度：每当 YojigenOS 用自己构建出的包替换掉一项，就把对应行
# 删掉。5 → 4 → 3 → 2 → 1 都发生过。
#
# 但它**永远不会空**，而且这不是失败。引导环节存在内在的循环依赖：
#
#     glibc 构建时需要 make
#     make  运行时需要 glibc
#
# 这个环无法靠"多构建几轮"消除，只能由构建环境提供一个起点。LFS 用
# 「临时工具 → 正式系统 → 重建」三段结构处理它，本质也是环境给起点。
#
# 所以真正的自举标志不是"列表为空"，而是：
#     **列表里的东西是我们自己构建的，且构建环境是我们自己搭的。**
#
# 规则：
#   - 每行一个包名，# 之后是注释
#   - 出现在这里的包，构建时会被跳过（视为已由构建环境满足）
#   - 不在列表里、又没构建过的依赖，会直接报错，不会静默跳过
#
# ============================================================================

# --- 工具链：引导的起点，不是进度 -----------------------------------------
#
# 这三个 **已经自建成功过**（binutils 2.47 汇编链接出可运行程序；gcc 16.2.0
# 编译并运行 C 与 C++；make 4.4.1 用它重建了自己，两次构建逐位一致）。它们
# 回到基线里，**不是回退**，而是因为它们构成一个自身无法消解的环：
#
#     gcc 的构建需要 gmp / mpfr / mpc
#     gmp 的构建需要一个 C 编译器
#     → gcc → gmp → gcc
#
# 任何编译器都得用「某个已经存在的编译器」来构建。这个环只能由构建环境
# 提供一个起点，和 glibc 那条是同一类。
#
# 【两个地方对基线的理解不同，这是有意的】：
#
#   deps.py        基线里的包不参与依赖闭包 —— 不合并、不等待。构建环境
#                  里本来就有它们，合并是多余的。
#   order.py       基线里的包【仍然出现在构建列表里】—— 断掉的只是「等待」。
#                  自举的目标正是重建它们，把它们从列表里删掉就本末倒置了。
#
# 换句话说：基线决定「谁不用等」，不决定「谁不用建」。
# -------------------------------------------------------------------------
gcc
make
binutils

# --- 关于 autotools：它【不】在这里 ---------------------------------------
#
# 这里原来还列着 perl / autoconf / automake / libtool，理由是那个环：
#
#     libxcrypt → autoconf → perl → libxcrypt
#
# 那个理由当时是对的，但用错了办法。加进基线意味着 deps.py 会【跳过合并
# 它们】——于是 autoreconf 用的还是构建环境镜像自带的那份。而在第一轮里
# 构建环境是 Debian，它的 libtool 是 2.5.4，缺 LT_SYS_SYMBOL_USCORE：
#
#     configure.ac:56: error: possibly undefined macro: LT_SYS_SYMBOL_USCORE
#
# 我们自己建的 libtool 2.6.2 有这个宏，但被基线挡住了，送不进去。
#
# 正确的断法是【不让环形成】：让 libxcrypt 走发行包（它带 configure，不需要
# autoreconf），环就没了。于是 autotools 不必进基线——它们会被真的建出来，
# 通过配方的 build 依赖合并进 sysroot，然后才是被用的那一份。
#
# 教训：基线是用来断【真】环的（编译器没法依赖自己），不是用来绕开"某个包
# 需要先建好"的。后者排序能解决。

# --- 当前基线 -------------------------------------------------------------

# 编译，含 usr-merge 布局）。留在这里是因为上面说的那个内在循环：一旦从
# 依赖解析里去掉，glibc → make → glibc 立刻成环。
#
# 它退出基线的条件不是"我们构建了它"，而是"构建环境换成了我们自己的镜像"。

#   而用我们自己的 base-devel 时，语义上应该是【全部 48 个】。
