# 自举历程

按时间记录自举这件事怎么走通的。

**这是【记录】，不是【指南】。** 要找「自举是什么、顺序是什么、产物丢了
怎么办」，看 [`docs/指南/自举.md`](../指南/自举.md)。

留在这里的原因：**里面的排查方法能复用**——怎么确认一个 bug 是上游的、
怎么从「构建卡在某个包」定位到真正的原因、怎么分辨一个失败是环境问题
还是代码问题。还有一节「两次空验证」，讲的是**一个恒为真的检查比没有
检查更糟**。

## 两次空验证 —— 记在这里当教训

写这份文档的时候我想先「验证手写顺序是对的」，结果连续两次得到绿灯，
**两次都什么都没验证**：

| 第几次 | 写了什么 | 为什么是空的 |
|---|---|---|
| 1 | `for d in deps_for(spec, arch)` | `deps_for` 返回的是 **dict**，遍历到的是 `"runtime"` 这种键，不是包名 → 图里 **0 条边** → 排序结果就是字母序，而检查 `-1 > -1` 恒为假 |
| 2 | 改用 `direct_deps` | 图有 108 条边了 ✓ 但**有环** → 抛异常 → `order` 被设成空列表 → 比较又变成 `-1 > -1` → **绿灯依旧** |

**教训不在这两个 bug 本身，而在于**：一个检查如果**恒为真**，它比没有检查更糟——
它给出的是"已验证"的错觉。第一次绿灯让我差点把「手写顺序是对的」写进待办。

**能用的检查必须有一条会失败的路径。** 第二次之后之所以发现，是因为我把
「图里有几条边」也打出来了——**顺带输出的那个数字**才是真正的检查。

## 2026-10-10：两个架构的全量引导都成功了

第一次跑完 42 个包 —— **aarch64 和 x86_64 都是**。

```
✅ build (aarch64)  引导 —— 建出全部包    53 分 13 秒
✅ build (x86_64)   引导 —— 建出全部包    55 分 43 秒
```

x86_64 此前两次都死在 `glibc`（38/41，11 秒）。真因不是 glibc，是**依赖合并
破坏了构建容器**——详见下面那节。

### 让 x86_64 走通的三个修复

**① 基线挡住了我们自己的 libtool**

`bootstrap/provides.txt` 里列着 `perl/autoconf/automake/libtool`，于是 `deps.py`
认为「构建环境已提供」而跳过合并——`autoreconf` 用的还是 Debian 那份
（libtool 2.5.4，缺 `LT_SYS_SYMBOL_USCORE`）。

**正确的断法是不让环形成**：让 `libxcrypt` 走发行包（它带 `configure`，
不需要 autoreconf），`libxcrypt → autoconf → perl → libxcrypt` 那个环就没了。
于是 autotools 不必进基线，它们会被真的建出来并用上。

**② 合并依赖时保护构建容器的布局**

```
Debian amd64:  /lib64 → usr/lib64
               /usr/lib64/ld-linux-x86-64.so.2   ← 动态链接器住在这里
我们的包:      filesystem 提供 usr/lib64 → lib

cp -a /in/sysroot/. /   ← 一覆盖，链接器就悬空了
        ↓
容器里所有动态链接的程序立刻全废
        ↓
实测报错：Dynamic loader not found: /lib64/ld-linux-x86-64.so.2
```

aarch64 一直没暴露：那里的链接器是 `/lib/ld-linux-aarch64.so.1`，而
`/lib → usr/lib` 两边一致。**只有 x86_64 的 lib64 家族有分歧。**

修法：合并时**动态排除容器的挂载点**，再排除我们自己的布局路径：

```sh
while read -r _dev mnt _rest; do
  [ "$mnt" = "/" ] && continue
  EXCLUDES="$EXCLUDES --exclude=.$mnt"
done < /proc/mounts
```

**动态算，不写死清单**——实测它抓到了 `/in/sysroot`（我们自己的绑定挂载），
写死的清单想不到这一条。

**③ 一个诊断步骤不该有阻断的权力**

引导成功之后，job 却因为「上传构建日志」失败而报错，连带 `selfhost` 被跳过、
推送没跑。两个原因：`upload-artifact` 只认工作区里的路径（给 `/tmp` 会被
拒绝），而且它没有 `continue-on-error`。

**教训**：把日志收集放在关键路径上，等于给一个可有可无的东西发了否决权。

### 三次错误归因，都是环境问题

```
✗ "libffi 的树 autoconf 不了"      → 是基线挡住了我们自己的 libtool
✗ "libxcrypt 的树不行"             → 同一个原因
✗ "glibc 在 x86_64 上要特殊处理"    → 是合并破坏了容器
```

**"某个项目/某个架构有问题"这种结论要格外小心**——它听起来像事实，
实际往往只是"我这儿缺东西"。

## 自举到底在抓什么：四类问题

自举不是一个仪式，它是一个**探针**。用别人的构建环境时，一切缺口都会被那个
环境悄悄补上；换成自己的，缺口才会变成错误。

实测下来，错误分成四类，一类比一类深：

### 第一类：依赖没声明（十来个）

构建时调用了某个命令，但配方里没写。用 Debian 环境时它在那儿，换成自己的
就没了。

```
patch · util-linux · libcap-ng · binutils · bison · python3
m4 · expat · libffi · libxcrypt · rsync
```

**发现手段**：跑一遍，报 `command not found`。

### 第二类：包不完整

依赖**声明了**，但提供方给得不全。

```
cc   —— POSIX 规定 C 编译器叫 cc，而 gcc 上游自己不建这个链接
       （Debian 用 update-alternatives 补）。而我们只建了 c++。
       报错：ccache: error: Could not find compiler "cc" in PATH
```

**和第一类的区别**：第一类是"没人提供"，这一类是"有人提供，但给漏了"。
**发现手段**：跑一遍——`command -v` 审计找不到这类问题，因为命令确实存在。

### 第三类：工具链更严格

上游代码在更老的编译器下能过，在新编译器下过不了 `-Werror`。

```
libxcrypt  strchr 的 const 传播规则在 GCC 14+ 变了
           报错：initialization discards 'const' qualifier
gmp        C23 把 f() 的含义从「参数任意」改成「无参数」，configure 里的
           一个 K&R 风格测试编译不过
```

**这一类的意义**：用别人的工具链时，你的代码质量由**那个**工具链的标准决定；
换成自己的，标准才由你决定。

### 第四类：驱动自己的 bug

**最难的一类**，因为它不在包上，在工具上。

```
collect.py 的 _write_package：目录用 mkdir 建（默认 0755），
            于是 filesystem 里 chmod 1777 的 /tmp 变成 0755。
            文件那一路有 shutil.copy2 兜着，只有目录会中招。
            而构建是降权跑的 → 写不了 /tmp →
            glibc 的 configure 报
            "config.guess: cannot create a temporary directory in /tmp"
```

**它一直藏着的两个原因**：

1. `home`/`etc`/`var` 本来就是 0755，看起来都对——**只有特殊模式会露馅**
2. 报错是 `Permission denied` 和 "cannot create a temporary directory"，
   **看不出和权限有关**

**而最刺人的是**：`merge_tree`（deps.py）里早就写着同一句话——

> 目录的权限也要带过来。mkdir 用的是默认的 0755，而 /tmp 是 1777、
> /root 是 0700——丢了这些模式，构建会以莫名其妙的 "Permission denied"
> 失败，而且看不出和权限有关。

它那里修了，`collect.py` 这里漏了。**同一句话、同一个错、两个地方。**

> **写下来的教训，只有真被读过才有用。**

### 这四类对"怎么验证"的启示

| 类 | 怎么发现 |
|---|---|
| 一 | 跑一遍，看 `command not found` |
| 二 | 跑一遍——**`command -v` 审计查不出来**（命令确实存在） |
| 三 | 跑一遍，看 `-Werror` 报的新警告 |
| 四 | **跑一遍，然后把每个包的完整日志留下来** ✗ |

第四类说明了日志为什么必须完整：那次的失败信息只有 8 行，而真正的错误
（`config.guess`）在更上面。**"日志在 /tmp"那句假话，让排查绕了很久。**

### 这一轮之前，倒数第二个坎是「目录模式」

前面 41 个都过了，只有最后一个 `glibc` 死在 configure 的第一步：

```
config.guess: cannot create a temporary directory in /tmp
```

根因是 `collect.py` 的 `_write_package`：**目录用 `mkdir` 建（默认 0755），
不拷模式**。于是 `filesystem` 里 `chmod 1777` 的 `/tmp` 变成 0755，而构建是
**降权**跑的——写不了临时文件。

这个 bug 藏了很久，因为它只影响**特殊模式**：`home`/`etc`/`var` 本来就是
0755，看起来都对；只有 `/tmp`（1777）和 `/root`（0700）会露馅。

而 `merge_tree`（deps.py）里早就写着同一句话。**同一句话、同一个错、两个地方。**

### 自举这件事的结论

**它是一个探针，不是一个仪式。** 用别人的构建环境时，一切缺口都会被那个
环境悄悄补上；换成自己的，缺口才会变成错误。实测抓出四类问题，见上一节。

**而它证明了 0011 那个判据**：

> 用 `base-devel` 能构建出 `base-devel` 本身。

跑通了。这条链从这一刻起闭合了。

会自动拿到自己架构的那份——这才是一个能用的发布。

### x86_64 那道墙：CET

它死在最后一个包 glibc，链接 ld.so 时：

    undefined reference to `_dl_cet_open_check'
    undefined reference to `_dl_cet_check'

驱动给 x86_64 加了 `-fcf-protection=full`，而 glibc 的 configure 会检测
「编译器是否默认开 CET」，检测说不开 → 不编 `sysdeps/x86/dl-cet.c`
→ 但别的文件引用了那些符号 → 链接失败。

**加固参数本身没错，错的是它没被 configure 看见。** 显式 `--enable-cet`
让检测和构建一致——加固照旧，只是自洽了。

### 另一道：libpng 的并行竞态

它死在 [31/42]，报错是：

    implicit declaration of function 'setjmp'
    'LIBPNG_WAS_COMPILED_WITH__PNG_NO_SETJMP' undeclared

**完全指不到真正的原因。** 真因是 libpng 自己的 Makefile 有竞态：
`contrib/libtests/` 需要构建时用 gawk 生成的 `pnglibconf.h`，但没声明这个
依赖，于是并行 make 先编测试、后生成头文件。

定位方法是把两边的 **configure 输出逐行对比**——完全一致，所以分歧只能在
「构建时发生了什么」。然后看到同一个文件被编了两遍（竞态的典型样子），
再对着 `[构建] ... -j4` 和本地的 `-j8` 一看就明白了。

**跟并行度无关，是运气。**

### 还有一个副产品：CI 的日志能读了

GitHub 的 artifact 存在 Azure blob 上，而那个域名被 DNS 污染（解析到
11.142.125.225 这种假地址），`gh run download` 一直 EOF。

办法是绕开本地 DNS：用 DoH 查真实 IP，再 `curl --resolve` 指过去。
**从此 CI 的完整日志都读得到**——上面那两个 bug 都是这么找出来的。

### 端到端验证：陌生人拉得到吗

发布出去不算完，得验一下**别人的那条路**通不通：

```
$ docker manifest inspect yojigenos/base-devel:edge
    manifests: [ arm64/v8, amd64 ]        ← 清单里两个架构都在

$ docker pull yojigenos/base-devel:edge   ← 只写 :edge，不指定架构
    架构: x86_64                           ← 自动选中了 amd64
    gcc:  gcc (GCC) 16.2.0                 ← 我们自己建的那个
    cc:   在 ✓                             ← cc 修复在里面
    /tmp: drwxrwxrwt                       ← 目录模式修复在里面
```

**这才是"发布"的完整含义**：一个陌生人只写 `:edge`，拿到的是他那个架构的、
带着全部修复的、用 GCC 16.2.0 的构建环境。

而 `gcc (GCC) 16.2.0` 出现在镜像里这件事本身，就是整个项目的意义——
**它不是 Debian 的 gcc，是从源码建出来的。**

## 第五类：上游工具自己的回归

前四类都在我们的配方或驱动里。这一类不在——**是我们用的某个上游工具坏了。**

### gawk 5.4.1：未赋值数组元素变成 "0"

```
$ gawk 'BEGIN { if (a["x"] == "") ; a["x"] = a["x"] "y"; print "[" a["x"] "]" }'
[0y]      # 5.4.1
[y]       # 5.4.0、mawk、以及 POSIX 期望的
```

一个"读过但从未赋值"的数组元素，**一旦参与过比较或判断**，再当字符串用就
变成了 `"0"`。上游自己的 `make check` 就有 6 个测试失败（arraysort2、
delarpm2、elemnew2、elemnew4、matchuninitialized、typeof7）。邮件列表里还
提到它同样会让 **GCC 16.2 的构建失败**。

**触发条件是"编译 gawk 时没有 MPFR"**——而 gawk 在我们的构建顺序里排第 21、
mpfr 排第 29，所以我们的 gawk 必然是 `--without-mpfr` 建的，正好落在里面。

### 它在我们这儿长什么样

libpng 的 `scripts/options.awk` 里有这么一句：

    requires[opt] = requires[opt] " " val

`requires["UNKNOWN_CHUNKS"]` 从来没被赋过值，于是这一句读它时拿到 `"0"`，
`pnglibconf.h` 里**每一项都成了 undef**，`PNG_SETJMP_SUPPORTED` 消失，
`png.h` 不 include `<setjmp.h>`，最后报出来的是：

    contrib/libtests/pnggetset.c:53: error: implicit declaration of function 'setjmp'

**一个 awk 的版本差异，报成了"setjmp 没有声明"。**

### 怎么找到的（这段方法值得复用）

1. **先要一个一分钟的复现**。从"每轮两小时的 CI"变成"本地一分钟"，这一步
   比什么都值钱。做法：把 CI 用的那个构建环境从 Docker Hub 拉下来，用它
   直接跑那一个包。
2. **切分流水线，找第一个分歧点**。libpng 的生成是四步 awk/gcc 串起来的。
   我 diff 了第①步的产物 `tf4`——**完全一致**——于是断定分歧在第②步。
3. **插桩，看类型而不只是看值**。`typeof()` 给出了 `untyped` vs `unassigned`，
   一眼就看出这不是"值算错了"，是"类型语义变了"。
4. **写最小复现**。七种写法全试一遍，确认是基础语义而不是边角情况。
5. **查上游**。搜到 bug-gawk 的同一个报告，连触发条件（无 MPFR）都对上了。

### 修

**停在 5.4.0**，而不是打补丁。理由：前者是上游发布的、sha256 可校验的源码
（符合配方约定），后者要我们维护一份改过的源码。5.4.2 一出来就升回去。

### 这一类对"验证"的启示

**报错信息指向的地方，可能和真正的原因隔着好几个抽象层。** 这次的链条是：

    awk 版本 → 数组元素语义 → libpng 的配置生成 → 一个宏没定义
             → png.h 的分支 → setjmp 没声明 → 编译错误

**从最后一环往回查是查不动的**（"为什么 setjmp 没声明"和 awk 有什么关系？）。
能做的是**找到两个环境的第一个分歧点**，而不是盯着最终的错误看。

### 附记：构建环境里"恰好有什么"，会悄悄改变产物

gawk 的 configure 会自动探测 mpfr，探测到就链接它。而我们的配方只声明了
`glibc`，于是同一份配方产出两种 gawk：

    CI 第一遍（Debian 构建环境，没装 libmpfr-dev）→ 不带 mpfr
    自举那一遍（base-devel 镜像里有我们建的 mpfr） → 链接 libmpfr.so.6

实测本地建出来的就是后一种，直接跑不起来：

    $ gawk --version
    /g/usr/bin/gawk: error while loading shared libraries: libmpfr.so.6

**libmpfr 于是成了一个未声明的运行时依赖，而且两边行为不一致。**

修法是显式 `--without-mpfr`：**关掉自动探测，构建就只由配方决定，
不由环境决定。**

#### 这条要注意的地方

**所有 autoconf 包都有这个性质**——它们会自动探测可选依赖。所以理论上每个
包都可能"因为构建环境里恰好有某个库"而产出不同的东西。

这也是"固定点"这件事的一个隐藏障碍：**如果两遍看到的构建环境不同，
产物就不可能逐字节相同。** 第一遍是 Debian 底、第二遍是我们自己——
这个差异是设计的一部分，但它带来的影响不只是"工具链不同"，还包括
"探测到的可选依赖不同"。

gawk 这个是被逮住的第一个。以后遇到"两遍产物不一致"时，**先想想是不是
某个 configure 探测到了不一样的东西**，而不是先怀疑编译器。

谁先出结果，一条挂了不影响另一条，而且可以只触发一个。

> ★ **2026-10-12 追记：这三个文件后来合并回一个 `bootstrap.yml` 了。**
> 拆开的两个理由（不互相等、可以只触发一个）在「单个 job + 矩阵 +
> `fail-fast: false`」下同样成立——当时那两个坑是 `needs: build` 和默认的
> fail-fast 造成的，不是矩阵本身。而一份文件一个架构的代价是两者会漂：
> 实测两份只差 48 行，且全是架构字样。理由见
> `.github/workflows/bootstrap.yml` 的抬头。

```
  1..10 的和 = 55
```

**内核版本行里的 `gcc (GCC) 16.2.0` 是我们自己建的。** 这是整件事的重点：
它不是 Debian 的内核，也不是 Debian 的工具链编出来的。

### 为了这一步补的四个包

    ① flex      内核 make defconfig 要它生成 kconfig 的词法分析器
    ② bc        内核算 include/generated/timeconst.h 要用它
    ③ openssl   内核的 certs/extract-cert 要它读 X.509
    ④ cpio      打 initramfs 要它

**前三个都是内核自己说的**——拿一个空的源码树试，让失败告诉我们缺什么：

    LEX     scripts/kconfig/lexer.lex.c
    /bin/sh: line 1: flex: command not found

    /bin/sh: line 1: bc: command not found
    make[2]: *** [Kbuild:24: include/generated/timeconst.h] Error 127

    certs/extract-cert.c:21:10: fatal error: openssl/bio.h: No such file

第三个试过绕开（关掉内核内建的信任钥匙串），关不掉——Kconfig 的 `select`
会覆盖配置文件里的显式值。所以改成把 openssl 补上，而它本来就在路线图上。

### 第四个暴露了一个更值得记的形状

`cpio` 那次：

    bash: line 11: cpio: command not found
    initramfs: 4.0K

**失败没被抓住。** 脚本里写的是

    find . | cpio -o -H newc | gzip > initramfs.cpio.gz

`set -e` 只看管道最后一个命令（gzip，成功了）。于是产出一个 4 KB 的空
initramfs，QEMU 立刻退出，没有任何错误信息。

**这和同一天在驱动里抓到的那个 bug 是同一个形状**：

    run.sh 没有 set -e      → build 失败、package 照跑，退出码取自 package
    管道没有 pipefail        → cpio 失败、gzip 照跑，退出码取自 gzip

两次都是「**错误没有沿着管道／进程传上来**」。修法也一样：让每一环都能
把失败传出去（`set -e` 进 run.sh、`set -o pipefail` 进管道），再加一道
独立的结果检查（产物里有没有 vmlinuz、initramfs 是不是空的）——
因为让错误传上来还不够，有些失败会产出「成功但内容为空」的结果。

### defconfig 的取舍

第一次编内核花了 **47 分钟**——aarch64 的 defconfig 把 nouveau、iwlwifi、
mediatek 的 codec 全带上了，和 QEMU 虚拟机毫无关系。

这是有意的：defconfig 是**已知能启动**的，而手写最小配置的失败模式是
「能启动但少个驱动」——那比编得慢难查得多。**配置瘦身要等到能开机之后**，
因为那时候才知道哪些真的不需要。

（第二次编只用了 4 分 31 秒，ccache 把第一次的结果缓存住了。）

## 2026-10-13：一次「验过了」都没验到 —— 四类空验证

这一晚在做镜像组装和磁盘镜像。**连着修了六个东西，其中四个属于同一类问题：
我的"验证"是假的。**

和上面那节「两次空验证」是同一条线，但这次的更隐蔽——**因为命令都跑了、
都绿了、都打印了东西**。

### 一、验的语言不是跑的语言

`scripts/assemble.sh` 的 shebang 是 `#!/bin/sh`（CI 上是 dash）。我给它加了
bash 数组：

```sh
LABEL_ARGS=(
    -c "LABEL ..."
)
```

CI 上报的是：

```
./scripts/assemble.sh: 102: Syntax error: "(" unexpected
```

**我用 `bash -n` 验过，过了。** 因为拿 bash 验的。

★ 同一个仓库里两种都有：`assemble.sh` 是 `#!/bin/sh`，`verify.sh` 是
`#!/bin/bash`。所以「这个项目用 bash」这种印象是错的。**验之前先看 shebang。**

改成 POSIX 的 `set --`（位置参数本来就是"可变长度的参数列表"）：

```sh
set -- -c "..." -c "..."
[ -n "$REVISION" ] && set -- "$@" -c "..."
docker import "$@" "$TAR" "$NAME:$TAG"
```

### 二、语法检查抓不到语义

改完上一处之后，替换的范围**把 `docker import` 这一行吃掉了**：

```
./scripts/assemble.sh: 126: -c: not found
```

`-c: not found` 的意思是「那一行的第一个词是 `-c`」——**命令名没了**。

**`sh -n` 还是过的。** 语法没坏，坏的是语义。

★ 而这次我是**看了一眼 `grep` 的输出、看到行对了就收工**的。要是把那一段
整个读一遍，命令名不见了是一眼的事。

**这一次之后改的验证方式**：不只语法，把那段**真的跑一遍**（假变量 + `set --`）：

```
参数个数: 6
  1. -c   2. ENV PATH=/usr/bin   3. -c
  4. LABEL x=y   5. -c   6. LABEL r=abc123
```

——参数列表本身是对的，缺的只是命令名。**这一遍就看得出来。**

### 三、一个「每次都跑、每次都成功」的步骤什么都没做

`release.yml` 里「存已建好的包」原本排在**打包之前**：

```
建包 → 存已建好的包 ←★ 这时新包还没打成 .apk，var/pkgs 里只有"进来的"
     → 打包并签名 → …
```

于是它引用的缓存里**永远只有播种和缓存恢复带来的那些**，本轮刚建出来一个都没有。

**它没有报错、没有变慢、大小看起来也合理**——只是内容永远停在上一轮。

发现的路径是**去查实际内容**：某一轮建好了 9 个包（含 linux/grub/openssh），
但它存下来的缓存是 301 MB，**和之前每一轮一模一样**。而同一轮的 artifact 是
331 MB（抢救步骤在打包之后跑）——**两个数字对不上，答案就在那儿**。

同类的还有两处，都是这一晚查出来的：

- **`actions/cache` 在后置步骤保存，而那个步骤在 job 失败时被跳过** →
  拆成 `cache/restore` + `cache/save`（`if: always()`）。
- **「产物」这条安全网只在【建包成功】时存在** → 建包一挂，`var/repo` 是空的，
  `upload-artifact` 传一个空目录，于是没有 artifact。

★ **判据**：一个自动化步骤值不值得信，不看它"是否成功"，看**它失败的样子**。
一个永远不会失败的步骤，和一个永远成功的步骤，从外面看是一样的。

### 四、同名 artifact 不会报错

`upload-artifact` 在同一轮里传两个**同名** artifact，不会报错——只会让
`gh run download -n <名字>` **随缘挑一个**。

**那种错误特别难查，因为两边看起来都是"合法"的产物。**

改法：让它们互斥（`if: always() && !failure()` 和 `if: failure()`），只有一个会跑。

---

### 这四条的共同点

**它们都不是"代码写错了"，是"我以为我知道那一步在做什么"。**

| 我以为 | 实际 |
|---|---|
| `bash -n` 过了就没问题 | 它不是在跑的那个 shell |
| `sh -n` 过了就没问题 | 语法对，但少了一个命令 |
| 缓存存下来了 | 存的是上一轮的内容 |
| 我修过那个坑了 | 修的是**表现**（"播种"），不是**本质**（"这个包不是本轮建的"），换个路径原样复发 |

★ **能用的经验是最后一条**：一个坑的触发条件如果被钉在**某条具体路径**上
（"播种"、"跳过"），那它一定会在别的路径上复发。要钉在**共同的性质**上
（"不是本轮建的"）。

### 附：一个反例，说明这些检查确实有效

这一晚也加过一个**真的有效**的检查。

`pantsu/pantsulib/vm.py` 里一个调用点少传了一个参数：

```python
if use_accel and _accel_name() is None:      # 签名要 guest_arch
```

它一路活到了**第一次真的建出磁盘镜像**那一天，一跑 QEMU 就 TypeError——
因为那个调用点**只在真启动的时候**才走到：骨架的单元测试不覆盖它，
CI 前几轮也从没跑到那里（盘根本没建出来过）。

补了 `distro/tests/test_call_arity.py`：静态扫每个文件里**本地定义的函数**的
必填参数个数，再看每一处按名字调的调用给够了没有。

不能抓全部（属性调用要类型推断，不查），但**能抓"少传一个参数"这一整类**。

验证方式是**把 bug 放回去**：

```
pantsulib/vm.py:237  _accel_name() 要 1 个参数，给了 0 个
```

——它真的会失败。**有一条会失败的路径的检查，才算检查。**
（这一句和上面那节「两次空验证」是同一句话。）
