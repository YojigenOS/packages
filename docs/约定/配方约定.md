# 配方约定

写 `recipes/<名>/spec.toml` 时要守的规矩。每条都写了为什么——只列规则的话，
遇到规则没覆盖的情况就不知道该怎么判断了。

## 源

### 三条路，按这个顺序选

| 优先级 | 用什么 | 为什么 |
|---|---|---|
| **1** | **上游自己的站点**（`ftp.gnu.org`、`cmake.org/files`、`cdn.kernel.org`、`rsync.samba.org`、SourceForge） | 最接近上游的承诺，而且不依赖任何一家代码托管 |
| **2** | **GitHub 的 commit 归档**（`/archive/<完整 commit>.tar.gz`） | 内容哈希钉死。**这是 GitHub 类源码的默认选择** |
| **3** | **GitHub 的 release 附件**（`/releases/download/…`） | 只在 commit 那条路走不通时用，**并且必须在配方里写明为什么** |
| **❌** | **tag 归档**（`/archive/refs/tags/v1.2.3.tar.gz`） | **tag 可以移动**。上游一推 tag，你下次构建就换了源码 |

### 为什么 commit 优于 release 附件

不是因为"附件可能被删"——**是因为改了之后还能不能重建**：

```
release 附件被替换  →  sha256 不匹配 → 构建挂 ✗
                      而且【旧字节永远找不回来了】✗✗
commit 归档被重新生成 →  sha256 不匹配 → 构建挂 ✗
                      但内容【随时能从 git 重新拿到】✓✓
```

git 是**内容寻址**的：从 GitHub、Codeberg、还是你自己搭的 Gitea clone 同一个
commit，内容完全一样——**一个恶意镜像改不了内容**，git 在 checkout 时会校验。

所以"用哪个托管"是**可用性**问题，不是**信任**问题。

### git 形式的写法

**配方写的是「哪个仓库的哪个 commit」，不是托管商的链接。**

```toml
[[source]]
git     = "https://github.com/ccache/ccache"
commit  = "c67954b7729c2a7a350c80e7634d704b669307dc"
mirrors = ["https://codeberg.org/…"]      # 可选，同一份内容的别处
```

**为什么不该写链接**：

1. **链接格式是托管商定的，而且各不相同**——GitHub 是 `codeload`，
   Gitea/Forgejo 是 `/archive/<sha>.tar.gz`，GitLab 又是另一种。写配方的人
   不该记这些，那是驱动的事。
2. **托管商换了不用改配方**——只改驱动里的模板。
3. **能用上游自己的 git 服务器**——`xz` 的主源就是 `git.tukaani.org`，
   GitHub 上那份只是它的镜像。那比任何托管都更接近上游。

**也【不需要 sha256】**：git 自己按 commit 校验内容。commit hash 就是那棵树
的内容哈希——**比 sha256 更强**。sha256 钉的是一份字节，而不同托管生成的
归档字节可以不一样，于是单个 sha256 根本盖不住多个镜像 ✗；git 没有这个
问题 ✓。

**镜像因此是免费的**：主仓库不通就换下一个，内容对不对由 git 保证。实测
第一次跑就赶上了——`xz` 的 `git.tukaani.org` 不通，驱动自动换了 GitHub，
取到的还是同一个 commit。

### 那什么时候还用 url + sha256

**发行包**（非 git 的源）仍然是 url + sha256：上游自己发布的 tarball、
SourceForge、`ftp.gnu.org` 那些。它们没有 commit 可以钉，sha256 就是身份。

**已知必须用发行包的一个**：`libffi`。理由见下。

### commit 路线的硬性要求：git 树必须能 `autoreconf`

发行包里有上游跑好的 `configure`，**git 树里没有**——那些生成物不进版本控制。

所以从 commit 构建 autotools 项目时，配方要写：

```toml
[build]
type       = "autotools"
autoreconf = true          # 现场跑 autoreconf -fi
```

**而且必须把 autoconf / automake / libtool 写进 `build` 依赖**——不写就会
悄悄用构建环境镜像里的那一份，那就是隐式依赖（`skirt/tests` 里有条测试守
着这件事）。

**有些项目做不到** ✗。判据是：**在它的 git 树里跑 `autoreconf -fi` 成不成**。
已知失败的一个是 `libffi`：

```
configure.ac:245: error: possibly undefined macro: LT_SYS_SYMBOL_USCORE
```

那个宏只定义在 libtool 的 `ltdl.m4` 里，而 libffi 的 `configure.ac` 没引入
它。**它的 git 树用现代 libtool 根本生成不出 configure**——上游是拿更老的
工具链生成好、把 `configure` 放进发行包的。

**这种情况退回发行包，并在配方里写明原因。** 不是"将就"——是"这条路对这个
项目不存在"，把理由写下来比装作没有例外有用。

### 备用源写在哪

**写在配方里，不由驱动补。**

驱动曾经自动给 `ftp.gnu.org` 的包补镜像，理由是"21 个包改 21 处太啰嗦"。
那个理由不足以抵消它的坏处：**配方应该是自包含的**——读一个配方就该知道它的
源码全部从哪来。驱动偷偷加源会让行为不可见，排查时你会问"它为什么从 USTC
下载？我没写这个"。

Arch 也是这么分的：

```
PKGBUILD:   source=("https://ftp.gnu.org/gnu/m4/m4-$pkgver.tar.xz")   ← 配方写上游
mirrorlist: Server = https://mirrors.ustc.edu.cn/...                   ← 系统配镜像
```

**配方那份是「身份」，系统那份是「政策」。** 我们两边都要，但不要混。

```toml
[[source]]
url    = "https://ftp.gnu.org/gnu/m4/m4-$VERSION.tar.xz"
# 备用源：同一份字节的镜像（sha256 会校验，所以换源不降低信任）。
urls = [
  "https://mirrors.ustc.edu.cn/gnu/m4/m4-$VERSION.tar.xz",
  "https://mirror.nju.edu.cn/gnu/m4/m4-$VERSION.tar.xz",
  "https://mirrors.tuna.tsinghua.edu.cn/gnu/m4/m4-$VERSION.tar.xz",
  "https://mirrors.aliyun.com/gnu/m4/m4-$VERSION.tar.xz",
]
sha256 = "…"
```

**上游排第一位**，所以镜像只在它不通时才会用到——这一条同时解决了"中美环境
不同"的问题：`ftp.gnu.org` 两地都不算慢（实测本机 2.9 秒），CI 上永远轮不到
镜像。

### 镜像怎么选（2026-10-10 实测）

拿 `gettext-1.0.tar.xz`（10 MB）在本机测的：

| 镜像 | 耗时 | 结论 |
|---|---|---|
| `mirror.nju.edu.cn` | 0.8s | ✅ 快 |
| `mirrors.tuna.tsinghua.edu.cn` | 0.8s | ✅ 快，**但有限速**，所以不排第一 |
| `mirrors.ustc.edu.cn` | 1.0s | ✅ 快 |
| `ftp.gnu.org`（上游） | 2.9s | ✅ 上游，排第一 |
| `mirrors.kernel.org` | 3.1s | ✅ 国外快 |
| `ftpmirror.gnu.org`（GNU 官方重定向） | 4.3s | ❌ **不用**——它把我们指到了巴西 |
| `mirrors.aliyun.com` | **56.1s** | ⚠️ 有，但慢 70 倍，所以放最后 |

**七个镜像的 sha256 完全相同**——镜像就是同一份字节，所以校验不用跟着改。
这再次印证了上面那句「sha256 才是身份，URL 只是提示」。

### 一个实际做法

拿不准的时候，先看看上游站点有没有：

```bash
# 这个方法有效：xz 在 tukaani.org 上的链接其实就是跳 GitHub，
# 而 expat 在 SourceForge 上有独立发布点（实测字节与 GitHub 附件一致）。
```

**字节一致意味着那个附件确实是维护者上传的原件**，也意味着它**可镜像**。

### 源码缓存的陷阱（还没修）

**换了配方里的 URL，驱动不会重新下载。** 实测踩过：libffi 从 commit 归档改
回发行包之后，构建仍然用着 `build/src/` 里那份解开的旧树，报
`./configure: No such file or directory`——而日志里连一行 `[下载]` 都没有。

改源之后要手动清：

```bash
rm -f cache/<包>-<版本>.tar.*
rm -rf build/src/*<包>*
```

这个和 `docs/待办.md` 1.5.B 的 `build_key` 是同一个问题：**产物和缓存的有效性
应该由配方内容算出来，而不是靠人记得清。** 修完就不用再写这一段了。
### 备用源

主源在国内时通时不通（`ftp.gnu.org` 实测如此，构建 `patch` 时直接 SSL 断流）。
`urls` 列备用源，按顺序试：

```toml
[[source]]
url  = "https://ftp.gnu.org/gnu/foo/foo-$VERSION.tar.xz"     # 主源：CI 在海外，更快
urls = ["https://mirrors.tuna.tsinghua.edu.cn/gnu/foo/foo-$VERSION.tar.xz"]
sha256 = "…"
```

**sha256 才是身份，换源不降低信任。** 校验失败**不会**换源重试——内容不对
不是网络问题，是配方或镜像错了。悄悄换一个源继续，会把「镜像被投毒」变成
「构建成功」。

### sha256 必须填满 64 位十六进制

不填、填错长度、填一个占位符，都会在下载阶段报错。**不接受未校验的源码。**

## 包分类

**分类就是目录名，没有并存的字段。**

```
recipes/lib/      纯依赖库
recipes/tool/     命令行工具
recipes/devel/    构建时用的（编译器、构建系统、开发工具）
recipes/lang/     语言运行时
recipes/data/     数据与文件骨架
recipes/example/  示例与探针
```

### 判据是「别人为什么依赖它」

```
去掉它，别的包还能【链接/运行】吗？      不能 → lib
去掉它，别的包还能【构建】吗？          不能 → devel
别人依赖它是因为要【在命令行跑它】吗？        → tool
它是个【语言运行时】吗？                      → lang
它没有代码，主要是文件吗？                    → data
```

`glibc` 装 `ldd`、`locale` 这些命令，但没人依赖它是为了跑那些命令——
依赖它是因为要链接。所以是 `lib`，不是 `tool`。

### 分类【必须】是声明的

**42 个包里有 17 个既装库又装命令**（xz、util-linux、perl、python3、glibc…）。
产物根本分不出来，所以 `kind` 是作者写的事实，就像依赖一样。

**但产物能检查它。** `test_kind.py` 拿 `var/output/` 里的真实产物验证声明，
条件是**必要条件**不是充分条件：

```
lang  → 必须装了可执行文件（解释器入口）
tool  → 必须有 bin/ 里的可执行文件
lib   → 必须有 .so 或 .a
data  → 【不该】有 .so
devel → 有可执行文件【或者】头文件
```

**为什么 `devel` 允许头文件**：`linux-headers` 一个可执行文件都没有，
但没它你构建不了任何东西。

**为什么用必要条件**：`lang` 必须装了解释器，但不排斥它也有 `.so`。反过来
不成立——有 `.so` 不等于它是 `lib`。

### 为什么 `section` 字段要删

它现在有 `base` `libs` `devel` `core` `utils`，但那些值**混了两个轴**：
`libs` 是「它是什么」，`base`/`core` 是「它在哪个镜像里」。而后者
**`variants/*.toml` 已经说了**——`variants/base.toml` 列的就是进 base 的那 12 个。

**一处信息只该有一处。** 留着它就会有人用它，然后两处不一致。

## 依赖：分成两类，而按命令只能查出第一类

写 `runtime` / `build` 列表时，缺的东西有两种，**性质完全不同**：

| | 例子 | 怎么发现 |
|---|---|---|
| **构建时被调用的命令** | `make`、`gcc`、`setpriv`、`patch`、`as`/`ld`（binutils） | 跑一遍就知道 `command not found` |
| **configure 会「检查」的程序** | `bison`、`python3`、`awk`、`msgfmt` | **只能撞**——它们平时不出现在命令行里 |

第二类是最容易漏的。`glibc` 的 `configure` 把话说得很直白：

```
configure: error:
*** These critical programs are missing or too old: bison python
```

**教训**：用 `command -v` 去审计"构建环境缺什么"会得到一个自信而错误的答案。
我一开始就是这么得出"自举只缺 setpriv 和 patch 两个"的结论的。真实的缺口，
得让构建设一遍才知道——这也是 `docs/决策记录/0011` 把「自举」定义成一个
**可实测判据**的价值所在。

### 怎么核对

Debian 那个构建环境镜像是个现成的参照，但要**整个镜像**对照，不能只看
Dockerfile：

```bash
docker run --rm debian:stable-slim dpkg-query -W -f='${Package}\n' | sort > /tmp/base.txt
docker run --rm yojigenos/buildenv:aarch64 dpkg-query -W -f='${Package}\n' | sort > /tmp/env.txt
comm -13 /tmp/base.txt /tmp/env.txt      # 构建环境比基础镜像多装了什么
```

**为什么不能只看 Dockerfile**：`python3` 和 `perl` 都不在它的 apt 清单里，
而是被 `meson` 和 `autoconf` 当依赖拖进来的。清单会骗人，装出来的东西不会。

## 时间戳

`[package] date` 必须写在配方里，带时区，而且是 TOML 原生日期时间（不能加引号）。

```toml
date = 2026-10-10T14:00:00Z      # ✓
date = "2026-10-10T14:00:00Z"    # ✗ 加了引号就是字符串
date = 2026-10-10T22:00:00       # ✗ 没有时区
```

**加新包时，date 要晚于它的所有依赖**，否则 `SOURCE_DATE_EPOCH` 会取自依赖
（那是对的，但会让人困惑）。理由见 `docs/决策记录/0005`。

## configure

### 不要用 `--disable-nls`

上游做了中文，我们只要**别把它关掉**。`docs/决策记录/0012` 定了这条边界：
有中文的用中文，没有的不强求。

### 关掉树里没有的可选依赖

不是嫌它们没用，是它们还没进来。写清楚是哪个：

```toml
"--without-python",     # 没有 python3
"--without-ncurses",    # 没有 ncurses；fdisk 的交互界面会退化
```

**configure 的汇总里会列出「因为缺什么而没编什么」**——值得看一眼，那是最
省事的缺口清单。`util-linux` 的 `setpriv` 就是这么被发现的（它需要
`libcap-ng`，而且是全有或全无）。

### 目录要显式指到 /usr

按 `docs/决策记录/0001`，我们做 usr-merge：`/bin`、`/sbin`、`/lib`、`/usr/lib64`
都是指向 `/usr` 里对应目录的符号链接。

**驱动的默认值已经钉住了库目录**，三个构建系统都是：

```
autotools  --prefix=/usr --libdir=/usr/lib
meson      --prefix=/usr --libdir=lib --buildtype=release
cmake      -DCMAKE_INSTALL_PREFIX=/usr -DCMAKE_INSTALL_LIBDIR=lib
```

**为什么必须钉**：autoconf 在 64 位系统上有个启发式，会把 `libdir` 定成
`${prefix}/lib64`。包于是装出一个**真目录** `/usr/lib64`，和符号链接撞车，
拼 rootfs 时 `cp` 直接失败：

```
cp: cannot overwrite non-directory '/rootfs/./usr/lib64'
    with directory '.../libffi-3.8.0-1/payload/./usr/lib64'
```

失败是响亮的，不会静默出错——但得知道为什么。

**有一个包连 `--libdir` 都不听**：`libffi`。它的 `configure.ac` 去问 gcc：

```m4
if test x"$enable_multi_os_directory" != x"no"; then
  multi_os_directory=`$CC $CFLAGS -print-multi-os-directory`
  case $multi_os_directory in
    ../*) toolexeclibdir=$toolexeclibdir/$multi_os_directory ;;
```

它问的是「多架构的库该放哪个子目录」，gcc 回答 `../lib64`，于是它在 `libdir`
后面又接了一层。上游为这种情况留了开关（`multi-os-directory` 是 GCC 的概念，
libffi 只是跟随），加 `--disable-multi-os-directory` 就老实了。

**这类包的特点是「不听 --libdir」**。遇到装错目录的包，先看它的 configure 里
有没有在算自己的目录，而不是怀疑驱动。

有些包也会故意装到 `/bin`（`util-linux` 为了让 `mount` 在 `/usr` 挂载前可用），
那同样要显式覆盖：

```toml
"--bindir=/usr/bin",
"--sbindir=/usr/sbin",
"--libdir=/usr/lib",
```

## 构建类型

```toml
type = "autotools"   # ./configure && make && make install
type = "meson"       # meson setup _build && meson install
type = "cmake"       # cmake -B _build && cmake --install
type = "custom"      # 由 steps.sh 提供 build() / package()
```

`custom` 用于需要自举的构建系统本身——`cmake` 就是用它自己的 `./bootstrap`
+ `make` 编出来的（不需要预装 cmake）。`steps.sh` 通过重定义 `build()` /
`package()` 覆盖默认行为。

## 目标构建要把注入的 CFLAGS 挡在门外

**skirt 会给每个构建注入一份加固用的 CFLAGS**（`skirtlib/build.py` 里那一行）：

```sh
export CFLAGS="-g0 -O2 -fstack-protector-strong -U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=3 $ARCH_HARDEN"
```

对普通包这是对的。对**目标构建**——freestanding 的代码：bootloader、固件、
内核模块——是错的，而且错得很难看出来，因为报错长得像"缺依赖"。

### 怎么个错法（GRUB 上的两次实测）

GRUB 的目标代码自己会说"不要栈保护"，并在命令行里选 `-fno-stack-protector`。
而注入的那份 CFLAGS **排在它后面**：

```
... -fno-stack-protector -Wtrampolines ... -g0 -O2 -fstack-protector-strong ...
    ↑ GRUB 选的                              ↑ 注入的，在后面，赢了
```

后写的赢，于是 freestanding 的 GRUB 内核里出现了对 `__stack_chk_fail` 的调用，
而那个符号在一个 `-nostdlib` 的链接里根本不存在：

```
ld: kernel_exec-parser.o: undefined reference to `__stack_chk_fail'
```

同一个病因还有更早的一次：`$ARCH_HARDEN` 在 x86_64 上是 `-fcf-protection=full`
（CET），而 32 位目标直接拒绝它：

```
cc1: error: '-fcf-protection' is not compatible with this target
```

### 怎么办

**只摘一条是治标。** 第一版 grub 配方只 `sed` 掉了 `-fcf-protection`，第二次
就换成 `-fstack-protector-strong` 挡路。正确做法是整条挡在门外：

```sh
build() {
    unset CFLAGS    # 注入的是宿主口味；目标构建用上游自己那套
    ...
}
```

`LDFLAGS` 可以留着——它不参与目标链接的符号解析（`-z relro -z now` 在两种
链接里都成立），而要发出去的工具还需要它。

（更好的做法是驱动给个开关，比如 `[build] env_cflags = false`，让配方声明而不
是自己 unset。那是 `build.py` 的事。）

### 别用"要不要 multilib"解释这类失败

上面那个 32 位目标的失败，很容易被读成"缺 32 位 glibc"。**不是**：GRUB 是
freestanding 的，从来不链 libc，32 位的模块编译链接全程正常。真正的病因是注入
的标志。判据是**报错的具体内容**，不是"它提到了 32 位"。

## 补丁

放在配方目录里，`[build] patches = ["名字.patch"]` 引用。

**必须是相对源码树根的路径**，而且用 `-p1 --fuzz=0` 应用——不精确匹配就失败。
理由：`patch` 默认容忍 2 行模糊匹配，一个已经不适用的补丁会被「差不多」地贴
上去，产出无声的错误代码，等到运行时才以看不懂的方式炸掉。

## 包名

**上游软件用上游的名字**——`glibc`、`coreutils`、`gawk` 叫什么就叫什么。名字是它的
身份，不该跟着我们的口味变。子包用「母包 + 限定词」（`glibc-dev`、`dash-binsh`），
见下一节。

**我们自己写的包带 `yojigen-os-` 前缀**：`yojigen-os-init` 是第一个，后面还会有
`yojigen-os-firstboot`、`yojigen-os-release`。

### 这个前缀里为什么有连字符，而 Docker 那边没有

两处不一样，因为约束不一样：

```
Docker 命名空间   yojigenos/base        连字符【不合法】（只允许字母数字），只能这样
包名前缀          yojigen-os-init       连字符合法，而且产品名本来就是两个词
```

**别把这两处对齐**——它们对齐的是各自的生态，不是彼此。

### 会不会和「母包 + 限定词」的语法混

会有一点，但有一条学得会的规则能消掉：

**`yojigen-os-` 开头的一定是我们自己写的包**，而**不存在一个叫 `yojigen` 的包**，
所以 `yojigen-os-init` 只可能是「我们的前缀 + 名字」，不会被读成
「`os` 是 `yojigen` 的哪个子包」。

反过来，上游的包（`glibc-dev`、`dash-binsh`）里 `-` 右边【确实】是限定词。
两套语法靠「前缀存不存在」区分。

理由、先例和"这条规则管到哪"在 `distro/docs/决策记录/0009-命名与品牌.md`。

## 子包

一个配方可以按文件模式产出多个包（`docs/决策记录/0014`）。

**只搬真正占体积的东西。** `/usr/lib` 下那些不带版本号的 `.so` 是链接期的
符号链接，但里面可能混着真的 ELF——模式匹配分不出「符号链接」和「真 ELF」。
宁可少省几 KB，也不要写一条会误伤运行时的规则。

## 检查

```bash
python3 -m unittest discover -s skirt/tests    # 每个真实配方都会被结构性检查
```

测试会验证：包名和目录一致、`release` 是整数、`date` 能算出时间戳、source
的 URL 没有未展开的占位符、sha256 是 64 位十六进制、子包名全局唯一且不和
配方重名。

## 让每一步说话：`|| true` 是这一类 bug 的温床

`|| true` 让「没跑成」和「跑成了但没有东西」长得一模一样。

**实测的四个例子**（都在同一条线上，而每一次的修法都一样）：

```
① 拆阶段时补丁打了两遍
     报的是「Reversed (or previously applied) patch detected」——
     看起来像"补丁过期"，我差点去改那个完全正确的补丁。
     推翻它的线索只有一句：日志里那个补丁【只打了一遍】。

② cleanup 里写的是裸的 getcap，而那个容器里没有它
     `getcap -r … > /tmp/.caps || true` —— 什么都没做，一声不响。
     下一句 setcap 当然也没做。而我把这一格标成了"修好了"。

③ 同一个 getcap，改成了绝对路径但没找对

④ `rsync -aX … || true` —— 它在 /in 上其实报了
     `fsetxattr … security.capability failed: Operation not supported`，
     而那个 `|| true` 把它吞了。我于是接着猜了两轮。
```

**所以**：

- 一句 `… || true` 后面，要跟一句**说出来的**话：跑了没有、成了没有、结果是什么。
  ```bash
  if command -v rsync >/dev/null 2>&1; then
    rsync -aX "$SRC/." "$DST/" || echo "[产物] ✗ rsync 失败" >&2
    echo "[产物] 用 rsync -aX 拷出" >&2
  else
    cp -a "$SRC/." "$DST/" || echo "[产物] ✗ cp 失败" >&2
    echo "[产物] ⚠ 没有 rsync，退回 cp -a" >&2
  fi
  ```

- **诊断要覆盖整个属性，不是一半。** 「只打 setuid 不打能力位」这个诊断，
  让 `ping` 少了四轮 —— 而 ping 两样都没有，我只看了一半。

- **一个检查匹配不到真实结构时，绿的和红的都不算数。** 例如
  「缺库的二进制：0 个」曾经是假绿 —— 那个 root 里没有 `grep`，
  检查根本没跑成。

### 而"说话"本身也要守规矩

上面说"让每一步说话"，而**诊断那一行也可能弄坏东西**。实测：

```bash
set -eo pipefail
find "$WORK/dest" -type f | head -3 | while read f; do ls -ld "$f"; done
```

**`head` 读三行就退出，`find` 拿到 SIGPIPE 而死，整条管道返回 141（=128+13），
而 `set -e` 把整个脚本杀掉。**

本地验证：

    bash -c "set -eo pipefail; find /usr -type f 2>/dev/null | head -3; echo 后面这行"
        → 三行打出来了，而"后面这行"【没打】；退出码 141

而它是在 perl 的构建上报出来的 —— **dest 越大越容易撞**
（perl 的 dest 有一万多个文件）。之前那几个包小，`find` 在 `head` 退出前
就写完了，所以这个雷一直在而没踩到。

**所以 `set -e`（尤其带 `pipefail`）下不许有会提前退出的读端。**
要取前 N 行，就先落到文件再读：

```bash
find "$WORK/dest" -type f 2>/dev/null > /tmp/.files || true
sed -n "1,3p" /tmp/.files | while IFS= read -r f; do ls -ld "$f" >&2; done || true
```

★ 而这一条最值得记的是：一个**只为了让人看见**的句子，把一个包的构建弄挂了，
而没有任何人会把 `141` 和 `head` 联起来。

## 两个同名但不同的路径

这一条是 `ping` 那一格的最后一层，而它本来能早四轮发现。

```
build.py:  -v "${BUILD_DIR}:/in"      BUILD_DIR = var/work
pack.sh:   -v "$PWD/$d:/in:ro"        d = var/output/<arch>/<包>-<版本>/
```

**两个组件各自都"说得对"，而它们说的不是同一件事。** 而两边在日志里
都叫 `/in` —— 于是"宿主上 0 条"看起来像"拷贝丢了"，其实是"读的是另一个目录"。

**所以**：容器里的路径名如果来自宿主的挂载，**它的含义就跟着挂载走**。
改这类东西之前，先看一眼那几个 `-v` 挂的是什么 —— **一行 grep 的事**。

## 改了配方，就要升 `release`

**这不是形式，是判断依据。**

apk 判断"要不要装/升"靠的是 `<name>-<version>-<release>`。**内容变了而版本没变，
它就认为"已经是这个了"** —— 于是：

| 场景 | 后果 |
|---|---|
| 全新安装（建镜像、装机） | ✓ 没事——索引指向的是新文件 |
| **已经装了的系统 `apk upgrade`** | ✗ **拿不到**，静默地什么都不做 |

实测撞过一次：`yojigen-os-init` 里加了 `cttyhack`、也重建发布了，
但版本还是 `1.0-r1` —— 新装的机器有，老机器升级升不出来。

**改什么都要升**，包括：

- `files/` 下的任何文件（脚本、配置、C 源码）
- `steps.sh` / `spec.toml` 里的行为（依赖、configure 开关、子包划分）
- 已经发布过的包的 `provider-priority` 这类元数据

**只改注释**不用升（产物一个字节都不变）。

★ 这条难在**没有自动检查**：判"内容变了"要读 git 历史，而配方仓库里
  一次提交动好几个包是常事。所以它靠的是写的人记得——写在这里，是为了
  下一个人（或者三个月后的自己）知道**为什么改了没效果**。
