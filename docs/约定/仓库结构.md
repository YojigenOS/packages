# 仓库结构

这份文档说清楚**什么东西放在哪，以及为什么**。改结构之前先读它。

```
packages/                     ← 这个仓库（git@github.com:YojigenOS/packages.git）
├── bootstrap/                构建环境的【两半】
│   ├── Dockerfile            怎么造出它（Debian + 一批构建工具）
│   └── provides.txt          造出来之后，哪些算【基线】
├── skirt/                    构建驱动
│   ├── skirt                 入口
│   ├── skirtlib/             实现
│   └── tests/                它的测试
├── recipes/                  配方（48 个包，按 kind 分层）
│   ├── lib/ tool/ devel/ lang/ data/ example/ kernel/
├── variants/                 风味（base · base-devel）
├── scripts/                  人用的脚本
│   ├── run-vm.sh             拼 rootfs → initramfs → QEMU
│   ├── smoke.sh              31 秒的端到端体检
│   └── vm.command            双击在终端窗口里启动
├── docs/                     文档
└── var/                      产物（不进版本控制）
    ├── output/               包产物
    ├── cache/                源码 tarball
    ├── logs/                 每个包的完整构建日志
    └── work/                 构建工作区
```

## 四条边界

**`skirt/` 是程序，`scripts/` 是给人敲的。**

驱动有 2300 行实现和 84 个测试，是仓库里唯一一个"软件"。`scripts/` 里那些
是开发时手动跑的东西。两者不该混在一起——原来它们都在 `tools/` 下。

**`recipes/` 和 `variants/` 是数据。**

配方说"这个包从哪来、怎么建"；风味说"哪些包组成一个交付物"。两者都是给
`skirt/` 读的输入。

**`bootstrap/` 是借来的起点，不是我们的东西。**

`Dockerfile` 里是 `FROM debian:stable-slim` + 一批 apt 包。它**不是 Yojigen OS
的一部分**——到工具链自举阶段，它会被我们自己的镜像取代。`provides.txt` 是
同一件事的另一半：它说"这个借来的环境里，哪些东西算数"。

（这两个文件原来分别在 `tools/buildenv/` 和 `host/`。`host` 那个名字是错的：
它说的不是宿主机，是"构建环境提供什么"。）

**`var/` 全是可再生的。**

四个目录都可以删掉重建。它们放在一个父目录下，是为了 `ls` 一眼就分得清
哪些是源码、哪些是产物。

## 路径只该有一处

`var/` 下的四个路径定义在 `skirt/skirtlib/common.py` 里，**只有那一处**。

shell 脚本不许自己拼这些路径，要问驱动：

```sh
eval "$(./skirt/skirt paths --shell)"
# 然后就有 $OUTPUT_DIR / $CACHE_DIR / $BUILD_DIR / $LOG_DIR
```

这条规则是被一次事故换来的：2026-10-11 把产物集中到 `var/` 时，驱动改了，
`scripts/` 里各自写死的那份没跟着改，冒烟测试当场报"缺产物"。

**同一件事在 `common.py` 里也发生过一次**：那段常量被复制了三遍，后两份
静默覆盖第一份，所以改第一份不会生效。有测试守着这两件事了
（`test_common_constants.py`、`test_shell_scripts.py`）。

## 决策记录里的路径是【当时的】

`docs/决策记录/` 下的 15 篇**不可变**——它们记的是当时决定时的事实，正文
永远不改。

所以里面的路径会过时。比如 0003 里写 `tools/skirtlib/common.py`，那个文件
现在是 `skirt/skirtlib/common.py`。

**处理办法是【追加】一行说明，不是改正文。** 与其回改 15 篇历史记录，不如
在这里说一次：**读决策记录时，把路径当成"当时它叫什么"。**

已经加过追加说明的：

```
0003-镜像命名与标签.md        tools/skirtlib/  → skirt/skirtlib/
                              tools/buildenv/  → bootstrap/
0005-可复现构建与时间戳来源.md packages/<包名>/ → recipes/<kind>/<包名>/
0011-构建环境的边界.md         host/provides.txt → bootstrap/provides.txt
0015-许可.md                   tools/skirt/     → skirt/
                               packages/        → recipes/
```

## 名字的来由

```
skirt       短裙里装着四次元空间；这里装着所有的包
bootstrap   从 Debian 引导出我们自己的系统——整件事的名字
recipes     文档里一直叫「配方」，英文正好是 recipe
var         和操作系统的 /var 同一个语义：可变数据
```

**仓库名 `packages` 是唯一一处名不副实的地方** ✗。里面的东西更像
`recipes + driver + docs`。但改 GitHub 上的仓库名要动所有 clone URL 和
`os-release` 里的 `BUG_REPORT_URL`，代价大于收益，所以留着。
