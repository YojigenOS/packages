# 客观性

> **能算出来的，不要靠人记得。**

这是这个项目最上面的一条规矩。其余那些约定（配方怎么改、目录怎么摆、构建在哪跑）
是它的具体形态，而这一份说的是**它们为什么是那样**。

## 为什么

因为「靠人记得」的失败方式是**静默**的。

它不会报错。它会在你改对了一个东西之后，让另一个东西照旧——而日志里一切正常，
产物看起来也正常。你要花很久才会开始怀疑"是不是根本没生效"。

这一路撞到的四次，形状都一样：

| 事故 | 靠人记得的是什么 | 结果 |
|---|---|---|
| 改了配方忘了升 `release` | 内容变了要改身份 | CI 说「跳过（已经有了）」，发布出去的是旧产物 |
| 源码缓存 | 改了源要清缓存 | 用着旧的源码树，报 `./configure: No such file or directory`——**而那个错和你改的地方毫无关系** |
| `sudo` 没有 setuid | 打包时要保住 setuid 位 | `sudo` 不叫 `sudo`，而原因在打包脚本的一行 `chown` 上 |
| `ping` 没有能力位 | 同上，加上四个层的叠加 | `ping` 能用，但只有 root 能用 |

**共同点是：每一件都不是"跑不通"，是"跑通了但结果是错的"。** 而每一件的成因，
都离症状很远。

## 具体是什么样

四类。每一类都有它的形态，而不是一句口号。

### 一、身份从内容算，不要从名字算

一个东西的身份，应该是它**内容的函数**，而不是一个人写上去的标签。

- `release` 号是标签——**而它现在承担着"内容变没变"的职责**，那是错配（见下面
  「还没客观化的」）
- `sha256` 是内容——所以源码的校验是可靠的，而"文件名 + sha256 碰巧对得上"就不是
- 版本、架构、依赖的 key——这些合起来算一个哈希，就是一份**算出来的身份**

**判据**：如果"这两个是不是同一个东西"要靠人回答，那它就不是客观的。

### 二、检查要能跑，不能只是文档里的一句话

写在文档里的规矩，是**给人读的**，不是**给机器查的**。

同一件事，两种写法：

```
✗  "shell 变量名和中文之间要加花括号"          ← 人读了会记得，三个月后不会
✓  test_shell_scripts.py 里那条扫描             ← 每次改动都查一遍
```

而这个项目里**已经有**一批这样的检查（见下面「已经客观化的」）。它们是模板：
**每一条能写成测试的规矩，都该写成测试。**

### 三、说话必须是真的

一句"成功了"如果不在任何判断链上，它就是在说谎。

实测撞过一次，而且很讽刺——那一整节在讲"让每一步说话"，而它自己那句话不是真的：

```sh
install -m 600 … "$TEMPLATE" "$TARGET" 2>/dev/null \
    || { cp … && chmod …; }
echo "  ✓ 已铺上默认公钥"          # ← 不在任何 && 链里，上面全失败也打这一句
```

**一个说谎的成功信息比没有信息更糟**——它会让人不再去看那件事。

同一类的还有 `|| true`：它让**"根本没跑"**和**"跑了但没找到"**看起来完全一样。
实测这一路撞了四次。

### 四、被静默忽略的东西等于没写

写了一个字段而驱动不认，那它和没写没有区别——**而写的人以为它生效了**。

实测：`meson` 的 `prefix` 能被配方里的 `configure` 顶掉，于是 `ping` 和 `dbus-daemon`
装进了 `/usr/local`。配方看起来完全正常。

**判据**：新增一个能写进配方的字段时，**驱动认不认它，是必须被证明的**——
要么有一条路径让它生效，要么有一个 `die()` 明确拒绝它。

## 而这条规范自己也要能被查

「要客观」这句话不能被机械检查。所以它落成一条**三选一**：

**每一个"靠人记得"的判断，必须属于下面三类之一：**

| 类别 | 要求 |
|---|---|
| **改成算出来的** | 最好。判断依据从内容来，人不需要记得任何事 |
| **配一个能跑的检查** | 可以。写进 `skirt/tests/` 或 `scripts/`，每次改动都跑 |
| **登记为已知欠账** | 最差，但**必须写下来**。写进这张表，并说清"忘了会怎样" |

**而第四种——"没有检查，也没登记"——就是这一节要防的东西。**

所以下面这张表是**这份文档的核心**：它不只是记录，它是清单。**新增一条"靠人记得"
的东西而没往这里加一行，就是违反这条规范。**

### 已经客观化的（有检查守着）

| 靠人记得的事 | 检查在哪 |
|---|---|
| shell 变量名和中文之间要加花括号 | `test_shell_scripts.py` |
| 每个配方的 `steps.sh` 不能有语法错 | `test_run_script.py` |
| 版本号里不能有 `<字母><数字>` | `test_versions.py` |
| `var/` 下的路径只在 `common.py` 一处 | `test_common_constants.py` |
| 源码的 `sha256` | 下载时逐个源校验 |
| 源码不在宿主上解压 | `scripts/smoke.sh` 第①项（APFS 大小写不敏感那件事） |
| 依赖的顺序 | `skirt order` 算出来，不手写 |
| 包里的文件属主是 `root:root` | `pack.sh` 强制 `chown 0:0`，构建时诊断会打出来 |
| setuid 位和能力位不丢 | 文本清单（`.yojigen-caps`）+ `pack.sh` 逐个恢复 |
| **"这个包要不要重建"** | `skirt stale` 比 `build_key`（六样成分的哈希），CI 的跳过判断用它 |
| **"改了配方有没有生效"** | 同上 —— 配方内容一进那个哈希，改了就变，不需要人记得升 `release` |
| **"改了依赖，用它的包会不会跟着重建"** | 同上 —— 依赖那一项是递归的 |

### 还没客观化的（登记在案）

| 靠人记得的事 | 现在的样子 | 忘了会怎样 |
|---|---|---|
| **`skirt stale` 只看目标本身** | 它比"目标现在算的 key"和"目标盘上那份"。而目标 key 里的依赖那一项，取的是**依赖盘上的 key** —— 所以依赖的配方变了、而依赖没被重建时，目标照样报"不用" | 在 CI 里**不会发作**（循环按依赖顺序走，依赖在前、各自都查过一遍）。只在手工 `skirt stale <某个包>` 时会漏 |
| ~~只改注释会触发一次重建~~ | **已收窄** —— `spec.toml` 改成按语义哈希（`tomllib` 解析），它的注释和排版不参与。而 `steps.sh` 仍然按字节 | `steps.sh` 的注释仍会触发一次重建，产物字节一样。**那是有意的**：剥 shell 注释要懂 heredoc、引号里的 `#`、续行，剥错的后果是漏掉一次真实改动 —— 而少算一样比多算一样危险得多 |
| **改配方时要记得升 `release`** | 见 `配方约定.md`。它现在只管 apk 那边"要不要装/升" | 新装的机器有，老机器 `apk upgrade` 升不出来 —— **而不再是"发布旧产物"** |
| **`.apk` 的可复现只挂在 `SOURCE_DATE_EPOCH` 一个开关上** | `apk mkpkg` 把所有条目的 mtime 统一重设成它 —— **那是整条链上唯一的归一化** | 一旦不生效（没人传那个变量、或者将来某个包不走 `pack.sh` 自己打包），收集阶段留下的墙钟会**直接进包**，而别处不会告诉你。**现在有 `smoke.sh` 第6项守着** |

**2026-10-15：头两条做掉了。** 它们的解法是同一条 —— **让身份从内容算出来**：

```
build_key = 哈希(配方内容 · SOURCE_DATE_EPOCH · 构建环境 · 工具集 · 架构 · 依赖的 key)
```

它写进 `meta.json`，也在产物目录里留一份 `.buildkey`（旁路文件 —— 因为
`apk mkpkg` 不收自定义字段，key 进不了 `.apk`）。而 CI 的跳过判断从
「var/pkgs 里有没有同名 `.apk`」换成了「build_key 一不一样」。

于是「改了配方忘了升 `release`」从结构上没了 —— **两边都是算出来的**，
不需要 git 历史，也不需要人记得任何事。而依赖那一项是递归的，所以
「改了依赖但 `packages=` 里漏了它」也一起治了。

细节见 `skirt/skirtlib/buildkey.py` 顶上那段：六样成分各自为什么在里面，
以及其中两样是拿什么事故换来的。

**而"两样"这个数是 2026-10-15 当天从两样涨到三样的** —— 补上的是"工具集"里
`scripts/` 那一半：

    原来只哈希 skirt/**/*.py，没算 scripts/
    而 scripts/pack.sh 决定"包里放什么"（跑 apk mkpkg、恢复能力位、补 ELF 依赖）
    → 改了它产物就变，而 key 不动

**而它当天就被撞上了**：那一天里 `pack.sh` 改了两次（加安装脚本、换时间戳），
两次都改变了产物，两次都没进 key。也就是说那两次改动之后，跳过判断会认为
盘上那个包还是对的 —— 而它不是。

这正是下面那条新规矩的第一次发作。

### 而「怎么验可复现」这件事本身也踩过一次（2026-10-15）

修完 `built_at` 之后，我拿「解包出来看时间戳」当判据，看到符号链接还是构建时刻，
于是判断「只修了一半」。**那是错的** —— 而错在判据上：

    apk extract 不恢复符号链接和目录的时间戳
    （apk-tools 的 fs_fsys.c 里那处 utimensat 只对非符号链接调用）

实测：同一个包解两次、隔 80 秒，符号链接的时间戳跟着解包时刻走，而真实文件不变。
包里那 8 个条目的 mtime 其实只有一个值，就是配方 `date`。

**所以：验可复现一律验 `.apk` 的 sha256，或者 `apk adbdump` 的 diff。**
「解开之后看时间戳」会假阳性 —— 它量的是你解包那一刻，不是包里记的东西。

★ 而这条和上面那些是同一类：**判据错了，结论就会错，而且错得很有说服力。**

**而它自己带来了一条新规矩**：那个键里**少一样，比没有键更危险** ——
少了它就不会重建，而产物其实变了，于是悄悄产出一批新旧混着的东西。
所以往里加东西是常态，而**拿不准的一样要加**。

### 它在 CI 上真的验过（2026-10-15）

不是"代码读下来是对的"，是跑出来的。五轮，用 `zlib`（它的自建依赖是空的，
所以每轮只动它一个）：

| 轮 | 情形 | 结果 |
|---|---|---|
| 1 | 第一次（还没有 key） | 建，并写下 key |
| 2 | 什么都不改 | 建 ——**而这是 bug**：旁路文件的文件名差三个字符，见下 |
| 3 | 什么都不改（修完之后） | **跳过** |
| 4 | **改配方、不升 `release`** | **重建，而理由是 `recipe`** |
| 5 | 什么都不改 | **跳过** |

第 4 轮是这一整件事的目的：**改了配方而没升那个号，它照样重建。** 而
"为什么"那一行也打出来了（`recipe`）—— 而如果构建环境也变了，那行会一并
列出来。它没有，所以那一次的重建确实只因为配方。

**而复现第 2 轮那个 bug 的形状值得记下来**：症状是「盘上没有它上次的
build_key」，而它离成因很远 ——

```
pack.sh 写:  zlib-1.3.2-1.apk.buildkey
restore 找:  zlib-1.3.2-1.buildkey          ← .apk 被剥掉了，差三个字符
```

**少一个文件在 shell 里是静默的。** 所以"我找不到它"这句话，要是没有，
你就只能看见"每次都重建"。

## 写新东西时的三句话

动手之前问自己：

1. **这件事的判断依据是什么？** 是算出来的，还是我记得的？
2. **如果我记错了，会怎样？** 如果答案是"静默地出错的产物"，那它必须变成能查的。
3. **我说的"成功了"，是真的吗？** 那句话挂在哪个判断上？
