# 构建在哪里跑

> **所有构建都在云端。本地不构建任何东西。**

这条是**硬规则**，不是偏好。

---

## 规则

```
✅ 云端 CI（GitHub Actions）       ← 一切构建
✅ CI 上临时加的工作流              ← 需要就加，用完删掉
❌ 本地 docker run / skirt build    ← 不要
❌ 本地跑构建脚本                   ← 不要
```

**"临时用 CI"是明确允许的**——为了验证一件事，可以专门加一个 workflow
或者一个 job，跑完就删。**不要因为"这个是一次性的"而退回到本地。**

## 为什么要这样

**① 本机是 macOS，不是构建目标。**

构建产物是 Linux 的原生 ELF。macOS 上要么跑容器（就是"本地构建"），
要么跑不了。而一旦开始跑容器，就绕不开这些：

- **APFS 默认大小写不敏感**（glibc 的构建会产生 `stamp.oS` 和 `stamp.OS`
  这种只差大小写的文件，在 macOS 上会互相覆盖）
- **文件属主和权限**在 macOS↔Linux 之间不保持一致（这个项目已经在这上面
  栽过三次：`/var/empty`、`authorized_keys`、`/root`）
- **性能**：容器里的构建比原生慢一截，而 CI runner 是原生 x86_64

**② 本地构建和 CI 构建是两条路径，会分叉。**

"我本地能编过"和"CI 能编过"不是一回事。而 CI 那条才是**发布用的那条**。
如果两条都留着，就会出现"本地过了、CI 挂了"——然后你要花时间分辨
是配方的问题还是环境的问题。

**只有一条路径，就没有这个问题。**

**③ 每条路径都要维护。**

本地那套要维护：Docker 镜像、payload 缓存、依赖还原脚本……
而它产生的价值（少等几分钟）抵不过它带来的分叉。

## 那"迭代太慢"怎么办

这是这条规则唯一的代价 ✗ —— 一轮 CI 七分钟，而写一个配方常常要试两三次。

**解法不是本地构建，是让每一轮 CI 干更多的事：**

| 做法 | 效果 |
|---|---|
| **一次派多个包** | 5 个包一轮，而不是 1 个包一轮 |
| **先过一个"能不能解析"的检查** | `skirt order` / 测试，几秒钟，不用等构建 |
| **临时 CI** | 需要专门验证一件事时，加一个 job，跑完删 |
| **把答案写进配方** | 一个包踩过的坑，下一个不要再踩（注释写清楚） |

**"起得来 ≠ 能用"这条教训延伸到这里就是：**
**"本地能编过 ≠ CI 能编过"** —— 既然只有后者算数，就别在别处花时间。
