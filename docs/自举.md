# 自举

自举（self-hosting）在这个项目里的**可操作定义**来自 `docs/决策记录/0011`：

> 构建环境的边界 = `base-devel` 变体的包集合。
> **自举完成 ⟺ 用 `base-devel` 能构建出 `base-devel` 本身。**

这不是口号，是一个**能实测的判据**——把 `SKIRT_BUILDENV` 指向自己的产物，
建一个包，看它炸不炸。炸了，第一个报错就是答案。

---

## 构建顺序不是一个纯拓扑排序

想「按依赖自动排出构建顺序」的话，会得到一个环：

```
glibc 的 build 依赖 binutils 和 gcc
gcc   的 runtime 依赖 glibc
        ↓
glibc → binutils → gcc → glibc
```

实测：35 个配方之间 **108 条依赖边**，其中这一个环是真的，不是数据错误。

**所以顺序不是配方的纯函数**——它取决于**构建环境里已经有什么**。
一个包如果在 `host/provides.txt` 里（也就是宿主环境已经提供），
它的依赖就不再需要用构建来满足，环就断开了。

这正是 0011 想说的那件事：

```
用 Debian 构建环境 →  glibc 和 gcc 由 Debian 提供 → 环断在这里 → 能建
用我们自己的产物   →  环断在自己上一轮的产物上     → 也能建（这就是自举）
从真正的一片空白   →  环断不开                   → 建不起来
```

**`host/provides.txt` 会随着自举推进而缩小，但永远清不空**——
真实的环 `glibc → make → glibc` 是消不掉的。这不是缺陷，是这一层的物理事实。

## 所以 `skirt order` 该是什么样

不是单纯的拓扑排序 ✗，而是：

```
输入：要建的包集合 + 构建环境已经提供什么（host/provides.txt）
输出：一个能实际跑通的顺序，以及【环断在哪里】
```

**做不到的时候要如实说**，而不是悄悄排出一个跑不通的顺序。

## 已知可用的顺序（2026-10-10 实测）

这是人写的，但**跑通过**（全量自举，35 步）：

```
m4 bison expat libffi python3          ← glibc 的 configure 要 bison 和 python3
zlib gcc binutils gmp mpfr mpc linux-headers make
filesystem gettext glibc libpng
bash coreutils sed grep gawk tar findutils diffutils gzip xz
patch libcap-ng util-linux zstd xxhash cmake ccache
hello
```

它的有效性**依赖一个前提**：`output/` 里有上一轮建好的 `glibc` 和 `gcc`，
环就断在它们上面。**把 `output/` 清空再跑这个顺序，会在 glibc 那一步失败。**

> 这个顺序将来由 `skirt order` 自动算出来（见 `docs/待办.md` 1.5.1）。
> 在那之前它是**对照物**：自动排出来的顺序要能和它对上。

## `output/` 丢了怎么办

先说清楚它为什么是承重墙：

| `output/` 是什么 | |
|---|---|
| 37 个已构建的包，2.1 GB | 在 `.gitignore` 里，**不在 git 里** |
| **构建的 sysroot 来源** | 每个包构建时，驱动把依赖的 payload 从它合并进容器 |
| **`base-devel` 镜像的来源** | 风味的 tar.gz 由它拼出来，再 `docker import` |

### 恢复路径

**不会从零开始**，因为这三样还在：

```
✓ 配方全在 git 里（包括这一路修的每一处）
✓ 源码有 sha256 钉住，能重新下载
✓ Debian 构建环境有 Dockerfile，在 git 里（tools/buildenv/），能重建
```

```bash
cd packages

# 1. 重建 Debian 构建环境（如果连镜像也没了）
docker build -t yojigenos/buildenv:aarch64 tools/buildenv

# 2. 按上面的顺序建一遍（不设 SKIRT_BUILDENV 就是用它）
#    —— 将来这一条会变成 `skirt bootstrap`
for p in m4 bison expat libffi python3 zlib gcc binutils gmp mpfr mpc \
         linux-headers make filesystem gettext glibc libpng bash coreutils \
         sed grep gawk tar findutils diffutils gzip xz patch libcap-ng \
         util-linux zstd xxhash cmake ccache hello; do
  ./tools/skirt build "$p" || break
done

# 3. 重拼构建环境，导入成镜像
./tools/skirt image base-devel
docker import output/aarch64/yojigenos-base-devel-aarch64.tar.gz \
               yojigenos/base-devel:aarch64

# 4. 用自举环境再建一轮 —— 这才是「自举」
export SKIRT_BUILDENV=yojigenos/base-devel
#    再跑一遍第 2 步的循环
```

**代价**：约 1–1.5 小时（ccache 冷的时候更久）。**损失**：自举状态和 ccache 缓存。

## 自举抓到的六个依赖

按**命令**查「自举缺什么」会得到一个**自信而错误的答案**。我最初就是这么得出
"只缺 `setpriv` 和 `patch` 两个"的。真实的缺口得让构建设一遍才知道：

| 缺的 | 怎么暴露的 |
|---|---|
| `patch` · `util-linux`（`setpriv`） | `command not found` |
| **`binutils`** | **产物差一个 GCS 位**——最难的一个，**没有任何报错** |
| `bison` · `python3` | `configure: error: missing: bison python` |
| `m4` · `expat` · `libffi` | 上面两个的依赖 |

**依赖分两类**，性质完全不同，详见 `docs/配方约定.md`：

```
构建时被调用的命令        → 跑一遍就报 command not found
configure 会【检查】的程序 → 平时不出现在命令行里，只能撞
```

## 两次空验证 —— 记在这里当教训

写这份文档的时候我想先「验证手写顺序是对的」，结果连续两次得到绿灯，
**两次都什么都没验证**：

| 第几次 | 写了什么 | 为什么是空的 |
|---|---|---|
| 1 | `for d in deps_for(spec, arch)` | `deps_for` 返回的是 **dict**，遍历到的是 `"runtime"` 这种键，不是包名 → 图里 **0 条边** → 排序结果就是字母序，而检查 `-1 > -1` 恒为假 |
| 2 | 改用 `direct_deps` | 图有 108 条边了 ✓ 但**有环** → 抛异常 → `order` 被设成空列表 → 比较又变成 `-1 > -1` → **绿灯依旧** |

**教训不在这两个 bug 本身，而在于**：一个检查如果**恒为真**，它比没有检查更糟——
它给出的是"已验证"的错觉。第一次绿灯让我差点把「手写顺序是对的」写进待办。

**能用的检查必须有一条会失败的路径。** 第二次之后之所以发现，是因为我把
「图里有几条边」也打出来了——**顺带输出的那个数字**才是真正的检查。

## 2026-10-10：两个架构的全量引导都成功了

第一次跑完 42 个包 —— **aarch64 和 x86_64 都是**。

```
✅ build (aarch64)  引导 —— 建出全部包    53 分 13 秒
✅ build (x86_64)   引导 —— 建出全部包    55 分 43 秒
```

x86_64 此前两次都死在 `glibc`（38/41，11 秒）。真因不是 glibc，是**依赖合并
破坏了构建容器**——详见下面那节。

### 让 x86_64 走通的三个修复

**① 基线挡住了我们自己的 libtool**

`host/provides.txt` 里列着 `perl/autoconf/automake/libtool`，于是 `deps.py`
认为「构建环境已提供」而跳过合并——`autoreconf` 用的还是 Debian 那份
（libtool 2.5.4，缺 `LT_SYS_SYMBOL_USCORE`）。

**正确的断法是不让环形成**：让 `libxcrypt` 走发行包（它带 `configure`，
不需要 autoreconf），`libxcrypt → autoconf → perl → libxcrypt` 那个环就没了。
于是 autotools 不必进基线，它们会被真的建出来并用上。

**② 合并依赖时保护构建容器的布局**

```
Debian amd64:  /lib64 → usr/lib64
               /usr/lib64/ld-linux-x86-64.so.2   ← 动态链接器住在这里
我们的包:      filesystem 提供 usr/lib64 → lib

cp -a /in/sysroot/. /   ← 一覆盖，链接器就悬空了
        ↓
容器里所有动态链接的程序立刻全废
        ↓
实测报错：Dynamic loader not found: /lib64/ld-linux-x86-64.so.2
```

aarch64 一直没暴露：那里的链接器是 `/lib/ld-linux-aarch64.so.1`，而
`/lib → usr/lib` 两边一致。**只有 x86_64 的 lib64 家族有分歧。**

修法：合并时**动态排除容器的挂载点**，再排除我们自己的布局路径：

```sh
while read -r _dev mnt _rest; do
  [ "$mnt" = "/" ] && continue
  EXCLUDES="$EXCLUDES --exclude=.$mnt"
done < /proc/mounts
```

**动态算，不写死清单**——实测它抓到了 `/in/sysroot`（我们自己的绑定挂载），
写死的清单想不到这一条。

**③ 一个诊断步骤不该有阻断的权力**

引导成功之后，job 却因为「上传构建日志」失败而报错，连带 `selfhost` 被跳过、
推送没跑。两个原因：`upload-artifact` 只认工作区里的路径（给 `/tmp` 会被
拒绝），而且它没有 `continue-on-error`。

**教训**：把日志收集放在关键路径上，等于给一个可有可无的东西发了否决权。

### 三次错误归因，都是环境问题

```
✗ "libffi 的树 autoconf 不了"      → 是基线挡住了我们自己的 libtool
✗ "libxcrypt 的树不行"             → 同一个原因
✗ "glibc 在 x86_64 上要特殊处理"    → 是合并破坏了容器
```

**"某个项目/某个架构有问题"这种结论要格外小心**——它听起来像事实，
实际往往只是"我这儿缺东西"。

## 自举到底在抓什么：四类问题

自举不是一个仪式，它是一个**探针**。用别人的构建环境时，一切缺口都会被那个
环境悄悄补上；换成自己的，缺口才会变成错误。

实测下来，错误分成四类，一类比一类深：

### 第一类：依赖没声明（十来个）

构建时调用了某个命令，但配方里没写。用 Debian 环境时它在那儿，换成自己的
就没了。

```
patch · util-linux · libcap-ng · binutils · bison · python3
m4 · expat · libffi · libxcrypt · rsync
```

**发现手段**：跑一遍，报 `command not found`。

### 第二类：包不完整

依赖**声明了**，但提供方给得不全。

```
cc   —— POSIX 规定 C 编译器叫 cc，而 gcc 上游自己不建这个链接
       （Debian 用 update-alternatives 补）。而我们只建了 c++。
       报错：ccache: error: Could not find compiler "cc" in PATH
```

**和第一类的区别**：第一类是"没人提供"，这一类是"有人提供，但给漏了"。
**发现手段**：跑一遍——`command -v` 审计找不到这类问题，因为命令确实存在。

### 第三类：工具链更严格

上游代码在更老的编译器下能过，在新编译器下过不了 `-Werror`。

```
libxcrypt  strchr 的 const 传播规则在 GCC 14+ 变了
           报错：initialization discards 'const' qualifier
gmp        C23 把 f() 的含义从「参数任意」改成「无参数」，configure 里的
           一个 K&R 风格测试编译不过
```

**这一类的意义**：用别人的工具链时，你的代码质量由**那个**工具链的标准决定；
换成自己的，标准才由你决定。

### 第四类：驱动自己的 bug

**最难的一类**，因为它不在包上，在工具上。

```
collect.py 的 _write_package：目录用 mkdir 建（默认 0755），
            于是 filesystem 里 chmod 1777 的 /tmp 变成 0755。
            文件那一路有 shutil.copy2 兜着，只有目录会中招。
            而构建是降权跑的 → 写不了 /tmp →
            glibc 的 configure 报
            "config.guess: cannot create a temporary directory in /tmp"
```

**它一直藏着的两个原因**：

1. `home`/`etc`/`var` 本来就是 0755，看起来都对——**只有特殊模式会露馅**
2. 报错是 `Permission denied` 和 "cannot create a temporary directory"，
   **看不出和权限有关**

**而最刺人的是**：`merge_tree`（deps.py）里早就写着同一句话——

> 目录的权限也要带过来。mkdir 用的是默认的 0755，而 /tmp 是 1777、
> /root 是 0700——丢了这些模式，构建会以莫名其妙的 "Permission denied"
> 失败，而且看不出和权限有关。

它那里修了，`collect.py` 这里漏了。**同一句话、同一个错、两个地方。**

> **写下来的教训，只有真被读过才有用。**

### 这四类对"怎么验证"的启示

| 类 | 怎么发现 |
|---|---|
| 一 | 跑一遍，看 `command not found` |
| 二 | 跑一遍——**`command -v` 审计查不出来**（命令确实存在） |
| 三 | 跑一遍，看 `-Werror` 报的新警告 |
| 四 | **跑一遍，然后把每个包的完整日志留下来** ✗ |

第四类说明了日志为什么必须完整：那次的失败信息只有 8 行，而真正的错误
（`config.guess`）在更上面。**"日志在 /tmp"那句假话，让排查绕了很久。**

### 这一轮之前，倒数第二个坎是「目录模式」

前面 41 个都过了，只有最后一个 `glibc` 死在 configure 的第一步：

```

而 `merge_tree`（deps.py）里早就写着同一句话。**同一句话、同一个错、两个地方。**

> 用 `base-devel` 能构建出 `base-devel` 本身。

  aarch64   05:42:07 ✓                 2026.10.11-aarch64   05:42:17 ✓
  x86_64    05:41:14 ✓                 edge-aarch64         05:42:15 ✓

                                       edge                 05:41:31 ✓
                                       2026.10.11-x86_64    05:41:22 ✓
                                       edge-x86_64          05:41:20 ✓
```

**不只是两个架构，还有多架构清单。** 所以 `docker pull yojigenos/base-devel:edge`
会自动拿到自己架构的那份——这才是一个能用的发布。

### x86_64 那道墙：CET

它死在最后一个包 glibc，链接 ld.so 时：

    undefined reference to `_dl_cet_open_check'
    undefined reference to `_dl_cet_check'

驱动给 x86_64 加了 `-fcf-protection=full`，而 glibc 的 configure 会检测
「编译器是否默认开 CET」，检测说不开 → 不编 `sysdeps/x86/dl-cet.c`
→ 但别的文件引用了那些符号 → 链接失败。

**加固参数本身没错，错的是它没被 configure 看见。** 显式 `--enable-cet`
让检测和构建一致——加固照旧，只是自洽了。

### 另一道：libpng 的并行竞态

它死在 [31/42]，报错是：

    implicit declaration of function 'setjmp'
    'LIBPNG_WAS_COMPILED_WITH__PNG_NO_SETJMP' undeclared

**完全指不到真正的原因。** 真因是 libpng 自己的 Makefile 有竞态：
`contrib/libtests/` 需要构建时用 gawk 生成的 `pnglibconf.h`，但没声明这个
依赖，于是并行 make 先编测试、后生成头文件。

定位方法是把两边的 **configure 输出逐行对比**——完全一致，所以分歧只能在
「构建时发生了什么」。然后看到同一个文件被编了两遍（竞态的典型样子），
再对着 `[构建] ... -j4` 和本地的 `-j8` 一看就明白了。

**跟并行度无关，是运气。**

### 还有一个副产品：CI 的日志能读了

GitHub 的 artifact 存在 Azure blob 上，而那个域名被 DNS 污染（解析到
11.142.125.225 这种假地址），`gh run download` 一直 EOF。

办法是绕开本地 DNS：用 DoH 查真实 IP，再 `curl --resolve` 指过去。
**从此 CI 的完整日志都读得到**——上面那两个 bug 都是这么找出来的。

### 端到端验证：陌生人拉得到吗

发布出去不算完，得验一下**别人的那条路**通不通：

```
$ docker manifest inspect yojigenos/base-devel:edge
    manifests: [ arm64/v8, amd64 ]        ← 清单里两个架构都在

$ docker pull yojigenos/base-devel:edge   ← 只写 :edge，不指定架构
    架构: x86_64                           ← 自动选中了 amd64
    gcc:  gcc (GCC) 16.2.0                 ← 我们自己建的那个
    cc:   在 ✓                             ← cc 修复在里面
    /tmp: drwxrwxrwt                       ← 目录模式修复在里面
```

**这才是"发布"的完整含义**：一个陌生人只写 `:edge`，拿到的是他那个架构的、
带着全部修复的、用 GCC 16.2.0 的构建环境。

而 `gcc (GCC) 16.2.0` 出现在镜像里这件事本身，就是整个项目的意义——
**它不是 Debian 的 gcc，是从源码建出来的。**

## 第五类：上游工具自己的回归

前四类都在我们的配方或驱动里。这一类不在——**是我们用的某个上游工具坏了。**

### gawk 5.4.1：未赋值数组元素变成 "0"

```
$ gawk 'BEGIN { if (a["x"] == "") ; a["x"] = a["x"] "y"; print "[" a["x"] "]" }'
[0y]      # 5.4.1
[y]       # 5.4.0、mawk、以及 POSIX 期望的
```

一个"读过但从未赋值"的数组元素，**一旦参与过比较或判断**，再当字符串用就
变成了 `"0"`。上游自己的 `make check` 就有 6 个测试失败（arraysort2、
delarpm2、elemnew2、elemnew4、matchuninitialized、typeof7）。邮件列表里还
提到它同样会让 **GCC 16.2 的构建失败**。

**触发条件是"编译 gawk 时没有 MPFR"**——而 gawk 在我们的构建顺序里排第 21、
mpfr 排第 29，所以我们的 gawk 必然是 `--without-mpfr` 建的，正好落在里面。

### 它在我们这儿长什么样

libpng 的 `scripts/options.awk` 里有这么一句：

    requires[opt] = requires[opt] " " val

`requires["UNKNOWN_CHUNKS"]` 从来没被赋过值，于是这一句读它时拿到 `"0"`，
`pnglibconf.h` 里**每一项都成了 undef**，`PNG_SETJMP_SUPPORTED` 消失，
`png.h` 不 include `<setjmp.h>`，最后报出来的是：

    contrib/libtests/pnggetset.c:53: error: implicit declaration of function 'setjmp'

**一个 awk 的版本差异，报成了"setjmp 没有声明"。**

### 怎么找到的（这段方法值得复用）

1. **先要一个一分钟的复现**。从"每轮两小时的 CI"变成"本地一分钟"，这一步
   比什么都值钱。做法：把 CI 用的那个构建环境从 Docker Hub 拉下来，用它
   直接跑那一个包。
2. **切分流水线，找第一个分歧点**。libpng 的生成是四步 awk/gcc 串起来的。
   我 diff 了第①步的产物 `tf4`——**完全一致**——于是断定分歧在第②步。
3. **插桩，看类型而不只是看值**。`typeof()` 给出了 `untyped` vs `unassigned`，
   一眼就看出这不是"值算错了"，是"类型语义变了"。
4. **写最小复现**。七种写法全试一遍，确认是基础语义而不是边角情况。
5. **查上游**。搜到 bug-gawk 的同一个报告，连触发条件（无 MPFR）都对上了。

### 修

**停在 5.4.0**，而不是打补丁。理由：前者是上游发布的、sha256 可校验的源码
（符合配方约定），后者要我们维护一份改过的源码。5.4.2 一出来就升回去。

### 这一类对"验证"的启示

**报错信息指向的地方，可能和真正的原因隔着好几个抽象层。** 这次的链条是：

    awk 版本 → 数组元素语义 → libpng 的配置生成 → 一个宏没定义
             → png.h 的分支 → setjmp 没声明 → 编译错误

**从最后一环往回查是查不动的**（"为什么 setjmp 没声明"和 awk 有什么关系？）。
能做的是**找到两个环境的第一个分歧点**，而不是盯着最终的错误看。
