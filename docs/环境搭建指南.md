# YojigenOS 构建环境搭建指南

> 目标：**一台能编译、能 chroot、能装东西的真 Linux 机器，加上一条从 Mac 到它的顺畅开发流。**
>
> 阶段：第 1 周。完成本指南后，你应该能在这个环境里跑通一个 hello world 的构建。

---

## 0. 架构策略（已定）

**本机：Apple M4（arm64）。开发用 aarch64 换速度，目标平台包含 x86_64。**

x86_64 的产出方式**不是**跑一个模拟的 x86_64 虚拟机，而是**交叉编译**——完整方案见 [附录 A](#附录-a双架构策略)。

### 三条纪律

1. **第 1~4 阶段只在 aarch64 上工作。** 构建系统开发和工具链自举都不碰 x86_64。
2. **从第一天起，所有产物就带架构维度**（输出路径、包元数据、命令行参数），但不去执行。
3. **不要同时自举两个架构。** 每多一个架构 = 把整个自举流程重做一遍。

> **为什么不在 macOS 上用 QEMU 直接产出 x86_64？**
> 本机的 QEMU 只有 `qemu-system-*`（全系统模拟），跑异架构客户机慢 5~20 倍，日常构建不可用。
> 关键的用户态模拟器 `qemu-x86_64` 是 **Linux 二进制**，必须装在 Linux VM 里，macOS 上装不了也用不上。
> 详见附录 A。

### 本机已验证的环境事实

| 项 | 值 |
|---|---|
| 机器 | Apple M4（arm64） |
| `uname -m` | `arm64` |
| QEMU | 11.1.2（Homebrew），仅有 `qemu-system-aarch64`、`qemu-system-x86_64`、`qemu-img` |
| 缺失 | `qemu-x86_64`、`qemu-aarch64`（用户态模拟器，需在 Linux 内安装） |

## 1. 准备构建机

### 路线 A：有旧电脑或服务器（首选）

编译吃 CPU、吃内存、吃磁盘 I/O。真机的体验比 VM 好一个档次，而且可以一直开着。

**装什么发行版？**

| 选择 | 评价 |
|---|---|
| **Ubuntu Server LTS（24.04 或更新）** | ✅ **推荐**。省心、工具链版本够新、文档最多 |
| Debian Stable | 稳定，但工具链版本偏旧，构建新软件时可能不够 |
| 其他 | 随意，但别选太冷门的，你会浪费时间去搜答案 |

**关键：不要装桌面环境。** 省资源，而且你会更快习惯纯命令行——做发行版这是必备技能。

**安装时注意：**

- 磁盘给足，**至少 100GB**（构建产物比你想的占地方），建议 150GB 以上
- 启用 SSH 服务
- 创建一个普通用户（不要一直用 root）

装完后跳到 [第 2 节](#2-宿主系统配置)。

### 路线 B：只有 Mac

先说清楚为什么必须用 VM，不能用 Docker：

> 你需要**真的 Linux 内核 + root 权限 + 自由地 mount/chroot**。Docker Desktop 在 macOS 上跑在一个隐藏的 VM 里，你无法在其中自由做嵌套 mount 和 chroot——而这两件事是自举流程的基础。**必须用 VM 或真机。**

#### B-1. UTM（图形界面，适合交互式使用）

官网：https://mac.getutm.app/

新建虚拟机时这样配：

| 项 | 建议值 | 说明 |
|---|---|---|
| 系统 | Linux | |
| ISO | Ubuntu Server LTS **arm64**（Apple Silicon）或 **amd64**（Intel） | **架构一定要对** |
| 内存 | 8GB 起，建议 16GB | 编译很吃内存 |
| CPU | 4~8 核 | 按你 Mac 的核心数给一半左右 |
| 磁盘 | **150GB** | 别省，事后扩容很麻烦 |
| 网络 | 默认（Shared / Emulated VLAN） | 能上网就行 |

装完后在 UTM 里开启端口转发，或直接用 UTM 显示的 IP 连接。

#### B-2. Lima（命令行，适合脚本化和长期使用）

安装：

```bash
brew install lima
```

创建配置文件 `yojigen-build.yaml`：

```yaml
# Apple Silicon 用 vz（Apple 虚拟化框架），性能最好
vmType: vz
arch: aarch64

cpus: 8
memory: "16GiB"
disk: "150GiB"

images:
  # 请到 https://cloud-images.ubuntu.com/releases/ 确认当前 LTS 的实际文件名
  - location: "https://cloud-images.ubuntu.com/releases/24.04/release/ubuntu-24.04-server-cloudimg-arm64.img"
    arch: "aarch64"

mounts: []          # 故意留空，原因见第 3 节
```

启动并进入：

```bash
limactl start --name=yojigen ./yojigen-build.yaml
limactl shell yojigen
```

> Intel Mac 请把 `vmType` 改成 `qemu`、`arch` 改成 `x86_64`，镜像换成 `amd64` 版本。

## 2. 宿主系统配置

在构建机里执行。注意这里配的是**宿主机**，不是你的发行版——你的发行版要从零构建，不要拿宿主的东西当自己的。

### 2.1 基础工具

```bash
sudo apt update
sudo apt install -y \
  build-essential gcc g++ make \
  binutils bison flex gawk m4 \
  texinfo patch wget curl git \
  xz-utils zstd gzip bzip2 tar \
  python3 python3-pip \
  rsync tmux htop tree \
  qemu-user-static binfmt-support
```

> 这些是宿主机借给你的工具。**LFS 的书会明确列出宿主需要满足的最低版本要求**，开工前对一遍。

### 2.2 建立构建目录

```bash
sudo mkdir -p /build
sudo chown "$USER:$USER" /build
```

**为什么不用 `~`？** 因为自举过程中会做 chroot 和大量路径处理，短路径、浅层级能避免很多莫名其妙的错误。`/build` 是惯例。

### 2.3 确认关键前提

```bash
# 必须有 root 权限
sudo -v

# must be x86_64 或 aarch64，记下它——这是你的目标架构
uname -m

# 确认磁盘空间
df -h /build

# 确认这些命令存在（自举流程依赖）
for c in gcc make ld as bison flex gawk m4 patch wget; do
  printf '%-8s %s\n' "$c" "$(command -v $c || echo '❌ 缺失')"
done
```

## 3. 建立开发流

**原则：代码在 Mac 上写，构建在 Linux 里跑。**

### 3.1 推荐：VS Code Remote-SSH

在 Mac 上装 VS Code 和 Remote - SSH 扩展，然后直接连构建机：

```
Remote-SSH: Connect to Host → user@<构建机IP>
```

之后你在 Mac 上编辑的文件，实际存在于 Linux 里——**路径一致，没有同步问题**。这是最省心的方案。

### 3.2 ⚠️ 一个必须避开的坑

**不要在任何共享目录（9p / sshfs / virtiofs / UTM 共享文件夹）里跑构建。**

原因：构建过程会产生**海量小文件的读写**（`configure` 的探测、编译中间产物、打包时的文件遍历）。共享文件系统的这类操作比本地磁盘慢 10 倍以上，一个几分钟的构建会变成一小时。

**正确做法：**

- 用 Git 同步：Mac 上写 → commit → push 到构建机（或反向）
- 或者用 VS Code Remote（文件本来就在 Linux 上，天然没有这个问题）
- 构建工作目录永远在 Linux 本地磁盘（`/build`）

Lima 的配置里 `mounts: []` 就是这个原因。

### 3.3 免密 SSH（可选但强烈建议）

```bash
# 在 Mac 上
ssh-keygen -t ed25519 -C "yojigen-build"
ssh-copy-id user@<构建机IP>
```

然后在 `~/.ssh/config` 里加个别名：

```
Host yojigen
    HostName <构建机IP>
    User <用户名>
```

之后 `ssh yojigen` 就能直达。

## 4. 项目目录结构

在**构建机**上（如果用了 VS Code Remote）或 Mac 上建立。这是起步用的最小结构，别一次设计太满：

```
YojigenOS/
├── README.md
├── docs/
│   ├── 环境搭建指南.md          # 本文件
│   ├── 要求与验收.md            # 三条要求 + 可验收的清单
│   ├── 决策记录/                # ADR：每个技术决定 + 为什么
│   │   └── 0001-glibc-and-systemd.md
│   └── 工作笔记/                # 构建日志，随手记
│       └── 2026-xx-xx.md
├── packages/                    # ★ 配方树，这是你真正的核心资产
│   └── hello/
│       └── spec
├── tools/                       # 构建系统（你自己的代码）
│   └── yj
└── host/
    └── setup.sh                 # 把第 2 节的命令脚本化
```

**关于 `docs/工作笔记/`：** 不要把它当成"写文章"。每次做完一件事，花 10 分钟记三件事——**做了什么决定、为什么、踩了什么坑**。三四个月后，这些笔记自动就是你的构建日志和文档素材，不需要额外投入。

## 5. 验收清单

环境搭好的标准是下面全部打勾。**打勾之前不要开始写配方。**

- [ ] `ssh yojigen`（或 `limactl shell yojigen`）能直接进入构建机

#include <stdio.h>
int main(void) { printf("YojigenOS build host ready\n"); return 0; }
EOF
gcc hello.c -o hello && ./hello

- [ ] 开发流已通：在 Mac 上改一个文件，能在 Linux 侧看到改动
- [ ] `/build` 不在任何共享目录下（用 `df -h /build` 或 `mount | grep build` 确认）
- [ ] Git 已配置（`user.name` / `user.email`），仓库已初始化

## 6. 已知的坑

| 坑 | 表现 | 对策 |
|---|---|---|
| **架构选错** | Apple Silicon 上装了 amd64 VM | 装之前 `uname -m` 对一遍；x86_64 在 M 系列上慢到不可用 |
| **在共享目录构建** | 构建耗时异常长 | 见 3.2，构建永远在本地磁盘 |
| **宿主机污染** | 后面自举时"成功"了，但其实用了宿主的库 | 从现在起养成习惯：**明确知道每个命令用的是谁的 `gcc`/`ld`** |
| **磁盘不够** | 第 3~4 阶段中途空间耗尽 | 一开始就给 150GB |
| **装了桌面环境** | 浪费资源，且会干扰你对系统的判断 | 构建机只要命令行 |
| **一直用 root** | 权限问题被掩盖，出问题难定位 | 用普通用户 + sudo |

# 附录 A：双架构策略

## A.1 三种"跑异架构"的方式，速度差 20 倍

| 方式 | 相对速度 | 用途 | 在哪装 |
|---|---|---|---|
| **全系统模拟**<br>`qemu-system-x86_64` | 🐌 1/5 ~ 1/20 | 只在里程碑验收时启动 x86_64 VM，验证"真的能开机" | macOS 或 Linux 均可 |
| **交叉编译**<br>aarch64 host → x86_64 target | ⚡ 接近原生 | **日常主力**：绝大多数包这样产出 | Linux VM 内 |
| **用户态模拟**<br>`qemu-x86_64` + `binfmt_misc` | 🚀 接近原生 | **补漏**：让 configure 探测和测试能跑 | **必须 Linux VM 内** |

三者不是替代关系，是**分工**。日常工作 99% 的时间花在中间那行。

## A.2 为什么离不开"用户态模拟"补漏

交叉编译有一个经典障碍：**`configure` 脚本经常要"编译一个小程序，然后运行它"来探测系统特性。**

在交叉编译场景下这必然失败——刚编出来的 x86_64 二进制在 aarch64 上跑不起来。

`binfmt_misc` + `qemu-x86_64` 让这类二进制**透明执行**：内核识别到 x86_64 的 ELF 头，自动交给 `qemu-x86_64` 运行。configure 于是顺利通过。

Docker 的多架构镜像、各大发行版的新架构 port，用的都是这一招。

**两个必须知道的边界：**

- ⚠️ `qemu-user` 是 **Linux 二进制**。你本机（macOS）没有，也装不了/用不上。它必须装在 Linux VM 里——这就是第 2.1 节把它加进安装列表的原因。
- ⚠️ 它不完全等价于真机。涉及 KVM、特定 ioctl、`perf`、硬件特性的测试会**假失败**。遇到诡异失败时，先怀疑是不是模拟的锅。

## A.3 GNU triplet：三段式架构术语

你很快会撞见 `--build` / `--host` / `--target`，它们经常让人绕晕。理清方式：

| 名称 | 含义 |
|---|---|
| `build` | **编译器**跑在哪台机器上 |
| `host` | **编译产物**跑在哪台机器上 |
| `target` | （只有编译器类程序才需要）这个编译器**产出的代码**跑在哪台机器上 |

你会遇到的两个场景：

```bash
# 场景一：日常交叉编译一个包（在 arm64 上产出 x86_64 的包）
./configure --build=aarch64-linux-gnu --host=x86_64-linux-gnu
# target 省略 = 等于 host

# 场景二：构建交叉编译器本身
#         一个"跑在 arm64、产出 x86_64 代码"的 gcc
./configure --build=aarch64-linux-gnu --host=aarch64-linux-gnu --target=x86_64-linux-gnu
```

场景二是最容易读错的一个：`build == host != target` 的意思是"**在这里跑，为那里产出**"。

## A.4 从第一天就要做到的架构意识

这一节是**现在定义、现在不用**的清单。成本接近零，事后补的代价很大：

| 要求 | 现在做的成本 | 事后补的代价 |
|---|---|---|
| 产物路径带架构：`output/{aarch64,x86_64}/` | 零 | 要改仓库布局 + 所有元数据 |
| 包元数据带架构字段 | 零 | 要重写所有已产出的包 |
| 构建驱动接受 `--arch`，默认当前架构 | 几行代码 | 要改所有调用点 |
| spec 支持架构后缀：`DEPS__X86_64`、`CFLAGS__AARCH64` | 零（定义了不用） | 要改 spec 解析器 + 所有已写的配方 |

**在单架构阶段把多架构的"形状"留出来，但不要实现多架构的逻辑。**

## A.5 时序

| 阶段 | 做什么 | 不做什么 |
|---|---|---|
| 第 3-4 周 | aarch64 工具链自举 | ❌ **完全不碰交叉编译** |
| 第 4 阶段后 | 用已自举的 aarch64 系统当宿主，构建 aarch64→x86_64 交叉工具链 | ❌ 不要重做一遍自举 |
| 之后 | 交叉构建 x86_64 系统，用 `qemu-user` 补漏 | ❌ 不要为 x86_64 起第二套构建脚本 |
| 最后 | 双架构自动化 | |

**核心原则：每个阶段结束时，你都必须有一个"能用的系统"。** 这个约束会自动阻止你同时调试两件难事。
