# 配方约定

写 `packages/<名>/spec.toml` 时要守的规矩。每条都写了为什么——只列规则的话，
遇到规则没覆盖的情况就不知道该怎么判断了。

## 源

### 三种归档的真实差别

选源之前先理解它们各强在哪：

| | 字节稳定 | 有生成物 | 内容不可变 |
|---|---|---|---|
| **release 附件**（`/releases/download/…`） | ✅ **存好的文件**，GitHub 只是原样发送 | ✅ | ⚠️ 理论上可被替换（sha256 拦得住） |
| **commit 归档**（`/archive/<commit>.tar.gz`） | ❌ GitHub 按需生成，压缩参数改过 | ❌ **原始源码树** | ✅✅ 哈希钉死 |
| ~~tag 归档~~（`/archive/refs/tags/…`） | ❌ | ✅ | ❌ **tag 可以移动** |

**关键的一条是「有生成物」**：commit 归档是原始 git 树，**里面没有 `configure`**。

实测（xz v5.8.4）：

```
release 附件:   configure ✅  Makefile.in ✅  config.h.in ✅
同一 commit:    configure ❌  Makefile.in ❌  config.h.in ❌
```

而我们的配方模型是建立在「发行包自带 `configure`」上的——**这正是我们不需要
autoconf / automake / libtool / m4 / perl 的原因**。给一个 autotools 项目换成
commit 归档，就要把那一整条链补回来。

### 所以按项目类型选

| 项目类型 | 用什么 |
|---|---|
| 上游自己有站点（`ftp.gnu.org`、`cmake.org/files`、`cdn.kernel.org`） | **优先用它**——上游自己的承诺 |
| GitHub，**有 release 附件** | **用附件** ✓ 尤其 autotools 项目（要生成物） |
| GitHub，**没有 release 附件**，且是 cmake / meson / 纯 Makefile | **用 commit 归档** ✓（它们不需要生成物） |
| GitHub，**没有 release 附件**，且是 autotools | ❌ 两条路都不通——去找上游别处的正式发布包，或者把 autotools 补进树 |
| **❌ 任何情况** | **不要用 tag 归档**——tag 可以移动，上游一推你就悄悄换了源码 |

### commit 归档要两层钉

```toml
[[source]]
# commit hash 进 URL —— 内容不可能变，那棵树是哈希钉死的
url    = "https://github.com/OWNER/REPO/archive/1a2b3c4d….tar.gz"
# sha256 仍然要 —— GitHub 按需生成 tarball，字节可能变
sha256 = "…"
```

**两者管的不是一回事**：commit 保证「内容对」，sha256 保证「字节对」。

去掉 sha256，GitHub 哪天重新生成你就不知道；去掉 commit（改用 tag），上游
一推 tag 你就悄悄换了源码。**两个都要。**

> 真正的解法是源码镜像（`docs/待办.md` 6.1）——我们自己持有那份字节，连带
> 生成物一起，就不再受这三条限制。

### 一个具体的例子：libcap-ng

它 0.9.x 只在 GitHub 发，**release 没有附件** ✗——只有按需生成的归档。
而它是 autotools ✗，commit 归档里没有 `configure`，也救不了。

所以退到 **0.8.5**：那是上游作者放在 `people.redhat.com` 上的正式发布包，
URL 稳定、带生成物。我们只需要它能让 `setpriv` 编出来，版本新旧在这个用途上
可以忽略。等源码镜像做完，就能换成 0.9.6。

### 备用源

主源在国内时通时不通（`ftp.gnu.org` 实测如此，构建 `patch` 时直接 SSL 断流）。
`urls` 列备用源，按顺序试：

```toml
[[source]]
url  = "https://ftp.gnu.org/gnu/foo/foo-$VERSION.tar.xz"     # 主源：CI 在海外，更快
urls = ["https://mirrors.tuna.tsinghua.edu.cn/gnu/foo/foo-$VERSION.tar.xz"]
sha256 = "…"
```

**sha256 才是身份，换源不降低信任。** 校验失败**不会**换源重试——内容不对
不是网络问题，是配方或镜像错了。悄悄换一个源继续，会把「镜像被投毒」变成
「构建成功」。

### sha256 必须填满 64 位十六进制

不填、填错长度、填一个占位符，都会在下载阶段报错。**不接受未校验的源码。**

## 依赖：分成两类，而按命令只能查出第一类

写 `runtime` / `build` 列表时，缺的东西有两种，**性质完全不同**：

| | 例子 | 怎么发现 |
|---|---|---|
| **构建时被调用的命令** | `make`、`gcc`、`setpriv`、`patch`、`as`/`ld`（binutils） | 跑一遍就知道 `command not found` |
| **configure 会「检查」的程序** | `bison`、`python3`、`awk`、`msgfmt` | **只能撞**——它们平时不出现在命令行里 |

第二类是最容易漏的。`glibc` 的 `configure` 把话说得很直白：

```
configure: error:
*** These critical programs are missing or too old: bison python
```

**教训**：用 `command -v` 去审计"构建环境缺什么"会得到一个自信而错误的答案。
我一开始就是这么得出"自举只缺 setpriv 和 patch 两个"的结论的。真实的缺口，
得让构建设一遍才知道——这也是 `docs/决策记录/0011` 把「自举」定义成一个
**可实测判据**的价值所在。

### 怎么核对

Debian 那个构建环境镜像是个现成的参照，但要**整个镜像**对照，不能只看
Dockerfile：

```bash
docker run --rm debian:stable-slim dpkg-query -W -f='${Package}\n' | sort > /tmp/base.txt
docker run --rm yojigenos/buildenv:aarch64 dpkg-query -W -f='${Package}\n' | sort > /tmp/env.txt
comm -13 /tmp/base.txt /tmp/env.txt      # 构建环境比基础镜像多装了什么
```

**为什么不能只看 Dockerfile**：`python3` 和 `perl` 都不在它的 apt 清单里，
而是被 `meson` 和 `autoconf` 当依赖拖进来的。清单会骗人，装出来的东西不会。

## 时间戳

`[package] date` 必须写在配方里，带时区，而且是 TOML 原生日期时间（不能加引号）。

```toml
date = 2026-10-10T14:00:00Z      # ✓
date = "2026-10-10T14:00:00Z"    # ✗ 加了引号就是字符串
date = 2026-10-10T22:00:00       # ✗ 没有时区
```

**加新包时，date 要晚于它的所有依赖**，否则 `SOURCE_DATE_EPOCH` 会取自依赖
（那是对的，但会让人困惑）。理由见 `docs/决策记录/0005`。

## configure

### 不要用 `--disable-nls`

上游做了中文，我们只要**别把它关掉**。`docs/决策记录/0012` 定了这条边界：
有中文的用中文，没有的不强求。

### 关掉树里没有的可选依赖

不是嫌它们没用，是它们还没进来。写清楚是哪个：

```toml
"--without-python",     # 没有 python3
"--without-ncurses",    # 没有 ncurses；fdisk 的交互界面会退化
```

**configure 的汇总里会列出「因为缺什么而没编什么」**——值得看一眼，那是最
省事的缺口清单。`util-linux` 的 `setpriv` 就是这么被发现的（它需要
`libcap-ng`，而且是全有或全无）。

### 目录要显式指到 /usr

按 `docs/决策记录/0001`，我们做 usr-merge：`/bin`、`/sbin`、`/lib`、`/usr/lib64`
都是指向 `/usr` 里对应目录的符号链接。

**驱动的默认值已经钉住了库目录**，三个构建系统都是：

```
autotools  --prefix=/usr --libdir=/usr/lib
meson      --prefix=/usr --libdir=lib --buildtype=release
cmake      -DCMAKE_INSTALL_PREFIX=/usr -DCMAKE_INSTALL_LIBDIR=lib
```

**为什么必须钉**：autoconf 在 64 位系统上有个启发式，会把 `libdir` 定成
`${prefix}/lib64`。包于是装出一个**真目录** `/usr/lib64`，和符号链接撞车，
拼 rootfs 时 `cp` 直接失败：

```
cp: cannot overwrite non-directory '/rootfs/./usr/lib64'
    with directory '.../libffi-3.8.0-1/payload/./usr/lib64'
```

失败是响亮的，不会静默出错——但得知道为什么。

**有一个包连 `--libdir` 都不听**：`libffi`。它的 `configure.ac` 去问 gcc：

```m4
if test x"$enable_multi_os_directory" != x"no"; then
  multi_os_directory=`$CC $CFLAGS -print-multi-os-directory`
  case $multi_os_directory in
    ../*) toolexeclibdir=$toolexeclibdir/$multi_os_directory ;;
```

它问的是「多架构的库该放哪个子目录」，gcc 回答 `../lib64`，于是它在 `libdir`
后面又接了一层。上游为这种情况留了开关（`multi-os-directory` 是 GCC 的概念，
libffi 只是跟随），加 `--disable-multi-os-directory` 就老实了。

**这类包的特点是「不听 --libdir」**。遇到装错目录的包，先看它的 configure 里
有没有在算自己的目录，而不是怀疑驱动。

有些包也会故意装到 `/bin`（`util-linux` 为了让 `mount` 在 `/usr` 挂载前可用），
那同样要显式覆盖：

```toml
"--bindir=/usr/bin",
"--sbindir=/usr/sbin",
"--libdir=/usr/lib",
```

## 构建类型

```toml
type = "autotools"   # ./configure && make && make install
type = "meson"       # meson setup _build && meson install
type = "cmake"       # cmake -B _build && cmake --install
type = "custom"      # 由 steps.sh 提供 build() / package()
```

`custom` 用于需要自举的构建系统本身——`cmake` 就是用它自己的 `./bootstrap`
+ `make` 编出来的（不需要预装 cmake）。`steps.sh` 通过重定义 `build()` /
`package()` 覆盖默认行为。

## 补丁

放在配方目录里，`[build] patches = ["名字.patch"]` 引用。

**必须是相对源码树根的路径**，而且用 `-p1 --fuzz=0` 应用——不精确匹配就失败。
理由：`patch` 默认容忍 2 行模糊匹配，一个已经不适用的补丁会被「差不多」地贴
上去，产出无声的错误代码，等到运行时才以看不懂的方式炸掉。

## 子包

一个配方可以按文件模式产出多个包（`docs/决策记录/0014`）。

**只搬真正占体积的东西。** `/usr/lib` 下那些不带版本号的 `.so` 是链接期的
符号链接，但里面可能混着真的 ELF——模式匹配分不出「符号链接」和「真 ELF」。
宁可少省几 KB，也不要写一条会误伤运行时的规则。

## 检查

```bash
python3 -m unittest discover -s tools/tests    # 每个真实配方都会被结构性检查
```

测试会验证：包名和目录一致、`release` 是整数、`date` 能算出时间戳、source
的 URL 没有未展开的占位符、sha256 是 64 位十六进制、子包名全局唯一且不和
配方重名。
