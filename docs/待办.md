### ★ 自举抓到的六个依赖 —— 这个方法论值得记住

### 已查到底（2026-10-15；原来叫「还没验证的」）

- ~~**13 字节的残留差异**~~ **查到底了 —— 它不是 bug，是「构建环境要进 `build_key`」的正面证据。**

  量法：同一个配方、**同一个 gcc 16.2、同一个 binutils 2.47**，只把环境里那份 **glibc**
  换掉（Debian 的 → 我们自建的），产出的 `hello` **段表逐项相同、文件大小也相同**
  （67824 vs 67824），而逐字节比**正好差 13 个字节**（所以「在代码段里，不是段结构差异」
  那句是对的）：

  | 差在哪 | 字节 | 是什么 |
  |---|---|---|
  | `.text`：文件 0x09104、0x09108–0x0910f | 9 | 链接期从**环境 glibc** 的 `libc_nonshared.a(atexit.oS)` 拉进来的 `atexit` 桩：`bti c; adrp; mov x1,#0; ldr x2,[x2]`（Debian 的 2.41）vs `bti c; adrp; ldr x2,[x1]; mov x1,#0`（我们的 2.44）。**`hello` 自己编出来的机器码逐字节相同** |
  | `.note.ABI-tag` | 2 | 最低内核版本：Debian 的 glibc 写 `3.7.0`，我们的写 `5.4.0` |
  | `.note.gnu.property` + `.ARM.attributes` | 1 + 1 | GCS 位（`BTI,PAC` vs `BTI,PAC,GCS`）—— 由 gcc 16.2 的 AEABI 属性决定，而链接期对全部输入取「与」（环境那份 glibc 的 crt 会否决它，见 gcc 配方里的注释） |

  旁证：`skirt build hello` 跑两遍（`SKIRT_BUILDENV=bgenv` / `yojigenos/devel`）得
  67744 / 67824；把工具链钉死、只换 glibc 的那组对照才得到上面这 13 字节。
  像这样「同名同配方、只换环境、差一点点、而且是确定性的」，正是下面 1.5.B 里
  **构建环境**那一格必须进键的理由。**不需要修** —— 要「一致」只能是两边用同一份 glibc。
- **gcc 对 `-print-multi-os-directory` 的回答**：它说 `../lib64`，而文件实际在
  `/usr/lib`（当时的判断：它是驱动加 `--libdir` 之前构建的，全量重建应该会修好）。
  **2026-10-15 复查（真实构建环境）**：它**仍然**这么答——重建不会改它，这个回答
  是 gcc 目标配置里写死的（`MULTILIB_OSDIRNAMES`）；而 `libstdc++` 等确实装在
  `/usr/lib/`。**结论：回答偏、落点不偏，不是待修的 bug**——回答指向的那条路被挡在
  中间：`/usr/lib64` 按 0001 是 usr-merge 的符号链接（→ `lib`，产物里由 filesystem
  提供；gcc 构建时配方在 `package()` 里预置同一个链接，install 才落进 `/usr/lib`，
  装完删掉）；顶层那部分则由配方第 78 行的 `--libdir=/usr/lib` 钉着。

### 1.5.Bb ★★ `spec` 里写了 `configure`，驱动的默认值就被【整个替换掉】

**症状（2026-10-16 实测）**：`iputils` 装出来是 **`/usr/local/bin/ping`** —— 而
`usr/bin` 里是空的。于是 `test_kind.py` 那条「net 但 bin/ 里没有可执行文件」报错。

**根因**在 `build.py:141`：

```python
opts_list = list(b.get("configure", ["--prefix=/usr", LIBDIR]))
```

`b.get(键, 默认)` 的语义是「**有就用你的，没有才用默认**」——所以 spec 里一旦写了
`configure`，驱动那两个默认值（`--prefix=/usr` 和 `--libdir=/usr/lib`）**就没了**。
而 meson 自己的默认 prefix 是 `/usr/local`，cmake 也是。

**中招的四个**（2026-10-16 修完）：`lib/libevent` · `net/dbus` · `net/iputils` ·
`tool/fastfetch`。★ 而这不是"它们四个写错了"——是**这个接口的形状会惩罚每一个
只写自己那几个选项的人**，而那种写法是**自然的**。

**根本的修法**：把 `opts` 从「覆盖」改成「追加」：

```python
opts_list = ["--prefix=/usr", LIBDIR] + list(b.get("configure", []))
```

★ 而它**不能现在做**：`build_key` 把 `skirt/**` 算进 `tooling_hash()`，所以改
`build.py` 会让**所有 89 个包**都算成 stale → 全量重建（2 小时 × 2 架构）。
而 §1.5.B（增量构建）那一整条要解决的正是这件事——**两条该一起做**。

★ 在那之前，还有个便宜的中间态：**让驱动在 spec 写了 `configure` 而没写 prefix
时报一个警告**。那也要动 `skirt/`，所以同样要等 §1.5.B。**在那之前靠人记得。**

### 1.5.Bc ★★★ `restore` 在多版本并存时【取最旧的那个】—— 升 release 会静默失效

**症状（2026-10-17 实测）**：配方里 `iputils` 是 `release = 3`、`libevent` 是 `r2`、
`fastfetch` 是 `r2`，而**线上仓库里三个都是 `r1`**。而 CI 明明说了"该重建"、
"建出来了"、"deploy 传了 r3 的 buildkey"。

**根因**在 `restore.py:349-371`：

```python
shared = {rel: names for rel, names in _by_rel(jobs).items() if len(names) > 1}
…
if shared:
    for rel, names in sorted(shared.items()):
        print(f"  ★ {len(names)} 个包指向同一个目录 {rel}：{'、'.join(names)}"
              f" —— 只还原了排在前面的那个")
```

`var/pkgs/<arch>/` 里**同一个目录可以对应多个 `.apk`**（`iputils-20250605-r1.apk` ·
`-r2.apk` · `-r3.apk` —— 它们都是"同一个包、同一个打包目录"的不同 release 产物），
而它：

1. **知道**这件事（`shared` 非空时会打印）；
2. **但没有决定该用哪一个** —— `todo` 是去重后的，所以只处理一个；
3. 而它取的是【排序后第一个】—— 字符串排序下 `r1 < r2 < r3`，**于是取了最旧的**。

**后果**：**改了配方、升了 release，而线上永远是第一个 release**。而每一处都报了
"成功"——建包成功、打包成功、发布成功。

★ 而它和 §1.5.Bb（`configure` 覆盖默认值）是同一类：**一个看起来对的动作，
静默地没起作用**。而这次的代价更直接：**发布出去的包可能不是刚建的那个**。

**修法候选**（没定）：

- **按包名里的 `version-release` 排序取最新** —— 最正确，而要写一个解析器
- **按 `.apk` 的 mtime 取最新** —— 简单，而同版本重建时也成立
- **让 `var/pkgs/` 里不并存** —— 还原/打包之后清掉同目录的旧 release（而 0020
  有个"软件包的清理策略"，可能该在那里说）

★ 而**它要不要现在就修，取决于 §1.5.B**：`restore.py` 在 `skirt/**` 里，所以
动它会让**所有包**算成 stale → 全量重建。**三条（1.5.B · 1.5.Bb · 1.5.Bc）
该一起做。**

★ 而在那之前，有个**便宜的验证**：`skirt restore` 之后看 `var/output/` 里那个包
的 `.buildkey` 和配方算出来的是不是同一个。不一样就说明踩了这个坑。

### 1.5.Be ★★★ 一次误报三个"事故" —— 而根因是一句 `head -1`

**2026-10-17。这一条记的不是代码，是验证方法。**

当时从这行命令读"线上是什么版本"：

```bash
apk adbdump x.adb | grep -A2 "^  - name: iputils$" | head -1 | grep version
```

`head -1` 让它**只显示第一条**。而索引里 `iputils` 有**三条**（r1 · r2 · r3）——
它显示的是 r1。

从那个观察出发，我连着给出三个诊断，每一个都"有证据"：

| 次 | 诊断 | 真相 |
|---|---|---|
| 1 | 「我忘了升 release」 | 配方早就升过（r3 / r2 / r2） |
| 2 | 「`deploy` 按不可变性拒了同名覆盖」 | deploy 没拒，r3 的边车明明白白传上去了 |
| 3 | 「`apk mkndx` 留了最旧的那条，该在 `stage` 里只留版本最大的」 | 索引里三条都在 |

而第三次我**真的动了代码** —— 在 `stage()` 里加"同名只留最新"。两条现有的
测试立刻挂了，而它们守的都是真的东西：

    test_仓库里已有的包不会被删       → 「仓库是【只增不减】的」（0013 那条原则）
    test_索引里列出全部包_版本对得上   → hello 1.0-r0 和 1.1-r0 【能同时在索引里】

**索引的键是 `(name, version)`，不是 `name`。** 而那两个测试比我更清楚这件事。
改动已回退（`git checkout -- skirt/skirtlib/repo.py`），359 条测试全过。

★ 而真正的答案是：**那三处修改全都上线了，缺口二不存在。**

## 它和这个项目一直在修的那类，是同一个形状

    「一个该说话的地方没说话」

`head -1` 就是个沉默的地方 —— 它把「还有两条」藏起来了。而 `grep -c` 会说
「3 次」，`grep -A2 ... | head -1` 只会说「r1」。**后者看起来像个答案。**

## 所以验证的时候

| 做法 | 为什么 |
|---|---|
| 先问「这里有没有可能有多条」 | 索引、列表、版本、候选 —— 这些天然是多条的 |
| 用 `grep -c` 数一遍，再决定取哪条 | 一个数字就能拆穿这个错觉 |

### 1.5.Bd 增量构建真正的两块缺口 —— 2026-10-17 全量重建验出来的

**怎么验出来的**：1.5.B 那条待办写着「修法：在 `skirt bootstrap` 之前加一次
`skirt restore --arch <架构>`。代价只是'先拉一遍仓库'（几十 MB）」。照着做了，
派了一轮全量（`38992917166`）。它跑了 2 小时 4 分、全程 success，而结果：

| 判据 | 期望 | 实际 |
|---|---|---|
| `restore` 生效 | 建包那步说「跳过 N 个」 | 90 个包**全都重建** |
| 旧 release 不再取错 | 线上 iputils 变 r3 | 还是 r1 |
| prefix 修好 | 线上 iputils 装在 `usr/bin` | 还是 `usr/local/bin` |

而那轮日志里有一行直接说了原因：

```
没有 /home/runner/work/packages/packages/var/pkgs/x86_64，没什么可还原的
```

#### 缺口一：「从线上拉 `.apk`」那一步根本不存在

`skirt restore` 只做「把**本地**的 `.apk` 解成 payload」。

| 命令 | 方向 |
|---|---|
| `skirt pack` | payload → .apk |
| `skirt repo` | var/pkgs → 本地仓库目录（建索引） |
| `skirt deploy` | 本地仓库目录 → 线上（**上传**） |
| `skirt restore` | **本地** .apk → payload |

**没有一个是「线上 → 本地」**。所以 runner 每轮干净，`var/pkgs` 空，每个包都判成
「该重建」——**增量从来没有成立过，而它不是因为少调了 `restore`，是因为那条路
压根没铺**。

修法：加一个「下载」的动作（新命令 `skirt fetch`，或者给 `restore` 加
`--from <url>`）。它要用 S3 那四个 secret（`workflow` 里已有）。

★ 而 1.5.B 那条待办的措辞要改：它写的是「代价只是先拉一遍仓库」，
**而那个动作它没有算进修法里**，把它当成了 `restore` 会做的事。**一个漏掉的
步骤，写在「代价」那一栏里，看起来就像已经做了。**

#### 缺口二：工具链变了，而产出同名 —— 建了也发不出去

`build_key` 把 `skirt/**` 算进 `tooling_hash()`，所以这次三条修改让**全部 90 个
包**都算成 stale → 全量重建。而重建产出的 `.apk` 和线上**同名**（名字由配方的
`version-release` 决定，而配方一个字没改）→ `deploy` 按 0013 的**不可变性拒了
覆盖** → **新内容在 CI 里建出来了，而线上还是旧的。**

★「工具链变了产物可能变，该重新发」和「线上交付物不可变」**两条都对**，
而它们冲突时没有规则。

候选：

| 方案 | 做法 | 代价 |
|---|---|---|
| 让 `tooling_hash` 影响版本号 | 工具链变了，`.apk` 名字就不同 | 要改命名规则；每次改 `skirt` 都换一批名字 |
| `deploy` 加「允许覆盖」的开关 | 而判据只能是「内容变了」 | 削弱 0013 |
| 比**内容**而不是比**名字** | 内容变了就覆盖 | 要重写 0013 那条的定义 |
| 接受它：工具链变更时手动升一批 release | 简单 | 90 个包手工升，而且每次改 `skirt` 都重来 |

★ 而**在那之前**：任何只改 `skirt/**` 的修复，**重建了也发不出去**。
这一条不解决，「修好」和「上线」是两件事，而看起来像一件。

### 1.5.Bf ★★★ 既是"构建工具"又要"交付"的包，永远不会被重建

**2026-10-18 查到底的一个结构性问题。**

#### 现象

`python3` 连续四轮失败：

    [ERROR] readline failed to import: /usr/lib/libreadline.so.8:
            undefined symbol: UP

而 `readline` 的 `build` 依赖补了 `ncurses` 之后**还是失败** —— 因为
**`readline` 那一轮根本没被建**：`var/logs/` 里 68 份日志没有它，
建包那步 59 行进度里也没有它。

#### 根因：`SKIRT_PROVIDES` 会把包从构建顺序里「断环」

`bootstrap.yml` 现在（正确地从 `devel.toml` 算闭包）传下 `SKIRT_PROVIDES`，
而那是 `devel` 闭包的**全部 62 个包**。驱动对这份名单做的事是：

    [断环] 这些包由构建环境提供，指向它们的 490 条依赖边被断掉：

于是名单里的包**不进构建顺序、永远不重建**。而 `readline` 在名单里——因为
bash 要它，而我们在同一天把它加进了 `devel.toml`。

**所以 `sysroot` 里那份 `libreadline.so.8` 永远是镜像里那份旧的**（缺 ncurses
链接），而 `python3` 链接它、失败。

#### 而这是结构性的，不只是 readline

    `SKIRT_PROVIDES` 的语义 = "构建环境提供这些，所以不用建"

★ 对【纯构建工具】（autoconf · make · cmake · binutils …）—— **那是对的**，
  它们不需要重建。

★ 对【既要进构建环境、又要交付给用户】的包（`readline` · `ncurses` ·
  `openssl` · `zlib` …）—— **那是错的**。它们被"环境提供"之后，就再也
  不会跟着配方更新，而**最终系统里装的是那个永远不更新的版本**。

★ 而今晚的五次"隐含依赖"里，有三次的根子就在这儿：我们把包加进 devel
  （让构建环境够用），而加进去就冻住了它的版本。

#### ✅ 已修（2026-10-20）—— 把两件事分开

`SKIRT_PROVIDES` 现在**只管断环**；新增的 `SKIRT_REBUILD` 管「哪些"环境有"
的包也要建」。

#### ★★★ 而上面那句「不进构建顺序、永远不重建」是**错的** —— 2026-10-20 更正

做顺序对照时量出来的（同一份 `PROVIDES`，有 / 没有 `REBUILD`）：

| | 成员 | `readline` 位置 | `python3` 位置 |
|---|---|---|---|
| 只有 `PROVIDES`（旧） | **90 个** | 69 | **68** |
| 加 `REBUILD`（新） | **90 个** | **64** | **79** |

**成员一样。** 所以"断环"**不排除任何包**，它只**断边**：

* `readline` 一直在顺序里（第 69 位），所以它**会被建**
* 而真正的问题是 **`python3`（68）排在它【前面】**

为什么：`python3` 的依赖里没写 `readline`（那时确实没写），于是两者之间
**没有边** —— 而没有边的时候 `_topo_sort` 用**字母序兜底**，`p` < `r`，
于是 `python3` 先建、捡到镜像里那份旧的 `libreadline.so.8`。

★★ **所以那个 bug 的真正名字不是"不重建"，是"排错位置"。** 而 `REBUILD` 的
效用也不是"让它重建"，是**让边回来**（有了边，`readline` 就排到 `python3`
前面）。

★ 而这也解释了另一件事：那轮 `var/logs` 里没有 `readline` 的日志，不是因为它
"被跳过"，而是因为**那轮停在第 68 个（`python3`）—— 而 `readline` 是第 69**。
**我把"还没轮到"读成了"被跳过"。**

---

而它同样是**算**出来的（CI 里）：

    devel 闭包  ∩  base+minimal 闭包  =  49 个"也要交付"的包

实测（`--arch x86_64`，`SKIRT_PROVIDES` 是完整 62 个闭包）：

| | `python3` | `readline` | `ncurses` | 报环? |
|---|---|---|---|---|
| 只有 `SKIRT_PROVIDES`（旧） | 68 | **69** | 不在顺序里 | 否 |
| 加 `SKIRT_REBUILD`（新） | **89** | **67** | **56** | 否 |

★★ **而环没有回来**，因为 `make` 不在那份交集里（base/minimal 都没有它 ——
用户装不到一个构建工具）。`make → glibc → python3 → zlib → make` 依然断在
`make` 上。**而那不是我挑的，是算出来的。**

★ 而那个「算」第一次被我做错了：直接从 `SKIRT_PROVIDES` 里减掉交集，于是把
断环也拿掉了 —— CI 报「依赖成环」。那条路现在记在下面，留作记录。

#### ★★★ 第一版修法【试过，回退了】—— 2026-10-20

从 `SKIRT_PROVIDES` 里减掉 `base`+`minimal` 的闭包（"纯构建工具"= 差集）。
本地跑那一步是对的（闭包 62 → 29、`readline` 排掉了），而 CI 一跑到
`skirt bootstrap` 就报：

```
skirt: 错误 依赖成环，排不出构建顺序：
  make → glibc → python3 → zlib → make
```

**原因是 `host_provides` 一个集合干了两件事**（`order.py:58`）：

| 它做的 | 该不该改 |
|---|---|
| ① 把指向这个包的依赖边【断掉】—— **那是解决依赖环的机制** | **不该**。那个环是真的：make 要 glibc，glibc 要 python3，python3 要 zlib，zlib 要 make |
| ② 同时让它【不进构建顺序、永远不重建】 | **该改** |

我只该改 ②，而把 ① 也拿掉了 —— 环就露出来了。而它一直存在，只是被 ① 遮着。

★ 而"一个机制两个意思"是这个项目这几天第三次撞见的同一个形状
（前两次：一个变量表达两件事、一句 `head -1` 藏掉另外两条）。

**所以正确的修法要把 ① 和 ② 分开** —— 而它要改 `skirt/`（`order.py` +
`deps.py`），改它会让全部包 stale。**它该和下面的 B2/B3 一起做，不该在
workflow 里绕。**

#### 候选修法（没定）

| 方案 | 做法 | 问题 |
|---|---|---|
| 每个包显式标注 | 配方里加一个"这个包要交付"的记号 | 要和 0022 那个 `vendor` 一起想 |
| 从风味反查 | **构建时不"断环"那些【也在 base/minimal 里】的包** | ★ 最接近"对的判据"：**它最终要进系统，所以它必须跟着配方走** |
| 分两份名单 | `SKIRT_PROVIDES` 只放纯工具；要交付的包不在里面 | 要决定"谁算纯工具"，而那正是上面那条 |
| 让 `skirt build` 强制重建 | 环境里有旧版也重建 | 治标；而它会让每个包都重来 |

★ 而第二种的判据最干净：**"这个包最终要进用户的系统吗"** —— 那和今天讨论的
  「系统 vs 应用」是同一个问题的两半。

★ 而在那之前，有个便宜的验证：`skirt order` 输出里，**`devel` 闭包中的包
  是哪些**、而它们里有几个同时出现在 `base`/`minimal` 里。

### 1.5.Bg 三个方向的依赖检查，而只做了两个

**2026-10-20 做了一次线上仓库的审计**（读 `APKINDEX`，对每个包比 depends 和
provides），结果：**123 条 · 没人提供的依赖 0 种** —— 仓库是自洽的。

★ 而那次审计【抓不到】readline 那个 bug。原因是"依赖对不对"有三个方向，而
我们只覆盖了两个：

| # | 方向 | 谁在查 | 现状 |
|---|---|---|---|
| 1 | 声明了而【没人提供】 | 上面那次审计（手工，一次性） | ✓ 0 个 |
| 2 | 链了而【没声明】 | `pack.elf_fields` 从 NEEDED 自动补 depends | ✓ 自动 |
| 3 | **该链而【没链】** | **没人查** | ✗ ← readline 那个 |

而 3 是 readline 那次病的地方：`libreadline.so.8` 里对 `UP` 有符号引用，而
它【没有 NEEDED 指向 libncursesw】。于是：

* 方向 2 看不见它（没有 NEEDED，就没有可补的依赖）
* 方向 1 也看不见它（它没声明，所以"没人提供"无从谈起）

**它只在下游炸出来** —— 而这次隔了五轮 CI、两次误诊。

#### 方向 3 能怎么做

★ **对"链接器该链什么"这件事，最便宜的判据是【和上游发行版对照】**：

    拿同一个包在 Alpine（或 Debian）里的 NEEDED 列表，
    和我们的比 —— 少了什么就是"该链而没链"。

而它有前提：那个包在那边也有。而 readline / ncurses / openssl 这些都有。

★★ 而【更根本】的那条：**一个 .so 里有未定义符号、而它 NEEDED 里没有任何
提供那个符号的库** —— 这个能完全自动：

    对 payload 里每个 .so：
      未定义符号集合（nm -D --undefined-only）
      减去 已 NEEDED 的库里能提供的符号
      减去 主程序/自身定义 + glibc 提供的那批
      = 剩下的是"要么由没人 NEEDED 的库提供，要么真缺失"

  实测这条对 readline 会报出 `UP`（而 libncursesw 不在 NEEDED 里，所以它
  不在这条 .so 的"已满足"集合里）。

  ★ 而它有噪声：`dlopen` 那类符号（`nss` 系列）本来就不在 NEEDED 里。
    所以它该【报告】而不该失败 —— 和 `vendor_risky_needs` 一个规格。

#### ✅ 而它有一行命令的实现，2026-10-20 实测过了

不用 `nm` 减法 —— **`ldd -r` 就是那个检查**（`-r` 是 "report unresolved
symbols"）。实测：装好的 `minimal` 系统（65 包、1315 个 ELF）里跑一遍：

    1315 个 ELF · 41 个报「未解析」· **而真的只有一个**

| 报的 | 数量 | 真的吗 |
|---|---|---|
| `/usr/lib/libreadline.so.8.3` —— `UP` `PC` `BC` `tputs` `tgoto` `tgetent` `tgetnum` `tgetstr` | 1 | **真**（9 个符号全是 termcap 那一层，而 NEEDED 只有 libc + ld-linux） |
| `/usr/lib/bash/*` —— `loptend` `builtin_error` `list_optarg` … | 40 | **假**。loadable builtin，符号由【宿主 bash】注入，而 `ldd -r` 看不到宿主。实测 `enable -f /usr/lib/bash/{print,head,stat,uname}` 全部加载成功 |
| `/usr/lib/libthread_db.so.1` —— `ps_pdwrite` `ps_pglobal_lookup` … | 1 | **假**。gdb 的钩子，符号由 gdb 注入 |

★★ **所以判据是**：`ldd -r` 的输出【减去】两张白名单（`/usr/lib/bash/*` 和
`libthread_db.so.*`），剩下的任何一条都是真的。

★ 而它好在**一眼看得出层次**：readline 报的不是一个符号，是【termcap 那一层
全缺】。那比任何一句解释都清楚。

★ 而它该跑在哪：**装好的系统里**（`minimal` 就够），所以和 5.12.3 那个自检
是同一个地方、同一份容器。

#### 而三个方向的优先级

★★ 方向 3 这个检查【比方向 1 更值钱】—— 方向 1（声明了而没人提供）现在是
0 个，那是因为 `elf_fields` 会自动从 NEEDED 补；而 NEEDED 本身是错的（方向 3）
的时候，方向 1 和 2 都看得见"一切正常"。**readline 那次就是这样。**

### 1.5.C 包分类

`section` 现在有雏形（`base` `libs` `devel` `core` `utils` `localization`），但它说的是
**「在系统的哪个位置」**。要补的是**「它是什么」**：

```toml
kind = "lib"    # 纯依赖库：zlib、libffi、gmp、mpfr
kind = "tool"   # 工具：make、bison、patch、tar
kind = "lang"   # 编程语言：python3、perl
kind = "data"   # 数据：filesystem、时区、证书
```

**用途**（不是装饰，得有具体用处）：

1. **风味组成** —— `minimal` 要工具不要语言；`devel` 要语言因为构建要用
2. **防住 bison/python3 那类 bug** —— 能问「所有 `kind = "lang"` 都在 devel 里了吗」

## 工作分工：只在 CI 构建（2026-10-15 更正）

> ★ **这一节的结论改过。** 2026-10-10 写的时候是「CI 做全量，**本地做单包**」，
> 而那个分工后来被推翻了 —— 现在的约定是 **本地不构建任何东西**，见
> `docs/约定/构建在哪里跑.md`。下面那些实测数据仍然有效（它们记的是两个环境
> 的真实差异），但"所以"那一段已经重写。

**决定：所有构建都在 CI，基准是 x86_64。**

理由不是"CI 一定快"，是**分工**——两边强弱互补：

| | CI | 本地 |
|---|---|---|
| 全量引导（当时 41 个包；2026-10-15 已经 87 个）| **原生 Linux + NVMe，快 2-3 倍** ✓ | 穿过 macOS → 虚拟机 → 虚拟磁盘 ✗ |
| 两个架构 | **并行** ✓ | 只有一个宿主架构 ✗ |
| 环境 | **每次都干净** ✓ | 会被残留骗 ✗（实测两次，而那份源码缓存已于 2026-10-15 移除）|
| 占本机 | **不占** ✓ | 占 ✗ |
| 单个包 | 一轮 25 分钟起 ✗ | **5～60 秒** ✓ |
| 看日志 | 要等 job 结束 ✗ | **立刻** ✓ |
| 进去翻 | 不行 ✗ | **可以** ✓ |

**实测数据**（同一份配方）：

```
               CI        本地
m4           0:47      0:38      ← 小包本地反而快（本机 6 核，CI 4 核）
cmake        8:33     23:02      ← 大包 CI 快 2.7 倍（I/O 密集）
gettext      5:25      8:38
```

**所以**（2026-10-15 更正）：

- **全量验证 · 两个架构 · 发布** → CI
- **改一个配方后验那个包** → **也是 CI**。原来这里写的是"本地，只跑那一个包"，
  而那条路已经废掉了：本地构建和 CI 构建是两条会分叉的路径，而只有 CI 那条算数
  （见 `构建在哪里跑.md` 的第②条理由）。
- **那本地还剩什么用** —— 就是你现在正在做的这一类：读代码、看文档、跑单元测试
  （`python3 -m unittest discover -s skirt/tests`）、改配方。**这些不需要构建。**

**"环境干净"是 CI 的一个额外好处，值得单独记**：这一路被脏缓存坑了好几次
（libffi 改了源却仍用旧树、libxcrypt 本地假成功），而 CI 每次都从头来——**它
不会骗人**。

★ 而 2026-10-15 之后这一整类问题可以划掉了：**源码缓存已经移除**
（`0018-源码不缓存`），驱动不再保留任何跨构建的源码状态。所以"libffi 改了源却仍
用旧树"那个形状从结构上不可能了。

★ 而"本地假成功"（环境不干净）那一类**还在** —— 它和缓存不是一回事：那是构建
环境里的残留，清缓存治不了它。只在 CI 上不存在，因为 CI 每次是全新机器。

**x86_64 为基准**的含义：先修到 x86_64 绿。它的生态位更重要（服务器、大多数
CI），而且**当时**它是一次都没碰过的那个——现在两个架构的全量引导都绿了。
aarch64 照跑不误——并行，不额外花钱。

### 5.5 实际做出来和原计划有两处不同（外加顺带补的四个包）

**① 用 defconfig + 片段，不是手写最小配置。**

原计划写的是「config：virtio/串口/NVMe 内建」。实际是先 `make defconfig`
再合并一份只写我们在乎那几项的片段（串口、virtio、initramfs、devtmpfs），
最后 `olddefconfig`。

理由是取舍：defconfig 是**已知能启动**的，而手写最小配置的失败模式是
「能启动但少个驱动」——那比编得慢难查得多。代价是第一次编了 **47 分钟**
（它把 nouveau、iwlwifi、mediatek 的 codec 全带上了，和 QEMU 虚拟机毫无
关系）。**配置瘦身留到能开机之后**，因为那时候才知道哪些真的不需要。

（第二次编只用了 4 分 31 秒，ccache 把第一次的结果缓存住了。）

**② 走的是 initramfs，不是「不需要 initramfs」。**

原计划想让驱动内建到可以直接挂根文件系统。实际用的是「内核 + initramfs」——
内核把 cpio 解开到内存里的 rootfs，然后 exec /init，不需要分区表、不需要
文件系统驱动、不需要引导器。这是「能开机」最短的一条路。

两者不冲突：`CONFIG_BLK_DEV_INITRD=y` 和 `CONFIG_DEVTMPFS_MOUNT=y` 都开着，
将来要做磁盘镜像时另一条路也走得通。

**③ 顺带补的四个包**：`flex`、`bc`、`openssl`、`cpio`。前三个是内核自己
报出来的（见各自配方的注释），`cpio` 是打 initramfs 要的。
