### ★ 自举抓到的六个依赖 —— 这个方法论值得记住

按**命令**查「自举缺什么」得到的是**错的答案**。我最初得出"只缺 setpriv 和 patch

| 缺的 | 怎么暴露的 |
|---|---|
| `patch` · `util-linux`（setpriv） | `command not found` |

**两类依赖性质完全不同**，详见 `docs/配方约定.md` 的「依赖」一节：

```

configure 会【检查】的程序 → 平时不出现在命令行里，只能撞
```

### 1.5.C 包分类

`section` 现在有雏形（`base` `libs` `devel` `core` `utils` `localization`），但它说的是
**「在系统的哪个位置」**。要补的是**「它是什么」**：

```toml
kind = "lib"    # 纯依赖库：zlib、libffi、gmp、mpfr
kind = "tool"   # 工具：make、bison、patch、tar
kind = "lang"   # 编程语言：python3、perl
kind = "data"   # 数据：filesystem、时区、证书
```

**用途**（不是装饰，得有具体用处）：

1. **风味组成** —— `minimal` 要工具不要语言；`base-devel` 要语言因为构建要用
2. **防住 bison/python3 那类 bug** —— 能问「所有 `kind = "lang"` 都在 base-devel 里了吗」

## 工作分工：CI 做全量，本地做单包（2026-10-10 定）

**决定：全量验证以 CI 为主，基准是 x86_64。**

理由不是"CI 一定快"，是**分工**——两边强弱互补：

| | CI | 本地 |
|---|---|---|
| 全量引导（41 个包）| **原生 Linux + NVMe，快 2-3 倍** ✓ | 穿过 macOS → 虚拟机 → 虚拟磁盘 ✗ |
| 两个架构 | **并行** ✓ | 只有一个宿主架构 ✗ |
| 环境 | **每次都干净** ✓ | 会被脏缓存骗 ✗（实测两次）|
| 占本机 | **不占** ✓ | 占 ✗ |
| 单个包 | 一轮 25 分钟起 ✗ | **5～60 秒** ✓ |
| 看日志 | 要等 job 结束 ✗ | **立刻** ✓ |
| 进去翻 | 不行 ✗ | **可以** ✓ |

**实测数据**（同一份配方）：

```
               CI        本地
m4           0:47      0:38      ← 小包本地反而快（本机 6 核，CI 4 核）
cmake        8:33     23:02      ← 大包 CI 快 2.7 倍（I/O 密集）
gettext      5:25      8:38
```

**所以**：

- **全量验证 · 两个架构 · 发布** → CI ✓
- **改一个配方后验那个包** → 本地 ✓（**只跑那一个包**，别跑全量 ✗）

**"环境干净"是 CI 的一个额外好处，值得单独记**：这一路被脏缓存坑了好几次
（libffi 改了源却仍用旧树、libxcrypt 本地假成功），而 CI 每次都从头来——**它
不会骗人**。这也意味着 1.5.9 那个缓存问题在 CI 上不存在，只在本地存在。

**x86_64 为基准**的含义：先修到 x86_64 绿。它的生态位更重要（服务器、大多数
CI），而且它是我们一次都没碰过的那个。aarch64 照跑不误——并行，不额外花钱。

## 2. multi-arch ← **发布 base 之前必须做**

**现状：我们一次都没碰过 x86_64。** 所有产物、所有验证、所有数字都是 aarch64 的。

**核心洞察：不需要交叉编译，需要多平台容器。** 已验证 `docker run --platform
linux/amd64` 在这台 Mac 上能跑（走 Rosetta），CI 上有原生 amd64 runner。

### 审计过了：配方这边基本是干净的

| 查什么 | 结果 |
|---|---|
| 配方里写死 `aarch64` 的 | **没有** ✓ |
| 用 `--host` / `--build` / `--target` 的 | **没有** ✓ |
| glibc 的动态链接器路径 | **只在注释里** ✓ 代码靠 usr-merge 符号链接，架构无关 ✓ |
| gcc 把目标库装进 `/usr/lib64` | **有条件的** ✓ x86_64 上不触发 ✓ |
| 加固参数 | 驱动里已经按架构分支 ✓（`-mbranch-protection` / `-fcf-protection`）|
| buildenv 镜像 | **已经按架构打标签**（`:aarch64`）✓ CI 建 `:x86_64` 就行 ✓ |

**唯一要验的配方相关项**：`gzip` 的补丁是为 AArch64 写的（`head` 宏和内核头
里的字段撞名）。在 x86_64 上它大概率**无害**（只是改个宏名），但要实测。

## 未声明 `gawk` 依赖（25 个包）

**现象**：审计发现 25 个包的构建会调用 awk，但配方的 `build` 里没有 `gawk`：

```
autoconf automake binutils gcc gettext libtool m4 make texinfo
expat gmp libcap-ng libpng libxcrypt mpc mpfr
diffutils findutils gawk grep gzip patch rsync tar xz
```

**为什么不阻塞**：第一遍的 Debian 构建环境装了 gawk；自举时 base-devel 镜像里
也有（第一遍建出来的）。所以它一直是"恰好能跑"，而不是"按配方能跑"。

**为什么不能无脑加**：

1. **`gawk` 自己也在列表里** —— 声明它会自环。
2. **会打乱构建顺序**：给 `m4`（现在的第 1 位）声明 gawk，gawk 就得排到它
   前面；而 gawk 要 `make`、`gettext`。这条链会连锁移动一大片。
3. **审计本身很粗**：只是 grep 了 `Makefile.in` 里有没有 `awk` / `$(AWK)`。
   很多包只是在可选分支或 fallback 里用，并不是真的需要它。

**该怎么做**：不能只看 Makefile，要看**实际构建日志里有没有 awk 的调用**
（`build-logs/` 现在每个包都有完整输出，grep 一下就知道谁真的用了）。
确认真用的，再逐个评估声明后的顺序影响。

**发现经过**：查 libpng 为什么调用 gawk 时顺手审计出来的。当时正在等一轮
CI，不适合做这种会动构建顺序的改动。

## 12 条未声明的运行时依赖

用 `readelf -d` 把每个包 payload 里所有 ELF 的 `NEEDED` 抽出来，和它声明的
`runtime` 对比，得到 12 条对不上的：

```
bison       → libtextstyle.so.0   (gettext)
coreutils   → libgmp.so.10        (gmp)
gawk        → libgmp.so.10        (gmp)
gawk        → libmpfr.so.6        (mpfr)      ← 已用 --without-mpfr 解决
gcc         → libzstd.so.1        (zstd)
gettext     → libgomp.so.1        (gcc)
python3     → liblzma.so.5        (xz)
python3     → libuuid.so.1        (util-linux)
python3     → libzstd.so.1        (zstd)
util-linux  → libz.so.1           (zlib)
zstd        → liblzma.so.5        (xz)
zstd        → libz.so.1           (zlib)
```

**为什么是真问题**：构建时合并进环境的，只有这个包【直接+传递依赖】的闭包。
所以如果 X 链接了 libzstd 却没声明 zstd，那么建一个依赖 X、但不依赖 zstd 的
包时，环境里就没有 libzstd——X 的二进制跑不起来。

**而且它比 `/tmp`、`cc` 那几类更隐蔽**：构建能过，运行时才炸。

**为什么不能无脑加**：会成环。比如 `gcc → zstd`（运行时）而 `zstd` 的
`build` 里有 `gcc`——驱动的排序两条边都看，于是转不起来。

**该怎么做**：这类环要靠"运行时依赖不参与排序"或者"声明成可选依赖"来解，
需要先想清楚策略，再逐条加。**不是加几行了事。**

**发现方法**（可复用）：

```sh
# 在一个装了这些 payload 的容器里
for d in */payload; do
  pkg=${d%%/*}
  find "$d" -type f -perm -u+x | while read f; do
    readelf -d "$f" | sed -n 's/.*NEEDED.*\[\(.*\)\]/\1/p' | while read n; do
      echo "$pkg|$n"
    done
  done
done | sort -u
```

再拿 soname 反查提供者，和配方里声明的 `runtime` 比。

## 补记：为什么"加 runtime 依赖"会成环

确认过驱动的排序逻辑：

```python
# order.py
for dep in direct_deps(spec, arch, kinds=("runtime", "build")):
```

**运行时依赖确实参与排序**——这是对的，因为建一个包时要把它的
runtime+build 闭包合并进容器，所以那些都得先建好。

于是 `gcc → zstd`（运行时）和 `zstd build → gcc` 构成真环：

    建 zstd:  需要 gcc（因为 gcc 运行时需要 libzstd）
    建 gcc:   需要 zstd 已经建好（才能链上 libzstd）

### 它和 gawk/mpfr 是同一个形状

| | 真的需要那个库吗 | 解法 |
| --- | --- | --- |
| gawk / mpfr | 不需要 | `--without-mpfr` 关掉探测 |
| gcc / zstd | 有用 | 关掉是损失，需要分阶段方案 |

**两者都是"autoconf 自动探测到了一个可选库"**，但一个能关、一个不该关。

### 该怎么解

真·分阶段：先建一个不链 zstd 的 gcc，用它建出 zstd，再重建一个链 zstd 的
gcc。这也是各大发行版处理 gcc 自举的标准做法，但那意味着构建顺序里 gcc
出现两次——驱动目前的结构支持不了。

**所以先记着，别急着改。** 这 12 条是潜在问题（构建能过、运行时才炸），
不是当前的拦路石。

## 系统里下不了东西：没有 curl/wget，而 python3 不带 ssl

拿刚发布的 `base-devel` 做实测时发现的：

```
$ command -v curl wget
（都没有）

$ python3 -c "import urllib.request; urllib.request.urlopen('https://…')"
URLError: <urlopen error unknown url type: https>
```

**python3 的 https 用不了**——因为我们是个精简系统，没打 openssl，
标准库里的 `ssl` 模块就没编出来。

### 后果

**在一个刚拉下来的 base-devel 里，没有任何办法从网上取东西。** 实测建 Lua
的时候，tarball 是从宿主机挂进去的。

### 要怎么修

两条路，可以都走：

1. **加 openssl**（或者 gnutls / libressl）——python3 的 ssl 模块就有了，
   https 也就通了。这也是很多别的东西的前提（git、pip…）。
2. **加 curl 或 wget**——一个简单的下载工具，比"用 python3 下载"直观得多。

**openssl 更根本**：它不只是让 python3 能 https，还是整条信任链的基础
（包签名、TLS 客户端）。但它是这两个里更大的一个包。

### 顺带

这次也验证了系统的**能力边界**：建东西（编译、链接、跑）完全没问题，
**取东西**不行。这两件事的依赖是不同的。
