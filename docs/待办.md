## 2. multi-arch ← **发布 base 之前必须做**

理由：容器宿主里 x86_64 是压倒性多数。**只有 aarch64 的 `base` 发出去等于白发。**

**核心洞察：不需要交叉编译，需要多平台容器。** 已验证 `docker run --platform linux/amd64` 在这台 Mac 上能跑（走 Rosetta）。

| # | 做什么 | 说明 |
|---|---|---|
| 2.1 | `resolve_arch` 去掉「不支持交叉构建」的限制 | 那句话把问题想复杂了——我们不是换工具链，是换容器 |
| 2.2 | `run_in_container` 加 `--platform linux/<arch>` | |
| 2.3 | buildenv 镜像按架构构建 | |
| 2.4 | **架构相关的配方** | glibc 的 `-Wl,-dynamic-linker=/lib/ld-linux-aarch64.so.1` 写死在 steps.sh 里 ✗ x86_64 是 `/lib64/ld-linux-x86-64.so.2`；gcc 的 `-latomic_asneeded` 补救可能也是 aarch64 专有；gzip 的补丁要验 |
| 2.5 | CI 矩阵：`ubuntu-26.04-arm` + **`ubuntu-26.04`** | 不用 `ubuntu-latest`（移动别名，构建环境会静默变化）。两边都是原生，都不模拟，都免费 |
| 2.6 | 合成多架构清单 | 这正是 0003 说的「用户写 `FROM yojigenos/base`，Docker 按平台自动选」 |

**策略**：本地只建 aarch64（快），**x86_64 交给 CI**。但保留本地能建的能力——调试 x86_64 专有问题时会用到。

## 6. 更远

| # | 做什么 |
|---|---|
| 6.1 | **源码镜像** — 结构上必需：sha256 钉死意味着上游消失配方就永久死了。方案：`urls = [...]` 列表逐个试、逐个校验；托管在 GitHub Releases 或 Cloudflare R2 |
| 6.2 | **包签名与信任链** — `apk` 验证包签名（RSA）。**不急**：容器镜像不需要我们自己签（Docker Hub 本来就不签），而新密钥可以通过一次普通的包更新装进用户系统。真正的约束只是「别把旧密钥弄丢」。等做软件源时再定 |
| 6.3 | **许可证** — 仓库里**只有 README，没有 LICENSE** ✗ 想要别人用和贡献，这是第一道门 |
| 6.4 | **发行版代号** — 三个方向待选（动漫角色 / 日本神话 / 原创），见 0009 |
| 6.5 | **CVE / 安全更新流程** — 发行版的成年礼，会影响仓库和版本设计 |
| 6.6 | **glibc 自己的消息翻译** — `glibc → gettext → glibc` 是真环，要开得先设计两轮自举 |
| 6.7 | **gcc / binutils / make 的 NLS** — 它们排在 gettext 之前构建，要解决顺序问题 |

| 6.9 | **`objcopy --enable-deterministic-archives` 兜底** — 我们自己 strip `.a`，要确认没把它们变回不确定 |
| 6.10 | **`LINGUAS` 优化** — 只装 zh_CN / zh_TW 的翻译，其余语言不装。**能显著减小体积，但有些包会因此构建失败**（已知问题），所以留到以后 |
