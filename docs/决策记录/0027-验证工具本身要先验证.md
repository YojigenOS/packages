# 0027 验证工具本身要先验证

**2026-10-26 记。** 这一条是踩出来的，花掉了一整轮。

## 发生了什么

为了给 `parted` 解开 `tgetent` 找不到的问题，我在 TX 上跑了一串检查：

```sh
nm -D /usr/lib/libtinfow.so.6.4 | grep tgetent     → 空
strings /usr/lib/libtinfow.so.6.4 | grep tgetent   → 空
readelf -sW ... | grep tgetent                     → 空
```

结论：**"库里没有 tgetent"**。

于是改 ncurses 的 configure，一共改了三次：

```
① --with-termlib      生成独立 libtinfo
② 不带 w 的软链接      让探测 -ltinfo 的包找得到
③ --enable-sp-funcs   让 tgetent 真的被编进去
```

第三次改完，检查还是"空"。而我停在了那里 —— 直到我试着用一个
*别的* 方式验证时才发现：

```sh
command -v nm strings readelf objdump gcc python3
→ 全都不在
```

**TX 是纯运行系统，没有 binutils、没有 gcc、没有 python3。**

那些"空"不是"符号不存在"，是**命令不存在**：

```sh
$ nm -D file | grep tgetent
sh: nm: not found          ← 这一行被 2>/dev/null 吞掉了
→ 空
```

同理，那些链接测试 —— `gcc t.c -ltinfo && echo ✓ || echo ✗` ——
因为 `gcc` 不在，**永远输出 ✗**。所以"`-ltinfo` 链不上"也是假的。

## 而真实的证据一直都在

```sh
grep -c tgetent /usr/lib/libtinfow.so.6.4
→ 2
```

`grep` 在 TX 上有（它在 `busybox`/`grep` 包里），而它找到 2 处 `tgetent`
—— 那正是 `.dynstr` 里的符号名。

**库一直是对的。**

## 判据

### ① 验证之前，先确认验证工具在

```sh
command -v nm >/dev/null || { echo "nm 不在，这条检查无意义"; return 1; }
```

★ 而 `2>/dev/null` 是这里最危险的东西 —— 它把 `command not found`
  和「真的没有输出」变成了同一个现象。

### ② 检查要有阳性对照

一条"找不到 X"的检查，必须同时能对**某个一定存在的 Y** 说"找到了"。

```sh
nm -D lib | grep tgetent     # 空的
nm -D lib | grep setupterm   # 也空 ← 这时该怀疑工具，不是怀疑 X
```

★★ 我做过这个对照（"已知一定存在的符号"那一步），但**对照也用了同一个
  不存在的工具**，所以两个都是空 —— 而我读成了"两个符号都没有"。
  **对照必须换一条不同的路径**（这次改用 `grep -c` 直接搜二进制）。

### ③ 最终判据是「它能用吗」，不是「符号在不在」

`parted` 的 `configure` 会真的去链接。**那才是判据。**
`nm`/`strings` 只是更快的近似 —— 而近似在某些机器上根本不可用。

## 这不只是"装个 binutils"

TX 上不装 binutils 是**对的** —— 一台服务器不需要编译器。
错的是**我用需要编译器的检查去验一台没有编译器的机器**，
并且把"检查跑不起来"读成了"检查结论是否定的"。

★ 而这一类失败在 0025 那条「判据要站在离成因最近的地方」里其实已经写过
  一次了 —— 那一次的错误是"看别人的文档说装了什么"，这一次是
  "用一个没跑起来的工具说没有什么"。
  **两次都是"把间接证据当成事实"，而中间那一步没验。**
