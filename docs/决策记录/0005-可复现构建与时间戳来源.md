# 0005 可复现构建与 SOURCE_DATE_EPOCH

> 注（2026-10-11 追加）：本文里的 `packages/<包名>/` 后来改成了
> `recipes/<kind>/<包名>/`（目录改名，并且按 kind 分了层）。正文保持原样。

- **日期**：2026-10-10
- **状态**：已决定（验证工具部分待定）
- **影响范围**：所有配方的 `[package] date` 字段、skirt 注入的构建环境变量、
  将来的包格式与验证流程

## 背景

起因是一个查错的弯路：**ccache 被冤枉了。**

加上 ccache 之后，glibc 的冷构建和热构建产出的字节不一致。逐文件比对发现，
1450 个文件里只有 **7 个**不同，而且**全部是 `.a` 静态库**——共享库、可执行
文件、头文件一个不差：

```
usr/lib/libBrokenLocale.a   usr/lib/libc.a      usr/lib/libc_nonshared.a
usr/lib/libg.a              usr/lib/libm-2.44.a  usr/lib/libmvec.a
usr/lib/libresolv.a
```

两个证据指向同一个结论：

```
$ ar tv libc.a        冷构建: 09:12 2026    热构建: 09:13 2026
$ cmp -l libc.a ...   6117 个字节不同，全是 ASCII 数字，落在每个成员头部
```

**根因：`ar` 归档格式里存着每个成员的 mtime**（`struct ar_hdr` 的 `ar_date`
字段）。我们从源码构建 binutils 时没有打开确定性模式，而各发行版都会显式打开。

**这不是一个孤立的小毛病**：同样的源码两次构建产出不同的字节，意味着
「我下载的这个包确实是从这份源码构建出来的」这句话**无法被验证**。更糟的是，
**它会淹没真正的差异**——这次它就让 ccache 背了锅。

## 决定

### 一、`ar` 打开确定性模式

```toml
configure = ["--prefix=/usr", ..., "--enable-deterministic-archives"]
```

时间戳恒为 0，归档只由内容决定。修完之后：

```
不同文件: 0 / 1450        ✅ 冷热构建逐位一致
冷 347 秒 → 热 82 秒       ccache 4.2 倍，且被证明是透明的
```

### 二、时间戳必须写在配方里，不能从 git 推导

`SOURCE_DATE_EPOCH` 的来源是 **`[package] date`**，一个 TOML 原生日期时间：

```toml
[package]
name    = "glibc"
version = "2.44"
release = 1
date    = 2026-10-10T06:57:33Z
```

**一度考虑过从 git 推导**（`git log -1 --format=%ct -- packages/<包名>/`），
但它有一个致命缺陷：

```
改了配方、还没提交  →  git log 看到【上一次】提交的时间  →  本地构建用 T_旧
然后提交            →  git log 看到【这次】提交的时间    →  CI 构建用 T_新  ✗
```

**同一个配方，提交前后产出不同的字节。** 根因是 git 给的是「关于内容的元数据」，
而我们需要的是「内容本身」。

Debian 的 `debian/changelog` 和 Fedora 的 `%changelog` 之所以管用，正是因为它
**是源码的一部分**——改配方和改日期在同一次提交里，提交前后一致。

**约定**：改动配方的任何部分（configure 参数、补丁、依赖）都要更新 `date`
并把 `release` 加一。

### 三、`SOURCE_DATE_EPOCH` 吃整个依赖闭包

```
SOURCE_DATE_EPOCH = max(自己的 date, 所有依赖的 date)
```

**为什么不只看自己**：配方一个字没改、但依赖更新了，产出的字节**确实**会变——
链接进去的库换了。时间戳要是纹丝不动，就会产出「同名、同 mtime、内容不同」的包，
而那正是所有靠 mtime 判断变化的同步与备份工具的杀手。

Debian 到今天还在靠人在 binNMU 时**手工把时间戳加一**来绕开它。让时间戳跟着
依赖走，它就自动对了：

```
glibc  自己 06:57  →  生效 09:14   ← 取自 binutils
gcc    自己 05:13  →  生效 06:07   ← 取自 make
```

闭包里的环（`glibc → make → glibc` 是自举的常态）由 `dep_closure` 处理。

### 四、构建用 UTC，系统用北京时间

**这两个是不同层面的东西，不要混：**

| | 用什么 | 为什么 |
|---|---|---|
| 构建环境 | `TZ=UTC`、`LC_ALL=C.UTF-8` | 让构建可复现——某个工具按本地时区格式化日期时，输出不该随「在哪台机器上构建」而变 |
| 系统默认 | `Asia/Shanghai` | 中文优先——用户 `date` 看到的时间 |

构建时用 UTC **不是「用外国时区」，而是「不引入时区这个概念」**。
`SOURCE_DATE_EPOCH` 本身就是 UTC 秒数，用 UTC 能避免差 8 小时的困惑。

区域用 `C.UTF-8` 而不是 `C`：保持确定性，同时不牺牲 UTF-8 支持——有些包的
自检会因为非 ASCII 字符而失败（Arch 在 `LANG=C` 上踩过这个坑）。

## 后果

**已经拿到**：

- 构建可复现，且能验证发布包确实来自对应源码
- **差异不再被噪声淹没**——这是最实际的好处
- 依赖变化自动传导到下游时间戳，不需要人工记得加一

**代价**：

- 每个配方多一个必须维护的字段；忘记更新会让「改了配方但时间戳没动」
- 依赖链上一个包的日期变化，会推后所有下游——重建范围比直觉大

**还没做**：

- **包格式的 tar 参数**（做包格式时一起）：`--sort=name --mtime=@$SOURCE_DATE_EPOCH
  --owner=0 --group=0 --numeric-owner`，以及 PAX 头的 atime/ctime
- **`objcopy --enable-deterministic-archives` 兜底**：我们自己 strip `.a`，
  需要确认 strip 没有把它们变回不确定（目前实测结果是好的，但没单独验证）
- **验证工具**：`reprotest` 装在构建环境里**帮不上忙**——它靠 `LD_PRELOAD`
  施加变化，作用不到 docker 容器内部；而它本身又跑不了 macOS。
  目前真正有效的验证是「同一配方跑两次再比对」，而这次正是它抓住了 `ar`。
  等工具链自举、构建能在容器里原生跑起来之后，`reprotest` 才有用武之地。
- **构建主机名归一化**（Fedora 的 `%_buildhost reproducible` 对应物）
- **Python 的 `.pyc` 坑**：字节码缓存里嵌着源文件的 mtime，将来打包 Python 时
  会遇到（Fedora 为此改过 Python）
