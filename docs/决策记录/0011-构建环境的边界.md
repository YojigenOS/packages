# 0011 构建环境的边界

- **日期**：2026-10-10
- **状态**：**已决定**（自动检查机制待实现）
- **影响范围**：`base-devel` 的包集合、`host/provides.txt` 的语义、自举的判据

## 背景

构建 glibc 的时候，日志里出现了这个：

```
install -c -m 644 .../po/zh_CN.mo .../share/locale/zh_CN/LC_MESSAGES/libc.mo
```

**配方里没写 gettext，构建环境镜像里也没有人为它声明。** 它用的是镜像里 Debian
自带的 `msgfmt` ✓ 产物因此依赖了一个**配方之外的东西**。

这不是孤例。构建环境镜像里有 **615 个命令**，而配方能用哪些、不能用哪些，
**没有一条明确的线**。

## 两种哲学

| | 做法 | 代表 |
|---|---|---|
| **最小引导** | 构建环境只提供能启动构建的那几个工具，其余全部显式声明 | LFS、Gentoo |
| **完整系统** | 构建环境本身是一个完整系统，配方声明它额外要什么 | Arch、Debian |

**我们在第二侧。** 证据就是 `base-devel` 这个风味名——ADR 0003 里它叫
「base + 工具链与构建工具」，本来就是「一个完整的构建系统」的意思。

## 决定

### 一、构建环境的边界 = `base-devel` 变体的包集合

```
配方能用什么   ⟺   base-devel 里有什么
```

**一个明确、可执行、还能自动检查的定义。** 而风味机制马上要实现，两者合流。

msgfmt 那个问题因此自然解决：**`gettext` 必须在 `base-devel` 里**——它已经在
待办的那份清单上了。

### 二、自举的判据因此变清楚了

```
自举完成  ⟺  用 base-devel 能构建出 base-devel 本身
```

**这是一个固定点，也是可以实测的。** 比「构建环境是我们自己的」这种说法清楚得多。

### 三、`host/provides.txt` 是另一件事

两者容易混，写清楚：

| | 是什么 | 方向 |
|---|---|---|
| **`base-devel`** | 我们**自己构建**的构建环境 | 长大（包越来越多） |
| **`host/provides.txt`** | 暂时还**从宿主借**的东西 | 缩小（借的越来越少） |

两者在自举完成时相遇 ✓ 而且 `provides.txt` **永远不会完全空**——`glibc → make →
glibc` 那个环是真实存在的，总得有一环由宿主提供（见 ADR 0002 时期的讨论）。

## 后果

**拿到：**

- 「配方能不能用某个工具」从模糊变成可判定
- 自举有了可实测的判据，而不是感觉
- 和风味机制共用同一套定义，不会各自漂移

**代价：**

- `base-devel` 会比「最小构建环境」大不少——它是完整的 ✓ 但那本来就是它的定位
- 有些包会因此被拉进 `base-devel`（比如 `gettext`），而它们不在 `base` 里 ✓ 这是对的

## 还没定

- **自动检查怎么做。** 最严格的做法是让构建时 PATH 里只有 `base-devel` 提供的
  东西，找不到就报错——**而那其实就是自举本身**。所以在自举之前，这条线靠人守
- **`base-devel` 要不要拆。** 一个"什么都能编"的镜像和一个"能编基础包"的镜像，
  差多少包，现在不知道
- 镜像里那些**不属于任何包**的东西（比如镜像自己的 `/usr/bin/env`）怎么算
