# 0020 软件包的清理策略

- **日期**：2026-10-15
- **状态**：**已决定**（实现见 `skirt prune`）
- **影响范围**：`repo.os.yojigen.cn` 上那个包仓库的留存策略、`scripts/deploy.sh`
  顶部那条「绝不删旧版本」、`scripts/repo.sh`（索引用什么集合生成）、
  以及"manifest 钉住版本"这句话该怎么读

## 背景：repo 已经在长胖

2026-10-15 数了一遍仓库里有什么（从线上的 `APKINDEX` 读，不需要凭据）：

```
x86_64:  118 条记录 · 93 个包名 · 其中 14 个包名有多于一个版本
aarch64: 110 条记录 · 91 个包名 · 其中 14 个包名有多于一个版本

只留最新之后 —— x86_64 删 25 个文件（21%）、aarch64 删 19 个（17%）
```

而多版本的那些**正是这一周里修过 bug 的那几个**：

```
openssh         7 个：10.5_p1-r1 … r8   ← r1–r5 全是会覆盖 /root/.ssh/authorized_keys 的那个
filesystem      5 个：1.0-r1 … r6
yojigen-os-init 4 个
glibc / coreutils / gcc / grub / openssl …  各 2–3 个
```

**所以「旧的留着」在这个阶段不是保护，是留了一批已知有问题的东西。**

## 决定

**一、不推荐钉版本，尤其不推荐钉 `-rX`。**

`-rX` 是**我们的修订号**，不是上游的版本号。它跟着配方改动走（[配方约定] 里
那条 `release`），所以 `openssh-10.5_p1-r5` 这个坐标的含义是"我们自己第 5 次
改这个配方时的样子"——**而它当时的样子可能是有问题的**。

对外表达"我装了哪个版本"的正确方式是一份 **manifest**（`/etc/yojigenos-manifest`），
它是**记录**：这台机器当时是从哪些包建出来的。**它记录过去，不承诺未来。**

★ 所以 `scripts/deploy.sh` 顶上那条

> **① 绝不删旧版本。** 包仓库是【只增不减】的：manifest 钉住版本，半年后还
> 要能按同样的版本重建。

**从今天起不成立**——那句话把"记录"读成了"承诺"。真正的边界是：

    我们要能重建的       是【某个提交上的配方】(build_key 那套保证了它)
    我们不承诺能重建的   某台旧机器当时装的那一组具体 -rX

## 三种清理范围（都要有）

```
全部只留最后一个版本      每个包名只留最高的那个 (version, release)
                          openssh: 只留 10.5_p1-r8
                          → 最省，而它假设"没人需要旧版本"

每个 version 只留最后一个 r
                          同一个 version 下只留最高的 release
                          1.0-r1 / 1.0-r2 / 2.0-r1  →  留 1.0-r2 和 2.0-r1
                          → 留着"上游换了版本"这件事，只丢掉我们自己的旧修订

只清理一个指定的包        对某一个包名套上面两种之一
                          → 用来处理"某个包刚发现是坏的"
```

**为什么三种都要**：第一个管日常（仓库别长胖），第二个管"想回退上游版本"
那个少见但真实的场景，第三个管**应急**——某个包刚发现有问题时，要能只清它、
不碰别的。而第三个是最常用的那个（只在出事的当天用）。

## 怎么定"最新"

**用 `apk version -t`，不自己写比较函数。** 这个项目已经因为"自己发明一遍
上游的东西"吃过亏（见 0006、0002）。而 apk 的版本比较有它自己的规则
（`_pN`、字母后缀、`-rN`），写错一条的表现是"删掉了对的那个"——而那是
**不可逆**的。

## 顺序（不能反）

```
1. 先删文件
2. 再用【剩下的集合】重建索引
3. 最后传索引
```

反过来的话，索引里会留着一批已经不在的文件——`apk add` 到它们会 404。
而那是"看起来正常而实际是错的"最典型的样子：索引在、包不在，人看不出区别。

★ 而这条和 `deploy.sh` 里原本那条「**② 先传包，后传索引**」是同一个道理，
  只是方向相反（那条管"加"，这条管"减"）。

## 它不做什么

- **不动「上传」本身。** 日常发布照旧是 `rclone copy`（只增）——清理是一个
  **单独的、显式的**动作，不是发布流程的副作用。
- **不碰别的仓库。** 只删 `<架构>/` 下的包和那一个索引。

## 还没定的

**多久清一次、以及谁来触发。** 「周期性」是意图，而机制未定。先做成
**手工触发、默认干跑**（`skirt prune` 不带 `--go` 就只打印），跑几次看清规模
之后再决定要不要挂 `schedule`。挂上去之前先想清楚一件事：

    一次自动的运行，会把"删错了"变成一个【没人看着】的后果。
