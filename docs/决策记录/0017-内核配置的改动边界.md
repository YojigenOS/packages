# 0017 内核配置的改动边界

- **日期**：2026-10-12
- **状态**：**已决定**
- **影响范围**：`recipes/kernel/linux/config.fragment` 的内容、内核配方任何改动的流程

## 背景

x86_64 的内核在 2026-10-12 第一次被真正构建（为腾讯云那台机器准备磁盘镜像），
一路撞出五个**只有 x86_64 会发作**的问题——两个是配方里的 bug，三个是缺依赖：

| # | 问题 | 症状 |
|---|---|---|
| 1 | `make Image` 是 arm64 的目标名 | `No rule to make target 'Image'`，编了几十分钟才报 |
| 2 | 产物在 `arch/x86/` 而不是 `arch/x86_64/` | 编完了，install 找不到文件 |
| 3 | `objtool` 要 `gelf.h`（x86 才编它）| 缺一整条链：bzip2 → pkgconf → elfutils |
| 4 | `skirt order` 默认按宿主架构算 | 清单里 `linux` 排到了 `elfutils` 前面 |
| 5 | bzip2 的共享库必须先建（和主 Makefile 共用 `.o`）| `relocation ... recompile with -fPIC` |

它们一个都没在 aarch64 上暴露过——因为 aarch64 那条路是走通过的。

修第 1、2、5 条时，我**没有先问**，理由都是"它在报错"。但那不是可以自己定的
事：内核配方是这套系统里最贵、最难回退的一处，而且它的症状离原因最远。

（把这件事写进决策记录，是因为"下次还会这么想"。）

## 决定

### 一、内核配方和内核配置的任何改动，**先报后做**

**包括纯 bug 修复。**"它在报错"是好理由，但不足以自己决定——报错的是症状，
要不要动的是取舍。

### 二、`config.fragment` 只写"我们真正改变的东西"

2026-10-12 之前，它还"钉住"了 17 项（PL011 两个、virtio 六个、PCI、initrd +
gzip、devtmpfs 两个、tmpfs、proc、sysfs、ext4）。这些本来就是 defconfig 的
默认值，写与不写编出来的内核一模一样。

**这是实测的，不是推断**：同一个容器、同一个编译器，分别算「defconfig + 旧片段」
和「defconfig + 新片段」，两份 `.config` 一字不差。

于是那 17 行删掉了。依赖没有消失，只是换了归属地——写在**消费方**更靠得住：
`yojigenos-init` 的 `/init` 里那句「devtmpfs 由内核自动挂载
（CONFIG_DEVTMPFS_MOUNT）」就是那个依赖的归属地。

**现在的全部改动 = 两项**：`CONFIG_MODULES=n`、`CONFIG_DEBUG_INFO_NONE=y`。
（相对纯 defconfig：3039 行选项差异，其中 2999 行是 `MODULES=n` 的级联，
40 行/约 20 个选项是片段真正造成的。）

### 三、不加云厂商专属驱动

考虑过这些：`VIRTIO_SCSI` + `SCSI_VIRTIO`（阿里云 / GCP / OpenStack 的默认
磁盘）、Hyper-V 的网卡与存储（Azure 用的不是 virtio）、`VMWARE_PVSCSI`、
`ISO9660`（云厂商的 config-drive），以及可选的 `GVE` / `IXGBE`。

**不加。** 理由：

1. **目标机器固定。** 那台腾讯云机器用 `virtio-blk` + `virtio-net`，现有配置
   已经覆盖。多出来的是**不打算用的场景**。
2. **加了也验证不了。** 我们只有那一台机器的实测；Azure / GCP 的驱动加进去
   只是"按需求声明"，不是"验证过"。这种东西堆在内核里，将来是负担。
3. **代价是实打实的**：两个架构的内核各重编一次，收益为零。

将来真要支持别的云，**先决定"要不要支持这个场景"，再动配置**——顺序不能反。

## 后果

**拿到：**

- 内核配置的 diff 从 62 项降到 20 项，其中 19 项还是 `MODULES=n` 的连带。
  唯一"直接写下"的就是那两项——**读得懂**
- "改动需要确认"这件事有了出处，不再靠记性

**代价：**

- 一张镜像只在**实测过的那台机器**上有保障。别的云能不能起，不知道，也不承诺
- 删掉钉住之后，如果 defconfig 改掉某个我们依赖的默认值（比如
  `DEVTMPFS_MOUNT`），症状会出现在看起来无关的地方（"/init 起来时 /dev 是空的"）

## 还没定

- **新版内核带来的选项漂移怎么审。** 现在靠 `merge_config.sh` 对"消失的选项"
  报警；Fedora 那种"把每次 rebase 新增的选项生成一条待审片段"的机制值得抄，
  但还没做
- **`DEBUG_INFO_NONE` 要不要为 BTF 让路。** 开了才能用 `bpftrace` 这类 eBPF
  CO-RE 工具，代价是多一个 `pahole` 依赖 + 内核里几 MB 的 `.BTF` 段。现在不需要
