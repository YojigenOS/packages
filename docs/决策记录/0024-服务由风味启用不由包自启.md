# 0024 服务由【风味】启用，包只提供定义

**2026-10-22 定。** 它回答的是"一个软件的服务该由谁决定开机自启"。

## 起因

接 docker 的时候，我把"起 dockerd"写成了 `boot.d/30-docker` —— 也就是照
`openssh` 的 `boot.d/20-sshd` 的样子做。而 YG 指出：

> `boot.d` 这里的东西，应该必须是真的系统需要的东西。而不是一些外部软件的补丁。

对。分界是这一句：

    没有它，这台机器【不算一台能用的机器】     → boot.d
    它没起来，系统照样是系统                  → 服务

按这个分界，`boot.d` 里该有的只有：挂 cgroup、设 hostname、扩根分区、控制台键盘。
而 `20-sshd`（openssh）和 `30-docker`（docker）**都是外部软件**，都不该在那儿。
后一个当场拿掉了；前一个是老问题，和这次一起修。

## 决定

**三层，各管一件事：**

    包       提供【服务定义】：/usr/lib/yojigen-os/services/<名字>
             它只有 start / stop 两个动作。**包永远不自启自己的服务。**
    风味     决定【启用哪些】：variants/<风味>.toml 里声明
    系统     执行：/init 在 boot.d 之后，逐个 start /etc/services/ 里启用的那些

而 YG 给的例子就是这条规则的由来：

> 我们将来会有一种风味，就是 `server`，这个风味就应该有自动启动 ssh 服务。

也就是说 **"装 openssh" 和 "开机起 sshd" 是两件事**，而后者是风味的决定：

    base（容器）    装了也不启用 —— 容器的"启动"是它的 entrypoint，不是 init
    minimal         启用 sshd（0008：能开机、能串口、能 SSH）
    server（将来）  启用 sshd + 硬化 + 更多服务
    devel           不启用（它是个构建环境，用完就扔）

## 为什么不是包自己决定

因为**同一份包会被几种风味装**。包一旦自启，"minimal 里 sshd 会不会自己起来"
就由包说了算，而那是风味该回答的问题。今天 `openssh` 就是自启的 —— 于是
"容器里装 openssh 也会想起 sshd"这种荒唐事只是**运气好没发生**（容器根本不跑
`/init`），而不是设计如此。

## 附带一条：启用状态属于管理员

`/etc/services/<名字>` 是**软链接**（指向那个定义），走 apk 的 `conffiles`：

    · 包升级不会覆盖管理员的启用/停用决定
    · 而"启用"这件事在盘上看得见（`ls /etc/services/`）

## 还没做的

- `pantsu` 的 `variants/*.toml` 加 `services = [...]`
- `yojigen-os-init` 加 `service` 命令 + `/init` 扫启用的服务
- `openssh` 的 `20-sshd` 搬家（它同时还做"生成主机密钥"，那属于服务定义的 start）
- `docker` 加服务定义（**不启用**）
- `minimal` 声明 `sshd`
