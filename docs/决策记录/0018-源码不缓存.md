# 0018 源码不缓存

- **日期**：2026-10-15
- **状态**：**已决定**
- **影响范围**：`skirt/skirtlib/source.py` 的取源码路径、`var/` 的目录结构、
  `bootstrap.yml` 的缓存清单、`scripts/smoke.sh` 的一项检查

## 背景

驱动原来保留下载过的源码：放在 `var/cache/` 里，下次构建同一个包时，如果
文件名和配方声明的 `sha256` 都对得上，就直接用它，不再下载。

它的价值只有一个：**同一台机器上的重复构建省一次网络**。

而它带来的风险是真的，并且已经写进过文档（`配方约定.md` 里那一节标题就叫
「源码缓存的陷阱（还没修）」）。最难受的不是它会出错，而是**它出错时不说话**：

```
换了配方里的 URL
  → 缓存命中，直接用旧的
  → 日志里连一行 [下载] 都没有
  → 报的错是 ./configure: No such file or directory
  → 而那个错和你改的地方毫无关系
```

## 决定

**完全移除。** 每次构建都重新下载一份，下到 `var/work/download/`，而那个目录
在每次取源码时先清空。`var/cache` 这个路径不再存在。

`sha256` 的校验、多源重试、失败时打印是哪一源——一个字不改。

## 理由

**一、它的价值在我们这儿是零。** 我们没有任何在本地构建的计划。这不是"暂时
不做"，是方向：全量构建、两个架构、发布，都在 CI 上。

**二、它在 CI 那两条线上处境都不好。** 我查了 workflow：

| 线 | 它在那儿的样子 |
|---|---|
| `release.yml` | 一个字都没提到它 → 每次 runner 是全新虚拟机 → 缓存永远是空的 → 它一点用没有 |
| `bootstrap.yml` | 确实缓存了它，而 `restore-keys: bootstrap-<arch>-` 会退到上一轮的缓存 → 改了配方之后，那次构建可能用到上一轮的旧源码 |

也就是说：**它在该有用的地方（本地）用不上，在该干净的地方（CI）反而可能
带来旧东西。**

**三、它的有效性靠的是巧合，不是推理。** 「URL 最后一段 + 声明的 sha256」
这两个东西碰巧对得上，就算缓存可用。而决定产物的东西远不止这两个——这正是
`待办.md` 1.5.B 那条要说的事。**缓存的有效性应该由配方内容算出来。**

## 代价

**每次构建多一次下载。** 在 CI 上这不是新增代价（原来也是每次都下）。在本地
单包构建时会变慢，而按上面的方向，那条路我们不走。

`scripts/smoke.sh` 的第①项检查（内核源码解压完整性）原来从 `var/cache/` 里找
内核 tarball。现在那个地方没有了，所以它改成：用 `KERNEL_TAR=` 指定一份，或者
跳过。**故意不在那里自动下载**——它一百多 MB，而 smoke.sh 的定位是"大约 1 分钟"。

## 还没定

- **`build_key`（待办 1.5.B）仍然没做。** 那一层管的是"要不要重新建"，而这一条
  管的是"源码从哪来"。两件事。移掉缓存之后，"重新建"这件事反而更清楚了：
  现在没有"上一次的源码"这个变量，判断只需要看配方内容、构建环境、驱动、依赖。
- **`var/output/` 和 `var/pkgs/` 仍然是跨运行复用的**（前者不缓存，后者缓存）。
  它们会不会有和这里同类的问题——"复用了不该复用的东西"——**没有审过**。
  这一条记在这里，等有空再看。
