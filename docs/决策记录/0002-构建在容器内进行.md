# 0002 构建在容器内进行，不在宿主目录

- **日期**：2026-10-10
- **状态**：已决定
- **影响范围**：`skirt` 的执行方式；所有包的构建环境

## 背景

第一次构建 glibc 失败，但失败原因和 glibc、和工具链都没有关系。

失败信息是：

```
mv: '/work/src/glibc-2.44/_build/nptl/stamp.oST' and
    '/work/src/glibc-2.44/_build/nptl/stamp.oS' are the same file
    *** [../o-iterator.mk:9: .../nptl/stamp.oS] Error 1
```

而在失败之前，构建已经用**我们自建的 gcc** 成功编译了数千个 glibc 源文件。也就是说，工具链叠加是通的，问题出在别处。

## 根因

**macOS 的 APFS 默认大小写不敏感（case-insensitive）。**

glibc 的构建系统（`o-iterator.mk`）会生成两个只差最后一个字母大小写的中间文件：

```
stamp.oS     共享（shared）目标
stamp.oST    共享 + 静态（shared + static）目标
```

在 Linux 的 ext4 上这是两个不同的文件；在绑定挂载到容器里的 macOS 目录上，它们是同一个文件，于是 `mv` 报错。

**这不是 glibc 的问题，也不是我们配置错了**——它只会在"在 macOS 上构建 Linux 软件"时出现。

## 决定

**整个构建过程在容器内的 Linux 原生文件系统里进行。**

宿主目录只作为传送带：

```
宿主 build/  ──/in──▶  容器
  src/                   /work-local/src      解压后的源码
  steps.sh               /work-local/steps.sh 包提供的步骤脚本
  sysroot/               （合并进容器根文件系统）
                         /work-local/dest      安装目标（$PKGDEST）
宿主 build/  ◀──/in──  容器
  dest/                  /work-local/dest 拷回
```

容器内不再有绑定挂载的工作目录，`WORK=/work-local` 是容器自己的文件系统。

## 理由

1. **消除整个 bug 类**，而不只是绕开 glibc 这一处。任何产生大小写冲突文件名的构建都会踩同样的坑，而这类冲突往往要构建到很深处才暴露。
2. **性能**。绑定挂载上的海量小文件 I/O 比容器内慢一个数量级，而构建过程恰好就是海量小文件读写。构建越重，差距越明显。
3. **职责更清楚**。宿主目录不再承担"构建场所"的角色，只是输入和输出的通道。这与我们最终要做的"构建环境自举"方向一致——构建应该在受控环境里发生。

## 后果

- **构建树不再能从 macOS 直接翻看**。需要检查中间产物时用 `docker cp`，或临时把 `WORK` 挂出来。
- 容器内的路径约定固定为：`WORK=/work-local`、源码 `$WORK/src`、`$PKGDEST=$WORK/dest`、`$SRCDIR` 由驱动注入。
- `steps.sh` 里不应写死宿主路径。它通过 `$SRCDIR`、`$PKGDEST`、`$WORK` 与环境交互。
- 宿主与容器之间**只传源码和产物**，不传中间文件。

## 未采用

- **只在 `out_of_tree` 的包上把构建目录搬进容器**：改动更小，但 in-tree 构建的包仍有同样风险，等于留下半个 bug。
- **在 macOS 上建一个大小写敏感的卷**：需要 `diskutil` 和额外权限，对每个开发者的机器都要额外配置，且不解决 I/O 慢的问题。
