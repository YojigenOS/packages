# 0022 有官方二进制就只分发，不编译

- **日期**：2026-10-16
- **状态**：**已决定**（`vendor` 那个字段与两条自动判据待实现）
- **影响范围**：`recipes/` 里放什么形状的配方、仓库里该有多少包、那条"交付物里没有别人的东西"的边界在哪

## 背景

要给系统加 node、bun、rust、docker、systemd，目标是一条具体的验收：**能装 1panel 并让它跑起来**。

而在算这条链要多久的时候，先撞上的是**我一个过时的印象**：我说 bun 是 Zig 写的，
所以只能借官方二进制。查了一下：

```
oven-sh/bun 的语言组成（GitHub API）
  Rust          69,316,573 字节   76.0%
  C++           12,483,376 字节   13.7%
  TypeScript     6,547,682 字节    7.2%
  C              1,421,473 字节    1.6%
  …
  Zig                    0 字节    0.0%
```

**它是 Rust 了**，而我一整晚都在按"要 Zig"算。这处纠正本身不重要，重要的是它引出的问题：

> **这种上游自己有官方二进制的包，要不要自己建？**

翻了一遍决策记录（packages 21 条 + distro 19 条）——**没有一条是关于这件事的**。
0002 说构建在容器里、0011 说构建环境的边界，那两个都是**技术层面**的；而"要不要自己建每一个包"
是更高一层的问题。

## 那条线其实已经画过一次，而画在别处

0011 写的是：

```
配方能用什么   ⟺   devel 里有什么
```

那是**构建期**的边界。而今晚又有另一条被证明过：

```
交付物里不许有别人的二进制
```

（那个测试是这次会话里立的，而它当场抓到了一次违规——一份 `BOOTX64.EFI`
里数得出 `alpine` 这个词，来源是 `grub.cfg` 里的一句注释。见 `distro/docs/决策记录/0013`。）

★ 但那两条**都没有回答运行期**：**发出去的盘上，哪些东西可以是别人的？**

## 决定

### 一、规则

> **有能直接运行的官方构建 → 只分发，不编译。**
> **没有 → 自己建。**

不是"尽量自己建"，也不是"能不建就不建"——是**按上游给不给**来分。理由在下一节。

### 二、这条规则自己就定义了"系统"和"应用"

```
上游给通用二进制的      =  应用   →  只分发
     node · bun · rust · go · docker · containerd · runc · 1panel …
上游给不了的            =  系统   →  自己建
     内核 · libc · 引导器 · init · 包管理器 · systemd …
```

★★★ **而这个分界不是我们画的**——是**上游自己划的**。给不给通用二进制，取决于
**它和发行版绑不绑**：

- libc 和内核**不可能**给"通用二进制"，因为它们**就是**发行版的一部分；
- systemd 同理（它要接 init、要管 udev、要和发行版的服务约定对齐）；
- 而一个 JS 运行时、一个容器引擎、一个面板程序，**它们在哪都长一样**。

**所以"发行版的本体"这件事，由上游的发布行为替我们定义好了。**

★ 而这也回答了一个可能的担心：「只做分发」会不会让这个项目变成 remix？
**不会。** 那个问题问的是**内核 · libc · 引导 · init · 包管理**是不是自己的——
而那几样，按这条规则，**恰好全都拿不到官方二进制**，所以**必须自己建**。

### 三、丑话说在前：这条规则的代价

| 代价 | 说明 |
|---|---|
| **校验只到 sha256 + 上游签名** | 我们读不了源码里有什么。上游说这是 bun，那就是 bun |
| **架构由上游决定** | 它给 x86_64 和 aarch64 我们就有，它不给就没有 |
| **修不了它的 bug** | 只能等上游，或者自己打补丁（而那就等于自己建了） |
| **依赖是它自己带的** | 官方二进制常是静态的、或者带一堆 .so——**那些库不在我们的账上** |

★★★ 而最后一条引出**必须做的记账**：

> **"这个包是别人的"必须在体力上看得见。**

现在仓库里 89 个配方**全都是自己建的**，所以这件事还不需要表达。而加了第一批
分发包之后，**过一年没人能说出盘上哪些是借的**——除非现在就把记号留下。

具体形状（实现时定）：`[build]` 里加一个 `vendor = <上游>`,或者把这类配方放在
单独的目录（`recipes/vendor/`），或者 spec.toml 里一个必填字段。**哪一种都行，
但必须有**——而 CI 该能算出「这个风味里有 N 个包来自上游二进制」。

## 判据：两条，都能自动检查

规则要能被执行，就得有能自动跑的判据。这条规则有两条：

### 判据一：`ldd` 里没有我们没有的库

官方二进制是给**别的 glibc 发行版**编的。它可能链一堆我们仓库里没有的东西。

```
如果它的 ldd 里有某个 .so 不在我们的仓库里 → 它装上去就跑不起来
```

★ 而这条能**完全自动**：对每个 `vendor` 包，拿它的产物跑 `ldd`，把结果和我们
仓库的包名对一遍。**这是唯一一条能提前抓住"这个二进制在我们系统上跑不了"的检查。**

★ 好消息是**我们也是 glibc**，所以大部分能直接用（而这也说明 glibc 那个选择是对的：
换成 musl 的话，全世界的官方二进制**一个都用不了**）。

### 判据二：它真的能跑

```
<那个程序> --version     # 或者一个最小 smoke
```

★ 0010 已经立了"上游测试"那条；这里要的是它的最小版本——**能启动、能报版本**。

## 对 1panel 那条链的后果

按这条规则重算一遍那个目标：

```
原来算的（按"自己建"）:
    node  ← 自己建（C++ 工具链 ✓）
    rust  ← 先借一次官方 rustc，然后自举
    bun   ← 要 rust nightly + 特定组件 + 特定 targets（而且它自己的 CI 都用镜像）
    go    ← 先借一次
    docker ← 要 containerd + runc + 十来个库
    systemd ← 自己建（原本也要）
    → 一条几层深的链

现在（按这条规则）:
    node · bun · rust · go · docker · containerd · runc · 1panel
        → ★ 全部落进「分发」
    → ★★ 而剩下【只有 systemd 自己建】+ 内核那四行配置
```

**链一下子短了。** 而这不是"走了捷径"——是**目标没变、而路径按上游的实际情况修正过**。

★ 而 systemd 那条也没被绕开：它是 1panel 的硬前提，而它按这条规则**必须自己建**
（没有官方通用二进制）。**该难的还是难。**

## 和仓库里那 89 个配方的关系

**它们不变。** 这条规则是**加**一种新的配方形态，不是改旧的：

```
recipes/tool/… lib/… net/… …   ← 自己建（现有的 89 个 + 将来那几百个）
recipes/<新的一类>/…            ← 分发上游二进制（这条路刚刚开）
```

★ 而两类的**验收不一样**：自己建的那类，判据是**它的构建过程在我们控制之内**；
分发的那类，判据是上面的两条（ldd + 能跑）。**别用同一把尺子量。**

## 没决定的事

- `vendor` 那个记号叫什么、写在哪（上面列了三种候选，实现时挑一个）
- 官方二进制的**签名怎么校验**（有的上游给 GPG，有的只给 sha256，有的连 sha256 都在一个 https 页面上——那三种的可信度不一样）
- **要不要把上游的源码也留一份**（我们现在按 0018 是不缓存源码的；而分发包里源码根本没下过）
- 而 1panel 那条验收怎么跑（它要 docker + systemd，而那两个起来之后才谈得上）

## 2026-10-21 补：「官方」的边界定义在 0023

这条规则里那句「有**官方**二进制的就只分发」，2026-10-21 被判清楚了：
**「可信源」= 上游项目自己发布的二进制**，第三方重新编译的再流行也不算
（含 `python-build-standalone` / `conda-forge` / 发行版的 `-bin` 包）。

见 `0023-什么算可信源.md`。★ 而它带来一个具体结论：**`python3` 永远自己建**
（python.org 不发 Linux 二进制），253 MB 靠按 0014 拆子包解决，不靠换源。
