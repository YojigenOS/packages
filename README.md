# YojigenOS

一个从零构建、中文优先的 Linux 发行版。

**当前状态：第 1 周 · 构建环境准备 · 尚无系统代码。**

---

## 这是什么

YojigenOS 不是任何发行版的衍生版。它的基础系统从上游源码自举构建，不拿任何发行版的包作为起点。

"从零构建"的准确含义是**从工具链开始重建**，而不是"从内核开始"。内核在这条链上的位置比想象中靠后——它在依赖图里出现两次，一次是头文件（很早），一次是内核镜像（最晚）。

## 三条要求

1. **从零构建** —— 基于 Linux 内核自举，不基于任何发行版魔改
2. **兼容主流生态** —— 主流国产商业软件可靠运行，常见开源软件可从源码构建
3. **中文优先** —— 开箱即用的中文环境，精简、轻巧、简单易用

第 2 条是**收窄过**的表述。原本的"兼容主流 Linux 生态"没有边界，等于承诺一切，会吞掉第 1 条和第 3 条。收窄之后它从一句口号变成了可以验收的清单。

## 由要求推出的技术决策

下面这些不是偏好，是上面三条要求的**后果**。换掉它们不是"换个阵营"，而是要自己付一笔长期的人力账。

| 决策 | 由哪条推出 | 原因 |
|---|---|---|
| **glibc** | 2 + 3 | 国产商业软件是基于 glibc 的预编译二进制。走 musl 需要 Flatpak 兜底，而 Flatpak 的输入法集成风险最高——输入法恰恰是中文体验的核心 |
| **systemd** | 2 | 主流生态默认假设有 logind / udev / cgroup 委托。替代方案的补丁负担是长期人力支出 |
| **GNU coreutils** | 2 | 上游构建脚本默认 GNU 行为。换掉会让大量脚本**静默出错**，而不是报错 |
| **bash** | 2 | 大量脚本使用 bash 特有语法（`[[ ]]`、数组、`shopt`） |
| **分层构建** | 1 | 核心层（约 50~100 包）完全自举；生态层（数千包）整合上游配方思路。独立性来自"自己构建每一个包"，不是"自己发明每种打包方式" |

## 架构策略

| | |
|---|---|
| 开发 | **aarch64**（原生速度） |
| 目标 | aarch64 + x86_64 |
| x86_64 产出方式 | **交叉编译**，不是模拟 |

不要同时自举两个架构——那等于把整个自举流程重做一遍。

## 路线图

| 阶段 | 时间 | 验收标准 |
|---|---|---|
| 1 | 第 1 周 | Linux 构建机就绪 |
| 2 | 第 2 周 | 构建系统骨架，能构建第一个包 |
| 3 | 第 3~4 周 | 工具链自举：`binutils` → `gcc` → `linux-headers` → `glibc` |
| 4 | 第 5~6 周 | 一个**脱离宿主机**、可 chroot 运行的 rootfs |
| 5 | 第 2~3 月 | 能开机到 shell |
| 6 | 第 3~6 月 | 中文优先落地：输入法、字体、locale 全部开箱即用 |

第 3 阶段是整条路上唯一的硬技术关卡（依赖环 + 强连通分量），同时也是文档最充分的地方。

## 仓库结构（规划）

```
packages/      配方树 —— 真正的核心资产
tools/         构建系统
host/          宿主环境准备脚本
docs/          文档与决策记录
```

## 三条纪律

1. **第 1~4 阶段只在 aarch64 上工作**，不碰 x86_64
2. **从第一天起，所有产物就带架构维度**（输出路径、包元数据、命令行参数），但不去执行
3. **每个阶段结束时必须有一个"能用的系统"** —— 这个约束会自动阻止同时调试两件难事

## 现在不要做的事

内核、ISO、安装器、logo、壁纸、主题、第二个架构、赞助页、文档站。

它们都有明确的时机，但不是现在。
